# 검증 체계

## 검증 대상

| 대상 | 질문 | 기준 | 방법 |
|---|---|---|---|
| Product Validation | 올바른 문제와 해결책인가 | 성과 조건 | 관찰·실험·지표 |
| Engineering Verification | 요구대로 동작하나 | 계약·완료 조건 | 테스트·빌드·리뷰 |
| Agent Evaluation | AI와 스킬이 안정적으로 수행하나 | 작업 정의·개발 원칙 | 반복 실행·실패 분석(`build-skill`이 맡음) |

## 기준의 층

| 기준 | 위치 |
|---|---|
| 제품 성공 기준 | `PRODUCT.md` |
| 기능 성과 조건 | PRD Success Criteria |
| 작업 완료 조건 | 작업 정의 |
| 도메인 계약 | 타입·인터페이스 |
| 실행 가능한 검증 | 테스트 |

정성적인 경험(사용성·재미·몰입)은 사람의 관찰을 포함한다.

## 기대 동작을 먼저 정한다

- 구현 전에 관찰할 수 있는 기대 동작과 필요한 실패 상황을 정하고, 가능한 범위에서 계약과 자동화 테스트로 표현한다.
- 엄격한 TDD를 강제하지 않는다. 구현 결과에 맞춰 기준을 나중에 바꾸지 않는 것이 핵심이다.
- 테스트 삭제·비활성화·기대값 완화로 실패를 숨기지 않는다. 승인된 요구 변경은 계약과 테스트에 함께 반영한다.
- 테스트는 구현 방식을 복제하지 않고 밖에서 관찰할 수 있는 결과를 본다.

## 방법 고르기

| 방법 | 대상 |
|---|---|
| 타입·계약 검사 | 유효 상태, 입출력, 사전·사후 조건 |
| Unit | 독립 도메인 규칙 |
| Integration | 저장·조회·서비스 연동 |
| E2E | 전체 사용자 흐름 |
| 정적 분석 | 린트·정적 품질 |
| 사람 리뷰 | 가독성·UX·재미 |
| 기기 | GPS·BLE·백그라운드 실행 등 |
| 사용자 실험 | 행동과 제품 가치 |

빠르고 유지하기 쉬운 검증을 충분히 쓰고, 통합과 실제 흐름도 확인한다. 비율은 강제하지 않는다.

## 실패 원인별 대응

| 원인 | 대응 |
|---|---|
| 구현 결함 | 코드 수정 후 재검증 |
| 계약 결함 | 설계 재검토 |
| 요구사항 문제 | 사람 판단 |
| 제품 가설 실패 | Discovery로 |
| 환경 문제 | 검증 환경 확보. 못 하면 통과가 아니라 미검증 |
| AI 수행 실패 | 스킬·지침·도구 개선 |

같은 실패가 반복되면 재시도하지 않고 원인을 분류한다.

## 완료 조건과 성과 조건

| | 완료 조건 | 성과 조건 |
|---|---|---|
| 질문 | 제대로 만들었나 | 만들 가치가 있었나 |
| 언제 | 구현 중·출시 전 | 실험·출시 후 |
| 정하는 때 | 구현 전 | 실험·출시 전 |

- 성과 조건에는 대상 사용자, 관찰 항목, 성공으로 볼 결과, 표본·기간, 볼 날을 적는다. 기준값을 모르면 「기준값을 잰 뒤 정함」으로 적는다.
- 표본이나 기간이 부족하면 판단을 유보하고 필요한 증거를 적는다.
- 완료 조건을 테스트로 옮겼으면 같은 체크리스트를 PRD에서 반복하지 않는다. 자동으로 판별하기 어려운 것은 리뷰 기준으로 둔다.

## 완료 보고

| 항목 | 담는 것 |
|---|---|
| Changes | 바꾼 동작 |
| Verification | 실제로 돌린 검사와 결과 |
| Remaining | 미검증과 남은 문제 |

실행한 검사와 실행하지 않은 검사를 구별한다.
