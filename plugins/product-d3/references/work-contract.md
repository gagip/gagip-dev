# 작업 정의와 사람이 정하는 곳

## 작업 정의 네 칸

작업(Work)은 제품이나 지식에 대한 일시적인 변경 하나다. 시작 전에 아래 네 칸을 필요한 만큼 채운다. 간단한 작업은 대화의 한 문단이면 된다. 전역 지침이 명세 형식을 정했으면 그 형식으로 쓰고 네 칸이 모두 들어갔는지만 본다.

| 칸 | 담는 것 |
|---|---|
| Objective | 무엇을 왜 바꾸나 |
| Context | 읽을 PRD·코드·테스트·자료 |
| Constraints | 유지할 동작, 건드리지 않을 곳, 지킬 규칙 |
| Completion Criteria | 관찰할 수 있는 완료 상태. 실패 상황 포함 |

작업 정의는 오래 보존하지 않는다. 장기간 보존할 필요가 있을 때만 이슈로 둔다. 기능의 의도는 PRD에 둔다.

작업 중 지킬 것(불변식): 제품 방향, 기존 동작, 개발 원칙, 위임 범위. 끝에 낼 것(사후 조건): 완료 조건 검증 결과, 바꾼 것, 남은 문제.

## 영향도와 불확실성

불확실성은 무엇을 해야 하는지의 명확성, 영향도는 잘못 판단했을 때의 비용이다.

| | 불확실성 낮음 | 불확실성 높음 |
|---|---|---|
| 영향도 높음 | 계획을 보이고 승인받은 뒤 실행: 데이터 이전, 공개 API·저장 형식 변경, 화면·문구 변경 | 사람이 정한다: 방향 전환, 핵심 경험 변경 |
| 영향도 낮음 | 묻지 않고 실행: 바로잡을 값이 분명한 버그, 외부 동작이 그대로인 리팩터링, 테스트 추가 | 스스로 탐색하고 안을 낸다: 아이디어, 폐기용 프로토타입 |

- 실패 비용이 낮으면 불확실한 탐색도 맡아서 한다.
- 전역 지침의 승인 등급이 이 표보다 엄격하면 전역 지침을 따른다.

## 사람에게 묻는 때

다음이면 문제·대안·영향을 보이고 판단을 요청한다. 그 밖의 실패(단순한 테스트 실패 등)는 범위 안에서 스스로 푼다.

- 제품 의도를 바꿔야 한다
- 범위를 넓혀야 한다
- 제약을 어겨야 한다
- 데이터 손실·개인정보·안전 위험이 있다
- 기준끼리 충돌한다(PRD와 테스트가 다른 동작을 요구 등)
- 진행할 수 없다
- 되돌리기 어려운 외부 작업이다

## 정하는 사람

| 활동 | 사람 | 에이전트 |
|---|---|---|
| 방향·문제 | 최종 가치 판단 | 조사·분석·문제 후보 |
| 해결책·요구사항 | 상위 의도와 중요한 변경 | 대안·구체화·모순 찾기 |
| UX·기술 설계 | 주요 경험과 제약 | 시안·계약·구조 |
| 구현·검증 | 필요할 때 리뷰 | 구현·테스트·빌드·자체 리뷰 |
| 출시 | 출시 정책과 권한 | 준비와 허용된 배포 |
| 성과 | 성과 판단 | 분석과 개선안 |

에이전트의 분석은 실제 사용자 증거를 대신하지 않는다. AI가 낸 분석은 그렇다고 표시한다.
