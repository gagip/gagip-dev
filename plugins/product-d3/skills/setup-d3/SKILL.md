# setup-d3

프로젝트에 D3를 한 번 깐다. 결과는 `PRODUCT.md` 초안, `docs/`, `AGENTS.md`의 D3 블록, 다음에 풀 문제 하나다. 판단 기준은 [d3-core.md](../../references/d3-core.md), 경로와 틀은 [paths-and-templates.md](../../references/paths-and-templates.md)를 따른다.

## 1. 현황 읽기

```bash
python3 <이 플러그인>/scripts/inspect_project.py <프로젝트>
```

`mode`가 `new`면 2절, `existing`이면 3절로 간다. `AGENTS.md`에 이미 `<!-- product-d3 start -->`가 있으면 깔린 프로젝트다. 다시 깔지 않고 방향 수정은 `set-direction`이 맡는다고 알린다.

## 2. 새 프로젝트

1. 사용자에게 묻는다: 누구의 어떤 상황·문제인가, 핵심 가치, 원칙(갈릴 때 고를 쪽), 비목표, 사용자에게 어떤 변화가 생기면 가치를 준 것인가. 한 라운드에 모아 묻고 질문마다 권장안을 붙인다.
2. 답을 `PRODUCT.md` 일곱 칸에 쓴다. 근거가 없는 줄은 「(가설)」과 확인할 방법을 붙인다. 답이 없는 칸은 지어내지 않고 「미정」으로 둔다.

## 3. 기존 프로젝트

1. 실제로 쓰이는 화면(띄울 수 있으면 띄워 본다), README, 기존 결정 기록, 이슈, 사용자 반응을 읽어 목적·사용자·핵심 가정을 정리한다.
2. 이를 바탕으로 `PRODUCT.md` 초안을 쓴다. 관찰 근거가 부족한 줄은 「(가설)」로 표시한다. 다른 이름의 방향 문서가 이미 있으면 새로 만들지 않고 어떻게 할지 묻는다.
3. 기존 코드·테스트에서 알 수 있는 동작을 문서로 역작성하지 않는다. 기능별 PRD를 한꺼번에 만들지 않는다. PRD는 그 기능을 다음에 바꿀 때 만든다.
4. 핵심 기능과 진행 중인 작업을 유지·개선·보류·제거 후보로 판정하는 일은 `set-direction`의 점검이 맡는다고 알린다.

## 4. 틀 만들기

검증 명령은 1절 JSON의 `verify_commands`에서 실제로 쓰이는 것을 고르고 한 번 돌려 본다. 돌지 않으면 「없음」으로 둔다.

```bash
python3 <이 플러그인>/scripts/d3_scaffold.py init --root <프로젝트> --verify-command "<명령>"
```

- `PRODUCT.md`가 이미 있으면 스크립트가 건너뛴다. 2·3절 초안은 그 파일을 고치는 안으로 보인다.
- `AGENTS.md`가 이미 있으면 스크립트가 병합할 블록을 출력한다. 기존 내용과 겹치거나 충돌하는 줄을 표시해 보이고, 승인받은 뒤 블록을 기존 파일에 넣는다.
- 지침 파일은 `AGENTS.md`만 만든다. `CLAUDE.md` 등 다른 하네스 파일은 만들거나 고치지 않는다.
- `README.md`가 없고 실행 방법이 있으면 설치·빌드·실행만 적은 최소본을 만든다.
- 다른 폴더(`design/`·`architecture/`·`experiments/`)는 만들지 않는다.

## 5. 검사와 보고

```bash
python3 <이 플러그인>/scripts/check_d3_docs.py --root <프로젝트>
```

오류 0을 확인한다. 보고에 만든 파일·건너뛴 파일, 「(가설)」·「미정」 줄, 검증 명령과 실행 결과, 다음에 풀 문제 하나(사용자에게 고르게 함)를 적는다. 그 문제의 탐색은 `discover-problem`이 맡는다.
