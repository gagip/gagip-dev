# deliver-work

코드 변경 하나를 끝까지 진행한다. 사용자는 Define 승인(필요할 때)과 Finalize 보고에서만 관여한다. 아래 다섯 단계를
작업 목록에 올리고, 단계마다 아래 "끝났다고 보는 기준"을 모두 만족한 뒤 다음으로 간다. 진행은 작업 목록과 커밋으로 보인다.

기준 문서: 생명주기·유형·읽는 범위는 [work-lifecycle.md](../../references/work-lifecycle.md), 작업 정의와 묻는 때는
[work-contract.md](../../references/work-contract.md), 검증은 [verification-system.md](../../references/verification-system.md),
영향 범위는 [change-propagation.md](../../references/change-propagation.md), 문서 경로는
[paths-and-templates.md](../../references/paths-and-templates.md). 구현 방법은 대상 레포의 `AGENTS.md`·`CLAUDE.md`를
따르고, 레포 관례가 다루지 않는 코드 판단은 [coding-philosophy.md](../../references/coding-philosophy.md)를 따른다.

## 1. Understand

- 유형을 고른다: Feature(새 동작) · Enhancement(기존 동작 변경) · Bug Fix(의도와 다른 동작) · Refactoring(외부 동작
  그대로, 구조만). 둘이 섞이면 나누거나 큰 쪽으로 보고 다른 쪽을 Define에 적는다. 결정을 바꿀 가설이 확인되지 않았으면
  실험(`validate-hypothesis`)이 맡는다고 알리고 멈춘다.
- 유형별 읽는 범위대로 `AGENTS.md` → `PRODUCT.md` → 관련 PRD → 계약·코드·테스트 순으로 찾는다. 주석·변수명이 아니라
  실제 문자열·값·동작을 본다. 안전·개인정보에 닿으면 버그 수정이라도 PRD로 의도를 확인한다.
- Feature·Enhancement면 PRD가 있는지와 Problem·Solution·Scope·Success Criteria가 찼는지 본다. 문제·근거부터 없으면
  `discover-problem`이 맡는다고 알리고 멈춘다. 범위·예외·검증 방법만 비었으면 Define에서 빈칸과 권장안을 보인다.
- PRD·테스트·코드가 서로 다른 동작을 말하면 어느 쪽이 결함인지 근거로 판정하고, 불명확하면 Define에서 묻는다.
- 이슈는 대상 레포 안에서 `gh issue view <번호> --json title,body,labels,number`로 읽는다. 같은 작업의 브랜치·워크트리가
  있는지 `git worktree list`·`git branch --list`로 보고, 있으면 이어간다. 승인된 계획서(머리말 `상태: 승인됨`)가 있으면
  그것이 기준이다.

끝났다고 보는 기준:
- 프로젝트 지침, 이슈·PRD·계획서, 바꿀 코드가 닿는 흐름을 끝까지 읽었다.
- 이미 해결됐거나, 없는 파일·심볼을 전제하거나, 준비물이 없으면 근거를 모았다. Define에서 보이고 진행 여부를 묻는다.
- 요청을 둘 이상으로 읽을 수 있거나 결과물이 달라지는 애매한 점을 질문으로 정리했다. 질문마다 맥락과 권장안을 붙였다.

## 2. Define

작업 정의 네 칸(Objective · Context · Constraints · Completion Criteria)과 유지할 동작을 쓴다. 완료 조건은 구현 전에
관찰할 수 있는 동작과 실패 상황으로 쓰고, 영향 범위는 전파표로 정한다. 사용자 기능은 기대 동작 하나씩 수직으로 나눈다.

영향도와 불확실성으로 승인이 필요한지 정한다.

- 바로잡을 값이 분명한 Bug Fix, 외부 동작이 그대로인 Refactoring, 테스트 추가, 오타·문구처럼 정해진 값의 수정은
  작업 정의를 대화에 몇 줄로 보이고 바로 Execute로 간다. PRD·방향 확인을 꺼내지 않는다.
- 그 밖에는 1단계 질문과 계획을 한 메시지로 보이고 승인을 받는다. 계획에는 바꿀 곳, 테스트 방법, PR 단위를 적는다.
  승인된 계획서가 이미 있으면 그 계획서와 달라진 점·남은 질문만 보인다. 정할 것에 답을 받아도 승인이 아니다. 답을
  계획에 반영해 다시 보이고 착수 승인을 받은 뒤에만 Execute로 간다. 계획서 머리말을 직접 `승인됨`으로 바꾸지 않는다.

승인을 받는 계획에 적용한다.

- 아래 중 하나라도 해당하면 계획서 파일로 쓴다. 나머지는 대화에 5줄 안팎으로 보인다.
  - 고를 선택지가 있다
  - 사용자에게 보이는 동작·문구가 요청과 다르게 바뀌거나, 기능·문구·데이터를 지운다
  - API·저장 형식·설정 키처럼 밖과의 약속을 새로 고르거나 바꾼다
  - 되돌리려면 커밋 되돌리기 한 번으로 끝나지 않는다
- 계획서 파일에는 작업 정의 네 칸, 바꿀 곳과 PR 단위, 검증 수단, 정할 것(배경·선택지·권장안), 실행 중 필요한 승인,
  사용자 손이 드는 준비물, 멈춤 전제, 빈 `변경·결정 로그` 절을 둔다. 머리말은 `상태: 초안`이다. 위치는 프로젝트 지침이
  정한 작업 폴더이고, 팀이 보는 코드 레포 안에는 두지 않는다. 정한 곳이 없으면 한 번 묻고 프로젝트 지침에 적는다.
- Feature·Enhancement로 PRD의 요구가 바뀌면 바꿀 PRD 칸(Requirements·Scope·Success Criteria 등)의 전·후 문장을
  계획에 넣어 함께 승인받는다.
- 사용자에게 보이는 문구를 새로 쓰거나 바꾸면 그 문구 원문을 계획에 적는다.
- 화면 디자인을 정해야 하면 시안 여러 개를 그려 보이고, 고른 것을 승인으로 받는다. 프로젝트 지침이 시안 스킬·도구를
  정했으면 그것을, 없으면 시안 비교(`compare-mockups`)가 맡는다.
- 화면을 바꾸면 [screen-check.md](references/screen-check.md) 1절을 읽고 계획에 `화면 기준` 목록을 출처 경로와 함께
  적는다. 시안 값은 다른 절을 가리키지 않고 이 목록에 직접 적는다. 기준이 없는 자리는 `기준 없음`으로 적는다. 이 표시가
  있으면 자동 머지하지 않는다.
- 화면·문구·사용자에게 보이는 동작이 바뀌는데 승인된 계획서와 시안이 없으면, 계획서 파일과 계획 시각 자료(HTML 한 장)를
  만들어 대화에 렌더해 띄우고 여기서 멈춘다. 계획서는 [screen-plan.template.md](assets/screen-plan.template.md)를, 시각
  자료는 [plan-visual.md](references/plan-visual.md)를 따른다. 시안 없이 승인을 묻지 않고 승인 전에 코드를 바꾸지 않는다.
- 한 PR이 파일 10개나 테스트를 뺀 400줄을 넘을 것 같으면 나누는 안을 함께 보인다. 한 기능을 PR 여러 개로 나누면
  develop에서 기능 브랜치를 만들어 모든 PR의 base로 둔다.
- 바꿀 파일이 10개를 넘거나 되돌리기 비싼 작업(데이터 이전·삭제, 외부 공개·출시)이면 승인 전에 계획 검토
  에이전트(`plan-reviewer`)를 한 번 부른다. 관점은 화면을 바꾸면 디자인, 그 밖은 코드다. 프롬프트에는 계획서 절대경로,
  관점, 사용자 요청 원문, 코드베이스 절대경로와 HEAD, 도구 호출 상한(기본 15회)만 넣는다. 이름으로 부를 수 없는
  하네스에서는 [plan-reviewer.md](../../agents/plan-reviewer.md)의 머리말을 뺀 본문을 서브에이전트 지시로 넘긴다.
  Blocker는 고치고, 사용자가 정할 문제는 정할 것에 올린다.
- push·PR, 강제 push가 필요하면 그 승인, 멈춤 전제(틀리면 멈출 전제)를 이 메시지에서 받는다. 요청문이나 전역·프로젝트
  지침에 이미 있는 승인은 다시 받지 않는다. 사용자가 PR을 직접 보고 머지하겠다고 하면 계획에 적는다.
- 답 때문에 계획이 크게 바뀌면 1단계로 돌아간다.

끝났다고 보는 기준: 완료 조건을 구현 전에 적었고, 승인이 필요한 작업이면 사용자가 승인했다.

## 3. Execute

브랜치·작업 위치는 프로젝트 규칙을 따른다(레포 지침이 main 직접 작업을 정했으면 그대로). 없으면 브랜치명은
`<타입>/<이슈번호>-<요약>`(타입은 `fix`·`feat`·`docs`·`test`·`chore`·`refactor`, 요약은 영문 소문자 kebab-case 3~5단어),
작업 위치는 레포의 워크트리 생성 스크립트가 있으면 그것, 없으면 `git worktree add`(추적 제외 설정 파일은 따로 복사해야
할 수 있다고 보고에 남긴다). 첫 변경 전 `git rev-parse HEAD`를 base로 적어 둔다. 리뷰 범위·범위 검사·커밋 정리·이어받기가
모두 이 base를 기준으로 한다.

유형별로 먼저 쓸 것:

| 유형 | 먼저 | 그다음 |
|---|---|---|
| Feature·Enhancement | 계약·타입과 기대 동작 테스트 | 가장 작은 가치 흐름을 구현 |
| Bug Fix | 결함을 재현하는 테스트(지금 실패하는지 본다) | 원인(공통 함수)에서 수정 |
| Refactoring | 외부 동작을 고정하는 테스트(없으면 더함) | 구조 변경, 테스트 기대값은 그대로 |

작은 동작 단위로 구현 → 그 변경에 맞는 검증 → 커밋을 반복한다. 새 공개 함수는 `coding-philosophy.md` 12장의 네 가지를
스스로 확인한다. 동작이 바뀌는 기존 함수에 `coding-philosophy.md` 1장의 계약 검사(사전·사후 조건)나 그 동작의 테스트가
없으면 그 함수에 한해 더한다. 오타·문구처럼 동작이 그대로인 수정에는 하지 않는다.

끝났다고 보는 기준: 계획의 바꿀 곳을 모두 구현했고, 커밋마다 그 변경의 검증을 실제로 돌렸다.

## 4. Verify

[verification.md](references/verification.md)대로 완료 조건별 증거를 남긴다. 작업 정의·계획서·이슈의 조건을 그대로
쓰고 별도 상태 문서를 만들지 않는다. 범위는 다음으로 검사한다.

```bash
python3 <이 플러그인>/scripts/scope_check.py --base <base> --root <레포> [--allow '<허용 경로 glob>']
```

이어서 아래 순서로 정리·리뷰한다.

1. 재사용·단순화·효율을 정리한다. 정리 도구가 없으면 읽기 전용 서브에이전트에 diff를 주고 같은 관점으로 검토받는다.
2. [code-review-criteria.md](references/code-review-criteria.md)대로 관점별 독립 리뷰어를 한 응답에서 병렬로 띄운다.
   범위는 `git diff <base>...HEAD`, `git diff HEAD`, `git ls-files --others --exclude-standard`를 합친 것이다.
   화면을 바꿨으면 같은 응답에서 screen-check.md 3절의 독립 화면 검토도 띄운다.
3. 이 변경으로 틀리게 된 레포 안 문서(README·지침·`docs/`)를 같은 브랜치에서 고친다. 변경이 외부 콘솔 값·키 발행 같은
   새 운영 절차를 만들면 그 절차도 레포 운영 문서에 추가한다. 레포 밖 문서는 보고에 목록으로 남긴다.
4. 고친 것이 있으면 자동 검사(타입·린트·테스트)와 범위 검사를 다시 돌린다. 화면을 다시 바꿨으면 캡처도 다시 찍는다.
5. 앞 커밋을 고친 커밋을 합친다. 후속 커밋은 처음부터 `git commit --fixup=<대상>`으로 만들고 `GIT_SEQUENCE_EDITOR=true
   git rebase -i --autosquash <base>`로 합친다. 합치기 전 HEAD에 백업 브랜치를 만들고, 합친 뒤 `git diff <백업> HEAD`가
   비었는지와 작성자가 그대로인지 본다. 확인되면 백업 브랜치를 지우고 그 해시를 보고에 적는다. 충돌하면
   `git rebase --abort`하고 합치기를 생략한다. 브랜치가 이미 원격에 있으면 강제 push 승인 없이는 합치지 않는다.

리뷰·수정을 두 번 넘게 반복하게 되면 회차 상한(기본 3회), 고치기로 확정한 지적 목록, 끝 검토 한 번을 이어받기 메모에 적고 그대로 따른다. 상한에 닿으면 멈추고 남은 지적을 사용자에게 보인다.

끝났다고 보는 기준:
- 타입 검사·린트·전체 테스트를 실제로 돌려 통과했다.
- `scope_check.py`가 오류 0이거나, 걸린 항목마다 요청 범위 안이라는 근거를 적었다. 테스트 삭제·skip·기대값 완화로
  통과시키지 않았다.
- 화면을 바꾼 diff면 실제로 띄운 화면 캡처를 계획의 `화면 기준`과 항목마다 대조했다(screen-check.md 2절).
- 새 테스트·가드는 고친 결함을 코드에 되살렸을 때(변형 주입) 실패하는 것을 봤고, 되살린 코드는 원복했다.
- 기대와 다르게 실패한 테스트는 실패 원인을 분류했다. 구현 결함이면 코드를, 기대 결과가 틀렸으면 PRD로 의도를 확인해
  기대 결과를 고쳤다. 요구가 바뀐 것이면 PRD를 먼저 고쳤고, 범위·완료 기준이 바뀌면 승인받았다. 환경이 없으면 통과가
  아니라 "미검증"이다.
- 고친 지적은 검증해 커밋했고, 반영하지 않은 지적은 이유를 남겼다.
- 의도·범위가 잘못 정해진 문제면 Define으로 돌아가 다시 승인받았다.
- 못 한 것은 이유와 함께 "미검증"으로 남겼다.

## 5. Finalize

바뀐 의도의 원본을 고친다.

| 유형 | PRD |
|---|---|
| Feature·Enhancement | 바뀐 칸을 고치고, 동작을 보장하는 코드·테스트 위치를 References에 적는다. 상충하는 옛 요구는 지운다 |
| Bug Fix | 의도가 불명확해서 생긴 결함일 때만 한 줄 보강 |
| Refactoring | 고치지 않음 |

중요한 결정 근거는 PRD Rationale에 적고, 커밋 메시지로 충분하면 따로 적지 않는다. 완료 조건 체크리스트를 테스트로
옮겼으면 PRD에 다시 적지 않는다. PRD·`PRODUCT.md`를 고쳤으면 아래 명령으로 형식을 검사한다.

```bash
python3 <이 플러그인>/scripts/check_d3_docs.py --root <프로젝트>
```

### 제출

push·PR 전에 verification.md의 `verify.py check`로 모든 완료 조건을 확인한다. 실패·미실행·미확인이 남으면 전체 달성으로 보고하지
않는다. 레포의 `.github/workflows/`를 열어 이 PR에 걸리는 CI 검사를 확인하고, 그 명령을 로컬에서 돌려 결과와 함께
보고에 적는다. CI가 있는지는 이 폴더로 판정한다. Define·요청문·지침에 push·PR 승인이 있을 때만 push하고 PR을 만든다.
승인이 없으면 커밋까지 하고 보고로 간다. 커밋·PR 형식은 프로젝트·전역 지침이 정한 것을 따르고, 없으면
[commit-and-pr.md](references/commit-and-pr.md)를 따른다.

PR을 만들었으면 [merge-criteria.md](references/merge-criteria.md)의 조건을 모두 채울 때 머지한다. 하나라도 빠지면 걸린
조건을 적어 사용자에게 머지를 요청하고, 그 PR마다 [pr-review-visual.md](references/pr-review-visual.md)대로 전/후 시각
자료를 만들어 대화에 띄운다.

기능 브랜치를 쓰면 기능 브랜치 안의 PR이 모두 들어온 뒤 기능 브랜치를 빌드해 완료 기준을 기기에서 대조하고, 통과한
뒤 develop PR을 만든다. PR마다 따로 통과한 것으로 완료라고 보고하지 않는다.

### 보고

첫 문장은 이 작업이 푼 문제(누가 무엇을 겪었나)와 그 중요도다. 이어서 Changes(바뀐 동작·핵심 결정), Verification(실제로
돌린 검사와 결과, 못 한 것은 "미검증"을 먼저), Remaining(남은 한계·문제)을 짧게 설명한다. 이슈·PR·브랜치는 번호·이름만
적지 않고 무엇을 하는 것인지 함께 적는다. 반영하지 않은 리뷰 지적은 지적마다 무엇이 문제이고 고치면 무엇이 달라지는지
적는다. 그다음 작업 위치(레포·브랜치) · 커밋 목록 · 고친 PRD 칸 · 문서 영향 · 합의와 달라진 점 · PR URL · 자동 머지한
PR과 머지를 요청한 PR을 적는다. 설명을 생성했다는 이유로 사용자가 이해했다고 기록하지 않는다. PR 본문에는 이 중 푼
문제·바뀐 동작·결정·검증 결과·남은 한계만 싣는다. 성과 조건은 출시 뒤에 본다고 적고, 완료를 성과로 보고하지 않는다.

끝났다고 보는 기준: 승인 범위까지 커밋·push·PR을 마쳤고, PR마다 머지했거나 머지를 요청했고, 보고했다.

## 커밋 규칙

- 매 커밋 전에 그 변경에 맞는 타입 검사·테스트·실행을 실제로 돌린다. 못 돌렸으면 이유와 함께 "미검증"으로 남긴다.
- 매 커밋 직전 `pwd`·`git rev-parse --show-toplevel`·`git branch --show-current`로 작업 위치를 확인한다.
- 작성자는 대상 레포의 git 설정을 그대로 쓴다. `--author`·`GIT_AUTHOR_*`로 덮지 않고, 서브에이전트에 커밋을 맡기면
  이 규칙을 지시에 적는다.
- `--no-verify`로 훅을 우회하지 않는다. 포맷 검사 실패는 레포의 포맷 명령으로 고친다.
- 변경 없는 점검에 빈 커밋을 만들지 않는다.

## 멈추는 곳

Define 승인 뒤(승인이 필요 없는 작업은 처음부터)에는 멈추지 않고, 묻지도 경과를 보고하지도 않는다. 합의에 없던 판단은
목표·범위 안이면 직접 정하고 보고의 "합의와 달라진 점"에 남긴다. 계획서가 있으면 본문은 고치지 않고 `변경·결정 로그`에
한 줄 더한다. PRD의 요구를 바꿔야 하면 구현보다 PRD를 먼저 고친다.

예외는 다음뿐이다. 이때는 깨졌다고 본 관찰을 근거로 보이고 묻는다: 멈춤 전제가 깨졌을 때, 목표를 이룰 수 없을 때,
범위 밖을 건드려야 할 때, 제품 의도를 바꿔야 할 때, PRD·테스트·코드가 충돌하고 근거로 가를 수 없을 때, 필요한
도구·권한이 없을 때.

## 이어받기 메모

세션이 끊겨도 다른 세션이 이어받을 수 있게 메모 하나를 단계를 끝낼 때마다 갱신한다. 담을 것: 레포·브랜치·base·HEAD,
유형, 끝낸 단계와 남은 단계, 막힌 것, 합의와 달라진 점. 머지 판단은 이 메모와 Verify 증거를 근거로 한다.

- 프로젝트나 상시 지침이 세션 기록 문서를 정했으면 그 문서에 쓰고 따로 만들지 않는다.
- 없으면 계획서 옆에 `handoff.md`로 둔다. 팀이 보는 코드 레포 안에는 두지 않는다.
- 계획서 없이 진행한 작은 작업은 메모를 만들지 않고 보고로 대신한다.
- "작업 이어서 해줘"면 이 메모와 `git log <base>..HEAD`로 남은 단계부터 이어간다.
