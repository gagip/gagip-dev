# 기획 문서 세 개 — 공용 규칙

`problem-definition`, `solution-design`, `work-plan`이 함께 따르는 규칙이다. 세 스킬은 문서 하나씩을
맡고, 한 내용은 한 문서에만 적는다. 다른 문서의 내용이 필요하면 옮겨 적지 않고 링크로 가리킨다.

## 세 문서

| 문서 | 스킬 | 답하는 질문 | 담는 것 | 담지 않는 것 |
|---|---|---|---|---|
| 문제 정의 | `problem-definition` | 무엇을 이뤄야 하고, 무엇으로 이뤘다고 판정하나 | 지금 상태, 이룰 상태, 왜, 범위 밖, 목표 트리, 판정 기준(OKR) | 해법(만들 것·방식), 작업, 일정 |
| 설계 | `solution-design` | 어떻게 풀 것인가 | 요구사항 결정과 이유, 제약, 기술 리스크·선행 검증, 미해결 설계 사안 | 문제·목표·판정 기준의 재서술, 작업, 일정, 검증 절차 |
| 플랜 | `work-plan` | 누가 무엇을 어떤 순서로 하고, 어떻게 확인하나 | 작업 범위, 작업 분해(담당·앞 단계), 검증 방법, 일정·기한 판정, 리스크, 코드 리뷰, 브랜치명, 승인 상태 | 규칙·구조의 상세, 문제의 재서술 |

흐름: `problem-definition → (grill) → solution-design → work-plan → implement`. 의도가 흐려 어느 문서의
빈칸이 서지 않으면 `grill`로 먼저 캐낸다.

**경계 둘**
- "범위 밖"(문제 정의)은 **이 목표가 다루지 않는 상태**다. "미루는 작업"(플랜)은 **이번 작업에서 하지 않는
  일**이다. 같은 내용이 양쪽에 있으면 상태면 문제 정의에, 일이면 플랜에 둔다.
- "리스크"는 플랜에만 둔다. 설계에는 설계를 가르는 불확실성(기술 리스크·선행 검증, 미해결 설계 사안)만 둔다.

## 문서끼리 잇는 방법

- 문서 머리말에 앞 문서 위치를 적는다. 설계는 `문제 정의:`, 플랜은 `문제 정의:`와 `설계:`.
- 판정 기준은 `O1.1 KR1`처럼 목표 번호와 KR 번호로 부른다. 설계 결정은 `D1`, `D2`로 번호를 붙인다.
- 설계 결정마다 기여하는 KR을, 플랜 작업마다 대응하는 설계 결정이나 KR을 적는다. 이 연결이 있어야
  문서 간 정합성을 기계로 확인할 수 있다.
- 앞 문서가 없으면 그 스킬부터 제안한다. 사용자가 생략을 고르면 머리말에 `생략 (<이유>)`로 적고,
  그 연결 칸은 `—`로 둔다.

## 저장 위치

스킬은 저장 위치를 정하지 않는다.

1. 프로젝트 지침(`CLAUDE.md`·`AGENTS.md` 등)에 기획 문서 위치가 있으면 그대로 쓴다.
2. 없으면 그 프로젝트에서 세 스킬 중 어느 것이든 처음 쓸 때 한 번 묻는다. 선택지는 프로젝트 문서 폴더,
   Notion 같은 연결된 문서 도구, 사용자가 지정하는 경로다. 받은 위치를 프로젝트 지침에 한 줄로 적어 이후로는
   묻지 않는다.
3. 로컬 파일이면 `YYYY-MM-DD_<주제>_문제정의.md`, `_설계.md`, `_플랜.md`로 이름을 맞춘다.
4. 검사 스크립트는 마크다운 파일을 읽는다. 문서 도구에 저장하는 경우에는 검사할 때만 본문을 임시 마크다운
   파일로 내려받아 돌리고, 그 사본은 남기지 않는다. 예외는 하나다 — `implement`는 로컬 파일만 읽으므로 승인된
   플랜은 사이클 폴더에 내보내 `plan:`에 적는다. 이 사본은 그 사이클의 입력 기록이고 원본은 문서 도구에 있다.

## 검수 — 작성자와 검수자를 나눈다

문서를 쓴 쪽은 자기 산출물을 너그럽게 본다. 그래서 판정은 쓴 쪽이 하지 않는다.

1. **작성**: 스킬이 문서를 쓴다. 사용자가 주지 않은 값은 칸마다 `후보:`를 붙인다.
2. **기계 검사**: 스킬의 `scripts/check_*.py`로 형식·금지 내용·연결을 확인한다. 오류는 고치고 다시 돌린다.
3. **독립 검수**: 이 플러그인의 `plan-reviewer`에 루브릭 모드로 맡긴다. 프롬프트에는 다음만 넣는다.
   - 문서 경로(플랜이면 앞 문서 경로도)
   - 스킬의 `references/review-rubric.md` 절대경로
   - 사용자 요청 원문 — "사용자가 주지 않은 것을 지어냈는가"를 대조하는 데 쓴다
   - 관점이 필요한 스킬이면 관점 이름, 도구 호출 상한(기본 15회)

   문서를 왜 그렇게 썼는지는 넣지 않는다. `plan-reviewer`를 이름으로 부를 수 없는 하네스에서는 이 파일 기준
   `../agents/plan-reviewer.md`를 읽어 머리말을 뺀 본문을 서브에이전트 지시로 넘긴다. 보고의 "읽은 것"에
   넘긴 문서가 없으면 그 보고는 버린다.
4. **반영**: 미통과는 고치고, 사용자가 정할 문제로 걸린 것은 고치지 말고 질문으로 올린다. 고친 뒤 결정이
   바뀌었으면 검수를 한 번 더 돌린다.

독립 검수는 건너뛰지 않는다. 문서가 짧다, 기계 검사가 깨끗하다, 사용자가 곧 볼 것이다는 건너뛸 이유가 아니다.
서브에이전트 도구 자체가 없는 하네스에서만 루브릭을 직접 적용하고, 보고 첫 줄에 "독립 검수 미실행 — <없던 도구>"를
밝힌다.
