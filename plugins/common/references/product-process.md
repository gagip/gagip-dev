# 제품 개발 절차

방향이 흔들려 다시 만드는 일과, 지금 어느 단계인지 모르는 일을 줄이기 위한 공용 기준이다. 작업 크기를 고르고, 시작
조건이 찬 단계로만 넘어간다.

## 목차

1. 적용하는 때
2. 작업 크기
3. 단계
4. 시작 조건
5. 되돌아가는 규칙
6. 정하는 사람
7. 문서

## 1. 적용하는 때

다음 중 하나면 적용한다. 아니면 이 절차를 꺼내지 않고 하던 방식대로 진행한다.

- 프로젝트 지침이 이 절차를 쓴다고 정했거나 방향 문서(`PRODUCT.md`)의 위치를 적었다
- `product/PRODUCT.md`가 있거나, 요청이 가리킨 `SPEC.md` 머리말에 `상태`와 `크기`가 모두 있다
- 사용자가 제품 방향 확인이나 이 절차를 요청했다

프로젝트 지침이 정한 값이 이 파일보다 우선한다. 정하지 않은 값은 아래를 쓴다.

| 값 | 정하지 않았을 때 |
|---|---|
| 정하는 사람 | 사용자 |
| 방향 문서 | `product/PRODUCT.md` |
| 기능 명세 | `product/features/<기능>/SPEC.md` |
| 시안 도구·스킬 | `compare-mockups`. 프로젝트의 시안 스킬을 쓸 때도 이 파일의 시작 조건과 세 번 제한, 결정 기록은 지킨다 |
| 출시 절차 | 이 절차는 다루지 않는다 |

`SPEC.md`가 있는 작업을 새 세션에서 이어받으면 `상태`부터 읽고 그 단계에서 이어간다. `보류`면 이유가 풀렸는지 먼저
보고, 풀렸으면 탐색부터 이어간다. `닫힘`이면 고치지 않고 새 `SPEC.md`에서 이전 명세로 링크한다.

## 2. 작업 크기

| 크기 | 판정 | 거칠 단계 |
|---|---|---|
| 수정 | 이미 적힌 동작이나 명백히 의도된 동작으로 바로잡는다 | 개발 |
| 변경 | 기존 기능의 흐름·동작·범위가 달라진다 | 방향 확인 → 필요하면 시안 → 개발 |
| 신규 | 새 기능이거나 여러 화면이 함께 달라진다 | 방향 확인 → 탐색 → 시안 → 개발 → 결과 확인 |

수정에는 `SPEC.md`를 만들지 않는다. 오타·깨진 동작·리뷰 지적처럼 바로잡을 값이 분명하면 수정이다. 의도된 동작을
정해야 하면 변경이다. 변경과 신규 사이가 모호하면 신규로 본다. 하다가 범위가 커지면 크기를 다시 고른다.

## 3. 단계

| 단계 | 하는 일 | `SPEC.md`에 남기는 것 | 쓰는 스킬 |
|---|---|---|---|
| 방향 확인 | `PRODUCT.md`와 대조해 진행·보류·방향 변경 중 하나로 가른다 | 방향. 보류면 이유(방향에 안 맞음 또는 근거 부족) | `grill` |
| 탐색 | 문제와 근거를 적고 가장 위험한 가정을 싼 방법으로 확인한다 | 문제·근거·가정 | `grill`, 명세를 문서로 달라면 `work-plan` |
| 시안 | 안을 비교해 하나를 고른다. 화면이 안 바뀌면 건너뛴다 | 시안 경로와 고른 이유 | 정해진 시안 스킬 |
| 개발 | 구현하고 명세대로 되는지 확인한다 | 검증 결과 | `dev` |
| 결과 확인 | 신규에서 `SPEC.md`에 적은 날에 적은 값을 본다 | 유지·개선·제거·판단 유보 중 하나와 근거 | `grill` |

`상태`는 그 단계를 맡은 스킬이 사용자가 정한 직후 바꾼다.

| 정해진 것 | 바꿀 `상태` |
|---|---|
| 방향이 맞아 신규를 진행 | 탐색 |
| 방향이 맞아 변경을 진행, 시작 조건이 참 | 화면이 갈리면 시안, 아니면 개발 시작 승인 뒤 개발 |
| 방향에 안 맞거나 근거가 모자람, 방향 변경을 기다림 | 보류 |
| 시안 시작 조건이 참 | 시안 |
| 세 번 안에 못 고름, 핵심 가정이 깨짐 | 탐색 |
| 개발 시작을 승인 | 개발 |
| 구현 검증이 끝남 | 신규는 결과 확인(다시 볼 날짜를 채움), 변경은 닫힘 |
| 결과를 유지·제거로 정함 | 닫힘 |
| 결과를 개선으로 정함 | 닫힘. 고칠 것은 새 `SPEC.md` |
| 결과를 판단 유보로 정함 | 결과 확인 그대로, 필요한 자료와 다음 날짜를 고침. 더 보지 않기로 하면 닫힘 |

다시 볼 날짜에 알려 주는 장치는 없다. 프로젝트가 쓰는 할 일 목록(이슈 등)에 날짜와 `SPEC.md` 경로를 남기자고 제안한다.

`PRODUCT.md`가 없으면 방향을 지어내지 않고 「방향 문서 없음」을 밝힌 뒤 누구의 어떤 문제인지만 사용자에게 묻는다.

## 4. 시작 조건

시안 시작 조건:

1. 대상 사용자와 문제
2. 근거. 없으면 「가설」로 표시하고 4번의 위험한 가정 후보에 넣는다
3. 화면이 답할 질문 하나
4. 가장 위험한 가정과 확인 방법. 코드를 짜지 않고 있는 자료로 확인할 수 있으면 결과까지 적고, 아니면 미루는 이유를 적는다

조건이 덜 차도 탐색용 시안은 그릴 수 있다. 탐색용 시안은 확정안으로 고르지 않는다.

개발 시작 조건:

1. 고른 시안. 화면이 안 바뀌면 「해당 없음」
2. 범위, 이번에 뺄 것, 예외 상태
3. 검증 방법. 신규는 사용자가 쓰기 시작한 뒤 볼 값 하나, 유지로 볼 기준, 다시 볼 날짜(또는 쓰기 시작한 날에서 며칠 뒤)도 적는다.
   기준을 모르면 「기준값을 잰 뒤 정함」이라고 적는다

변경은 시안 시작 조건과 개발 시작 조건 가운데 이번에 달라지는 칸만 적고 나머지는 이전 명세나 기준 문서를 링크한다.
개발 시작 승인은 구현 계획 승인과 한 번에 받고, 승인한 날과 사용자 말을 결정 이력에 적는다. 조건이 찼는지는 에이전트가 적고 사용자가 정한다. 빈칸을 추측으로 채워
통과시키지 않는다.

## 5. 되돌아가는 규칙

- 한 번에 나란히 낸 안들을 시안 한 번으로 세고 탐색용도 센다. 같은 질문을 세 번 안에 고르지 못하면 네 번째를 그리지
  않고 탐색으로 돌아가 질문을 다시 본다. 고른 안을 다듬는 시안은 세지 않는다. 사용자가
  알고도 한 번 더 그리자고 하면 그리고 결정 이력에 적는다.
- 개발 중 명세가 바뀌면 `SPEC.md`를 먼저 고치고 구현한다. 목표·범위를 넓히거나 완료 기준을 바꾸면 고치기 전에 승인받는다.
- 구현 중 핵심 가정이 깨지면 탐색으로 돌아간다.
- 확인해도 가정이 가려지지 않으면 보류하거나, 어느 쪽이 맞아도 쓸모 있는 가장 작은 범위만 진행한다. 사용자가 고른다.
- `PRODUCT.md`에서 아직 합의하지 않은 항목에 달린 기능은 그 항목을 먼저 정한다. 정하지 않고 진행하려면 사용자 승인과
  되돌릴 범위를 `SPEC.md`에 적는다.
- 결과를 볼 자료가 부족하면 「판단 유보」와 필요한 자료를 적는다.

## 6. 정하는 사람

방향(대상 사용자, 핵심 문제, 가치, 원칙, 비목표)과 작업 크기, 방향 확인 결과, 범위, 시안, 개발 시작, 결과는 정하는
사람이 정한다. 에이전트는 조사하고 안을 낸다. 새 지시가 오면 방향 변경인지 기능 요청인지 먼저 가른다. 방향 변경이면
정하는 사람과 합의해 `PRODUCT.md`를 고친 뒤(`write-docs`의 제품 방향 문서) 영향받는 명세를 고친다. 답을 기다리는 동안 그 답에 달린 시안·개발은 시작하지 않는다.

## 7. 문서

- `PRODUCT.md`: 제품마다 한 편. 목적, 대상 사용자와 문제, 핵심 가치, 지금 집중할 문제, 원칙, 비목표, 성공 기준, 아직
  합의하지 않은 것을 담는다.
- `SPEC.md`: 변경·신규마다 한 편. 진행 중 결정은 여기서만 고치고 계획서·이슈·PR은 이 파일을 링크한다. 아래 질문에 답하면
  되고 절 구성은 작업에 맞춘다. 머리말의 `상태`와 `크기`만 이름을 고정한다.

```markdown
상태: 탐색 / 시안 / 개발 / 결과 확인 / 닫힘 / 보류
크기: 변경 / 신규
```

| 답할 질문 | 채우는 때 |
|---|---|
| 방향의 어느 항목에 맞나, 이전 명세는 무엇인가 | 방향 확인 |
| 누구의 어떤 문제이고 근거는 무엇인가 | 탐색 |
| 가장 위험한 가정은 무엇이고 어떻게 확인했나 | 탐색 |
| 화면이 답할 질문은 무엇인가 | 시안 전 |
| 어떤 해결책을 왜 골랐고 버린 안은 무엇인가 | 시안 뒤 |
| 어디까지 하고, 무엇을 빼고, 예외는 어떻게 되나 | 개발 전 |
| 무엇으로 확인하고 결과는 어땠나 | 개발 전, 결과 확인 |
| 언제 누가 무엇을 왜 바꿨나 | 바뀔 때 |
