# common

언어·플랫폼에 독립적인 개발 워크플로 도구다.

## 스킬

| 스킬 | 설명 | 트리거 예시 |
|---|---|---|
| `agent-env-diagnosis` | Claude Code·Codex 세션 기록으로 스킬·지침·메모리·훅이 얼마나 쓰이고 어디서 실수가 나는지 재고(빠른 측정 → 진단), 고칠 곳을 골라 반영 절차로 넘김 | "스킬 사용 지표 보여줘", "실수 분석해줘", "개선할 곳 골라줘" |
| `build-mcp-server` | 외부 서비스를 범용 API 통로 없이 목적별 도구만 노출하는 작은 MCP 서버로 감쌈 | "MCP 서버 만들어줘", "이 API를 MCP로 감싸줘" |
| `build-skill` | 새 스킬을 만들거나 기존 스킬을 반복 개선. 결정론적 Python 러너로 테스트 | "스킬 만들어줘" |
| `critique-research` | 조사·분석 문서를 맥락 없는 별도 컨텍스트 여럿에 넘겨 독립 검증 | "이 문서 검증해줘", "독립 검증 세워줘" |
| `dev` | 개발 요청을 맥락 수집·요구사항 명확화 → 계획 승인 → 구현 → 테스트 → 정리·리뷰 → PR·자동 머지 판단 → 보고·회고까지 한 흐름으로 진행. 사용자는 계획 승인과 보고에서만 관여 | "~고쳐줘", "이슈 구현해줘", "/dev" |
| `grill` | 요구사항이 애매한 작업 요청에서 착수 전 인터뷰로 요구사항·설계 방향을 캐냄 | "grill me", "인터뷰해줘" |
| `html-brief` | 근거 기반 의사결정·보고 문서를 단일 HTML로 작성 | "대표 전달용 HTML 만들어줘", "조사 결과를 HTML 보고서로 정리해줘" |
| `module-review` | 모듈 공개 계약과 구조를 순차 점검해 메모로 축적 | "모듈 리뷰해줘" |
| `notion-write` | 구조화된 문서를 Notion에 작성 | "노션에 정리해줘" |
| `report-issue` | 자연어 설명으로 GitHub 이슈 초안 작성·생성 | "이슈 올려줘" |
| `retrospective` | 현재 대화 또는 기간을 회고해 스킬·지침·에이전트 개선안 도출 | "이번 작업 회고해줘" |
| `rubber-duck` | 답을 주지 않고 질문 하나씩으로 사용자가 스스로 막힌 곳을 깨닫게 하는 오리 모드 | "오리 모드", "/duck", "설명하다 보면 풀릴 것 같아" |
| `search-sessions` | 여러 하네스의 세션 로그를 한 번에 뒤져 과거 대화 찾기 | "예전에 이거 얘기했었나" |
| `work-plan` | 착수 전 계획서 한 장(목표·완료 기준, 지금 사실, 할 일, 확인 방법, 착수 전 합의)을 쓰고 승인받음. 개발·기획·연구에 쓰고 종류마다 할 일·확인 방법 칸만 바꿈 | "플랜 짜줘", "계획서 써줘", "조사 설계해줘" |

스킬은 현재 하네스에 구조화 질문·스킬 호출·워크플로 도구가 없으면 문서화된 폴백으로 진행한다.

## 에이전트

| 에이전트 | 하는 일 |
|---|---|
| `ai-tone-auditor` | 문서형 산출물이 "AI가 쓴 티"가 나는지 진단하고 실무 문서 톤 수정안을 제시한다. 읽기 전용이라 문서를 직접 고치지 않는다 |
| `plan-reviewer` | 계획서를 실행 전에 기획·코드·디자인 중 지정받은 관점에서 회의적으로 검토한다. `work-plan`이 검수 조건(바꿀 파일 10개 초과, 되돌리기 비싼 작업, 연구 판정선)에 해당할 때 호출한다 |
| `retro-verifier` | 회고가 뽑은 지침·스킬 업데이트 후보를 사용자에게 보이기 전에 거른다(이미 있음·자리·반복·행동 변화·형태). `retrospective`가 한 번 호출한다 |
