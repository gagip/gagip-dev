# common

언어·플랫폼에 독립적인 개발 워크플로 도구다.

## 스킬

| 스킬 | 설명 | 트리거 예시 |
|---|---|---|
| `agent-env-designer` | 특정 문제를 잘 푸는 에이전트를 위한 환경을 E={Tasks, Harness, Verifier, State, Configuration} 프레임워크로 설계 | "에이전트 환경 설계해줘", "이 문제 풀 에이전트 어떻게 구축하지" |
| `build-mcp-server` | 외부 서비스를 범용 API 통로 없이 목적별 도구만 노출하는 작은 MCP 서버로 감쌈 | "MCP 서버 만들어줘", "이 API를 MCP로 감싸줘" |
| `build-skill` | 새 스킬을 만들거나 기존 스킬을 반복 개선. 결정론적 Python 러너로 테스트 | "스킬 만들어줘" |
| `critique-research` | 조사·분석 문서를 맥락 없는 별도 컨텍스트 여럿에 넘겨 독립 검증 | "이 문서 검증해줘", "독립 검증 세워줘" |
| `grill` | 새로 만드는 요청에서 인터뷰로 요구사항·설계 방향을 캐냄 | "grill me", "인터뷰해줘" |
| `implement` | 계획서(또는 작은 작업 판정)를 받아 구현·정리·리뷰·문서·제출·종결을 단계 관문으로 멈춤 없이 진행 | "이 계획서대로 구현해줘", "이슈 구현해줘" |
| `html-brief` | 근거 기반 의사결정·보고 문서를 단일 HTML로 작성 | "대표 전달용 HTML 만들어줘", "조사 결과를 HTML 보고서로 정리해줘" |
| `mockup-review` | 기획서 기준 디자인 시안 3개 이상을 변형 생성하고 분리된 세션에서 비평 | "시안 만들어줘", "디자인 후보 비교해줘" |
| `notion-write` | 구조화된 문서를 Notion에 작성 | "노션에 정리해줘" |
| `problem-definition` | 기획 문서 세 개 중 문제 정의를 씀 — 지금·이룰 상태, 왜, 범위 밖, 세부 목표, OKR 판정 기준. 해법·작업·일정은 쓰지 않음 | "문제 정의부터 하자", "OKR 세워줘", "이 목표 어떻게 쪼개지" |
| `retrospective` | 현재 대화 또는 기간을 회고해 스킬·지침·에이전트 개선안 도출 | "이번 작업 회고해줘" |
| `rubber-duck` | 답을 주지 않고 질문 하나씩으로 사용자가 스스로 막힌 곳을 깨닫게 하는 오리 모드 | "오리 모드", "/duck", "설명하다 보면 풀릴 것 같아" |
| `screen-brief` | 화면·기능 단위로 타겟·문제·목적을 질문으로 끌어내 누적형 기획서 작성 | "기획서 작성해줘", "이 화면 기획 정리하자" |
| `screen-evidence` | 콘솔 화면을 외부 제출용 증빙으로 캡처하고 검수 에이전트로 검증 | "증빙 캡처해줘", "제출용 화면 캡처" |
| `search-sessions` | 여러 하네스의 세션 로그를 한 번에 뒤져 과거 대화 찾기 | "예전에 이거 얘기했었나" |
| `skill-metrics` | Claude Code의 스킬 호출 로그로 사용 지표 산출 | "스킬 사용 지표 보여줘" |
| `solution-design` | 기획 문서 세 개 중 설계를 씀 — 요구사항 `결정 \| 이유 \| KR` 표, 제약, 기술 리스크·선행 검증. 문제는 문제 정의를 가리키고 작업·일정은 쓰지 않음 | "설계해줘", "이슈 #N 설계", "어떻게 풀지 정하자" |
| `work-plan` | 기획 문서 세 개 중 플랜을 씀 — 작업 범위·미루는 작업, 담당·앞 단계·대응 결정이 붙은 작업, KR별 검증, 기한 판정, 리스크, 코드 리뷰, 브랜치. 세 문서 정합성을 검수하고 승인받아 implement로 넘김 | "플랜 짜줘", "작업 나눠줘", "기한 안에 되나" |

`skill-metrics`는 스킬 호출을 별도 `Skill` 도구 이벤트로 남기는 Claude Code 전용이다. 나머지
스킬은 현재 하네스에 구조화 질문·스킬 호출·워크플로 도구가 없으면 문서화된 폴백으로 진행한다.

## 에이전트

| 에이전트 | 하는 일 |
|---|---|
| `ai-tone-auditor` | 문서형 산출물이 "AI가 쓴 티"가 나는지 진단하고 실무 문서 톤 수정안을 제시한다. 읽기 전용이라 문서를 직접 고치지 않는다 |
| `plan-reviewer` | 계획서를 실행 전에 기획·코드·디자인 중 지정받은 관점에서 회의적으로 검토한다. `problem-definition`·`solution-design`·`work-plan`이 루브릭 모드로 문서를 검수할 때 호출한다 |
| `retro-verifier` | 회고가 뽑은 지침·스킬 업데이트 후보를 사용자에게 보이기 전에 거른다(이미 있음·자리·반복·행동 변화·형태). `retrospective`가 한 번 호출한다 |
