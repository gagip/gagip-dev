- cases.json 칸

- 반대 사례

## cases.json 칸

사례 하나가 객체 하나다. `verify_quotes.py`는 `id`·`source`·`quotes`·`evidence`만 읽고, 나머지 칸은 조사마다 더한다.

```json
{
  "id": "C01",
  "source": "captures/C01.txt",
  "url": "https://...",
  "date": "2026-05-12",
  "platform": "네이버 카페",
  "evidence": "스크린샷 판독",
  "questions": ["Q1"],
  "kind": "행동",
  "quotes": ["해지 버튼을 찾다가 결국 고객센터에 전화"],
  "coding": {"Q1": "전화로 해지"},
  "changed": "서브에이전트 '앱에서 해지' → 원문 보고 '전화로 해지'로 바꿈"
}
```

- `source`는 `cases.json` 기준 상대 경로나 URL이다. 인용은 이 파일에서 찾는다.
- `quotes`는 결론에 쓸 원문 조각만 넣는다. 길게 넣으면 판독 오기 하나로 대조가 깨진다. 40자 안팎이 적당하다.
- 댓글 사례는 본글과 다른 `id`(예: `C05-c1`)로 둔다. 본글과 댓글은 다른 사람이다.

## 증거 수준

| `evidence` | 뜻 | 결론에서 |
|---|---|---|
| `원문 저장` | 본문 HTML·글자를 받아 저장했다 | 인용 가능 |
| `스크린샷 판독` | 캡처를 사람이나 서브에이전트가 옮겨 적었다 | 인용 가능하되 "스크린샷 판독" 수준임을 밝힌다 |
| `직접 대조` | 판독본을 캡처 이미지와 나란히 놓고 글자를 맞춰 봤다 | 인용 가능 |

판독 숫자(사례 수, 캡처 장수)도 판독 오기가 난다. 장수는 파일 수를 세어 적는다.

## 행동·불편·추론 구분

`kind`는 셋 중 하나다.

- `행동`: 실제로 한 일이 원문에 있다(돈을 냈다, 해지했다, 다른 제품으로 바꿨다).
- `불편`: 하지는 않았지만 불편·바람을 직접 말했다("~했으면 좋겠다", "~가 답답하다").
- `추론`: 원문에는 없고 조사자가 읽어 낸 것. 결론의 근거 건수에 섞지 않고 가설로 따로 둔다.

희망·계획("다음 달에 다시 해 볼 생각")은 `불편`이지 `행동`이 아니다.

## 반대 사례

질문마다 결론을 약하게 만드는 사례(이미 다른 수단으로 해결했다, 필요 없다고 말했다, 정해진 절차대로 했다)를 같은 칸으로 코딩한다.
`coding` 값에 반대임을 드러내고, 결론에 찾는 쪽과 반대쪽 건수를 나란히 둔다.

## 제품 사실표

경쟁 제품·대체 수단·가격은 사례가 아니라 사실이다. `raw/facts.json`에 따로 두고 사례 건수에 넣지 않는다.

| 칸 | 내용 |
|---|---|
| `id` | F01 … |
| `product` | 제품·서비스 이름 |
| `claim` | 확인한 사실 한 줄(기능, 가격, 대상) |
| `value` | 숫자면 숫자와 단위(예: `15250 KRW`) |
| `source` | 저장한 원문 경로 또는 URL |
| `checked` | 확인한 날짜 |
| `quotes` | 근거 원문 조각 |

`quotes`를 두면 같은 `verify_quotes.py`로 대조한다. 공식 페이지에 없는 값(기사·블로그에서 본 가격)은 `claim`에 출처 종류를 적는다.

## 서브에이전트 코딩 재확인

선별·판독·코딩을 서브에이전트에 맡겼으면 결론에 쓰는 칸은 원문을 다시 보고 확인한다. 특히 "누가 정했나"(본인·전문가·회사),
"돈을 냈나", "실제로 했나"처럼 결론의 방향을 바꾸는 칸이 자주 틀린다. 바꾼 칸은 `changed`에 남기고 결론에 바꾼 수를 적는다.

## 0건과 범위

어떤 질문의 사례가 0건이면 결론 문장에 검색어 수, 출처, 기간, 접근 단계를 함께 쓴다.
예: "검색어 12개·네이버 카페·회원 전용 13건 제외 범위에서 0건". 이 범위 밖(인터뷰, 사용 기록)으로만 답할 수 있는 질문이면 그렇게 적는다.
