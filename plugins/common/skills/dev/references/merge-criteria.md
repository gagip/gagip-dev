# 자동 머지 기준

아래를 모두 채우면 에이전트가 머지한다. 하나라도 빠지면 머지하지 않고, 걸린 조건을 적어 사용자에게 머지를 요청한다.

## 레포와 대상 브랜치

머지해도 되는 곳은 둘뿐이다. 그 밖의 레포는 모두 사용자에게 요청한다.

- 사용자 개인 계정이 소유한 레포(`gh repo view --json owner`의 소유자가 `gh api user -q .login`과 같다)의 기본 브랜치와 기능 브랜치
- 프로젝트 지침에 "자동 머지 허용"으로 적힌 레포·브랜치

`release/*`와 태그는 어느 레포든 제외한다.

## 조건

| 묶음 | 조건 | 확인 방법 |
|---|---|---|
| 상태 | CI가 모두 통과했고 충돌이 없다. CI가 도는 중이면 사용자에게 묻지 않고 끝날 때까지 기다린다. 레포가 GitHub 자동 머지를 막아 두었어도 같다 | `gh pr checks <번호> --watch`, `gh pr view --json mergeable,mergeStateStatus` |
| 상태 | base보다 뒤처졌으면 강제 push 없이 따라잡았고, 그 뒤 CI가 다시 통과했다. 강제 push가 필요하면 요청한다 | `gh pr update-branch` |
| 상태 | 레포 룰셋이 요구하는 승인·검사를 모두 채웠다. 룰셋을 우회하지 않는다 | `gh api repos/{owner}/{repo}/rules/branches/{base}` |
| 검증 | 완료 조건마다 증거가 있다. 기기·플랫폼을 못 써서 남은 미검증은 시뮬레이터·에뮬레이터·빌드 서버 같은 대체 수단까지 시도한 뒤에도 남은 것이고, 그 부분이 실패해도 크래시·데이터 손상·보안·결제 오류가 나지 않는다. 남은 미검증은 PR 본문과 보고에 적는다 | `verification.md`의 `check` |
| 검증 | 화면을 바꿨으면 화면 기준 대조와 독립 화면 검토에 어긋남이 0건이고, 계획의 `화면 기준`에 `기준 없음` 자리가 없다 | `screen-check.md` 2·3절 결과 |
| 검증 | 독립 리뷰의 높음·중간 지적이 남지 않았다. 반영하지 않은 낮음 지적은 보고에 적는다 | 5단계 리뷰 결과 |
| 범위 | 결과가 2단계에서 승인한 계획과 같다. 합의와 달라진 점이 동작에 영향을 주지 않는다 | 이어받기 메모·작업 목록 |
| 범위 | 사용자가 직접 보고 머지하겠다고 한 PR이 아니다 | 2단계 계획 |
| 위험 | API·저장 형식·DB 스키마, 데이터 이관, 인증·결제·개인정보, 의존성 추가·버전 변경, 빌드·배포·CI 설정, 기능·데이터 삭제를 건드리지 않는다 | diff 경로와 내용 |
| 위험 | 사용자에게 보이는 문구를 새로 쓰거나 바꿨다면, 그 원문이 2단계 계획에 그대로 적혀 승인받았다 | 계획과 diff의 문자열 대조 |

## 머지 뒤

- 머지 방식은 레포 관례(squash 등)를 따른다. CI가 통과한 head로만 머지한다(`gh pr merge --match-head-commit <해시>`).
- `git fetch origin` 뒤 base에 변경이 파일 내용으로 들어갔는지 확인한다.
- 그 브랜치를 쓰던 워크트리를 `git worktree remove`로 지운 뒤 원격·로컬 브랜치를 지우고, 지운 해시를 보고에 남긴다.
- 보고에 자동 머지한 PR 목록을 따로 적는다.
