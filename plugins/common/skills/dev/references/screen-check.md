# 화면 판정

화면을 바꾸는 작업에서 "맞게 됐다"를 무엇으로 판정할지 구현 전에 정하고, 구현 뒤 그 기준으로만 판정한다.
기준 없이 캡처를 보면 만든 사람의 눈에 맞춰 통과시키게 된다.

## 1. 기준 찾기 (2단계)

아래에서 이 화면에 해당하는 것을 찾아 계획에 `화면 기준` 목록으로 적는다. 항목마다 출처 경로를 붙인다.

- 승인된 시안. 소스(HTML·JSX·CSS)가 있으면 간격·크기·색·문구 값을 소스에서 읽어 적는다. 이미지뿐이면 이미지 경로를 적는다.
- 프로젝트 디자인 규칙(`DESIGN.md`, 디자인 가이드, 토큰 정의).
- 사용자가 이 작업에서 정한 의도·결정(계획서, 시안 결정 기록).
- 상태별 모습: 빈 상태·실패·긴 글자·큰 글자 크기·좁은 폭·어두운 테마 중 이 화면에 생기는 것.

기준이 없는 자리(시안에 없는 화면 등)는 `기준 없음`으로 적는다. 그 자리가 있는 PR은 자동 머지하지 않고 캡처와 함께 사용자에게 머지를 요청한다.

## 2. 캡처와 대조 (4단계)

- 실제 렌더로 찍는다. 순서: 기기·에뮬레이터 → 대상 컴포넌트만 임시 페이지에 띄운 프리뷰(커밋하지 않음) →
  소스 분석. 앞 수단이 실패하거나 응답이 없을 때만 다음으로 내려간다. 기기가 아니면 무엇으로 찍었는지, 소스 분석이면
  "렌더 미확인"을 보고에 밝힌다.
- 기기를 몰 때: 좌표는 기기 해상도를 잰 뒤 환산한다. 잘못 눌러 확인 창이 뜨면 그 안의 단추 대신 뒤로가기로 닫는다.
  로그인·비밀번호는 대신 넣지 않고 사용자에게 맡긴다. 다른 작업이 같은 기기를 쓰는 중이면 설치하지 않고 프리뷰로 확인한다.
- 기준 항목마다 같은 단위의 값으로 대조한다(`시안 8px / 구현 4px`). 클래스 이름으로 px를 짐작하지 않고 실제 계산값을 본다.
  1배로 판단이 안 되는 차이는 그 영역을 확대해 본다. 시안이 이미지뿐이라 눈으로 잰 값이면 그렇다고 적는다.
- 어긋나면 고치고 다시 찍는다. 코드로 맞출 수 없는 차이만 이유와 함께 남긴다.
- 전/후 캡처는 같은 데이터·같은 폭으로 찍어 프로젝트 QA 캡처 폴더에 둔다.

## 3. 독립 화면 검토 (5단계)

맥락을 모르는 읽기 전용 서브에이전트 하나에 캡처 경로와 1절 `화면 기준` 목록만 넘긴다. 왜 이렇게 만들었는지는 넘기지 않는다.
지시: 기준 항목마다 통과·어긋남을 캡처 근거로 판정하고, 기준에 없더라도 사용자가 이 화면에서 겪을 실패(빈 값·극단값·잘림·
겹침)를 2개 이상 찾는다. 칭찬으로 끝내지 않는다. 확인할 수 없는 것은 "확인 필요"로 적는다.

기준 어긋남은 🔴, 기준 밖 지적은 🟡로 다룬다(code-review-criteria.md 4절과 같다).
