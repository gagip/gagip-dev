# 개발

개발 요청 하나를 끝까지 진행한다. 사용자는 2단계 승인과 7단계 보고에서만 관여한다. 아래 단계를 작업 목록에 올리고
하나씩 끝낸다. 단계마다 "끝났다고 보는 기준"을 채우기 전에는 다음 단계로 넘어가지 않는다. 어떤 도구·스킬로 채울지는
그 자리에서 고른다. 진행은 작업 목록과 커밋으로 보이고, 단계마다 기록 파일을 만들지 않는다. 구현 방법은 대상 레포의
`CLAUDE.md`/`AGENTS.md`를 따르고, 레포 관례가 다루지 않는 코드 판단(계약·실패 표현·공개 범위·시그니처·함수 분리)은
`../../references/coding-philosophy.md`를 따른다.

## 1. 맥락 수집·요구사항 명확화

요청을 실제 코드와 대조한다. 주석·변수명이 아니라 실제 문자열·값·동작을 본다. 승인된 계획서(머리말 `상태: 승인됨`)가
있으면 그것이 기준이다. 이슈는 대상 레포 안에서 `gh issue view <번호> --json title,body,labels,number`로 읽는다. 같은
작업의 브랜치·워크트리가 있는지 `git worktree list`·`git branch --list`로 보고, 있으면 이어간다.

끝났다고 보는 기준:
- 프로젝트 지침, 이슈·계획서, 바꿀 코드가 닿는 흐름을 끝까지 읽었다.
- 이미 해결됐거나, 없는 파일·심볼을 전제하거나, 준비물이 없으면 근거를 모았다. 2단계에서 보이고 진행 여부를 묻는다.
- 요청을 둘 이상으로 읽을 수 있거나 결과물이 달라지는 애매한 점을 질문으로 정리했다. 질문마다 맥락과 권장안을 붙였다.

## 2. 계획 → 승인

1단계 질문과 계획을 한 메시지로 보이고 승인을 받는다. 계획에는 바꿀 곳, 테스트 방법, PR 단위를 적는다. 승인된
계획서가 이미 있으면 그 계획서와 달라진 점·남은 질문만 보인다.

- 아래 중 하나라도 해당하면 계획서 파일로 쓴다. 나머지는 대화에 5줄 안팎으로 보인다.
  - 고를 선택지가 있다
  - 사용자에게 보이는 동작·문구가 요청과 다르게 바뀌거나, 기능·문구·데이터를 지운다
  - API·저장 형식·설정 키처럼 밖과의 약속을 새로 고르거나 바꾼다
  - 되돌리려면 커밋 되돌리기 한 번으로 끝나지 않는다
- 사용자에게 보이는 문구를 새로 쓰거나 바꾸면 그 문구 원문을 계획에 적는다.
- 화면 디자인을 정해야 하면 시안 여러 개를 그려 보이고, 고른 것을 승인으로 받는다.
- 한 PR이 파일 10개나 테스트를 뺀 400줄을 넘을 것 같으면 나누는 안을 함께 보인다. 한 기능을 PR 여러 개로 나누면
  develop에서 기능 브랜치를 만들어 모든 PR의 base로 둔다.
- push·PR, 강제 push가 필요하면 그 승인, 멈춤 전제(틀리면 멈출 전제)를 이 메시지에서 받는다. 요청문이나 전역·프로젝트
  지침에 이미 있는 승인은 다시 받지 않는다. 사용자가 PR을 직접 보고 머지하겠다고 하면 계획에 적는다.
- 답 때문에 계획이 크게 바뀌면 1단계로 돌아간다.

끝났다고 보는 기준: 사용자가 승인했다.

## 3. 구현

브랜치·작업 위치는 프로젝트 규칙을 따른다(레포 지침이 main 직접 작업을 정했으면 그대로). 없으면 브랜치명은
`<타입>/<이슈번호>-<요약>`(타입은 `fix`·`feat`·`docs`·`test`·`chore`·`refactor`, 요약은 영문 소문자 kebab-case 3~5단어),
작업 위치는 레포의 워크트리 생성 스크립트가 있으면 그것, 없으면 `git worktree add`(추적 제외 설정 파일은 따로 복사해야
할 수 있다고 보고에 남긴다). 첫 변경 전 `git rev-parse HEAD`를 base로 적어 둔다. 리뷰 범위·커밋 정리·이어받기가 모두
이 base를 기준으로 한다.

작은 동작 단위로 구현 → 그 변경에 맞는 검증 → 커밋을 반복한다. 새 공개 함수는 `coding-philosophy.md` 12장의 네
가지를 스스로 확인한다.

끝났다고 보는 기준: 계획의 바꿀 곳을 모두 구현했고, 커밋마다 그 변경의 검증을 실제로 돌렸다.

## 4. 테스트

[verification.md](references/verification.md)대로 완료 조건별 증거를 남긴다. 계획서·이슈의 조건을 그대로 쓰고 별도
상태 문서를 만들지 않는다.

끝났다고 보는 기준:
- 타입 검사·린트·전체 테스트를 실제로 돌려 통과했다.
- 화면을 바꾼 diff면 실제로 띄운 화면 캡처가 있다. 시안이 있으면 나란히 비교했다. 캡처는 프로젝트 QA 캡처 폴더에 둔다.
- 새 테스트·가드는 고친 결함을 코드에 되살렸을 때 실패하는 것을 봤고, 되살린 코드는 원복했다.
- 못 한 것은 이유와 함께 "미검증"으로 남겼다.

## 5. 정리·리뷰

아래 순서로 한다.

1. 재사용·단순화·효율을 정리한다. 정리 도구가 없으면 읽기 전용 서브에이전트에 diff를 주고 같은 관점으로 검토받는다.
2. [code-review-criteria.md](references/code-review-criteria.md)대로 관점별 독립 리뷰어를 한 응답에서 병렬로 띄운다.
   범위는 `git diff <base>...HEAD`, `git diff HEAD`, `git ls-files --others --exclude-standard`를 합친 것이다.
3. 이 변경으로 틀리게 된 레포 안 문서(README·지침·`docs/`)를 같은 브랜치에서 고친다. 레포 밖 문서는 보고에 목록으로 남긴다.
4. 고친 것이 있으면 4단계 자동 검사(타입·린트·테스트)를 다시 돌린다. 화면을 다시 바꿨으면 캡처도 다시 찍는다.
5. 앞 커밋을 고친 커밋을 합친다. 후속 커밋은 처음부터 `git commit --fixup=<대상>`으로 만들고 `GIT_SEQUENCE_EDITOR=true
   git rebase -i --autosquash <base>`로 합친다. 합치기 전 HEAD에 백업 브랜치를 만들고, 합친 뒤 `git diff <백업> HEAD`가
   비었는지와 작성자가 그대로인지 본다. 확인되면 백업 브랜치를 지우고 그 해시를 보고에 적는다. 충돌하면
   `git rebase --abort`하고 합치기를 생략한다. 브랜치가 이미 원격에 있으면 강제 push 승인 없이는 합치지 않는다.

끝났다고 보는 기준: 고친 지적은 검증해 커밋했고, 반영하지 않은 지적은 이유를 남겼고, 고친 뒤 4번을 다시 통과했다.

## 6. 제출

push·PR 전에 verification.md의 `check`로 모든 완료 조건을 확인한다. 실패·미실행·미확인이 남으면 전체 달성으로 보고하지
않는다. 2단계·요청문·지침에 push·PR 승인이 있을 때만 push하고 PR을 만든다. 승인이 없으면 커밋까지 하고 7단계로 간다.
커밋·PR 형식은 프로젝트·전역 지침이 정한 것을 따르고, 없으면 [commit-and-pr.md](references/commit-and-pr.md)를 따른다.

PR을 만들었으면 [merge-criteria.md](references/merge-criteria.md)의 조건을 모두 채울 때 머지한다. 하나라도 빠지면 걸린
조건을 적어 사용자에게 머지를 요청하고, 그 PR마다 [pr-review-visual.md](references/pr-review-visual.md)대로 전/후 시각
자료를 만들어 대화에 띄운다.

기능 브랜치를 쓰면 기능 브랜치 안의 PR이 모두 들어온 뒤 기능 브랜치를 빌드해 완료 기준을 기기에서 대조하고, 통과한
뒤 develop PR을 만든다. PR마다 따로 통과한 것으로 완료라고 보고하지 않는다.

끝났다고 보는 기준: 승인 범위까지 커밋·push·PR을 마쳤고, PR마다 머지했거나 머지를 요청했다.

## 7. 보고 → 회고

바뀐 동작 · 핵심 결정 · 확인한 것 · 남은 한계를 먼저 짧게 설명한다. 이어서 작업 위치(레포·브랜치) · 커밋 목록 ·
검증 결과(무엇을 돌려 어떻게 나왔는지, 못 한 것은 "미검증"을 먼저) · 반영하지 않은 리뷰 지적 · 문서 영향 · 합의와
달라진 점 · PR URL · 자동 머지한 PR과 머지를 요청한 PR을 적는다. 설명을 생성했다는 이유로 사용자가 이해했다고
기록하지 않는다. PR 본문에는 이 중 바뀐 동작·결정·검증 결과·남은 한계만 싣는다.

보고 직후 묻지 않고 이번 작업을 회고한다. 지침·스킬을 바꾸자는 후보는 반영 전에 사용자에게 묻는다.

## 커밋 규칙

- 매 커밋 전에 그 변경에 맞는 타입 검사·테스트·실행을 실제로 돌린다. 못 돌렸으면 이유와 함께 "미검증"으로 남긴다.
- 매 커밋 직전 `pwd`·`git rev-parse --show-toplevel`·`git branch --show-current`로 작업 위치를 확인한다.
- 작성자는 대상 레포의 git 설정을 그대로 쓴다. `--author`·`GIT_AUTHOR_*`로 덮지 않고, 서브에이전트에 커밋을 맡기면
  이 규칙을 지시에 적는다.
- `--no-verify`로 훅을 우회하지 않는다. 포맷 검사 실패는 레포의 포맷 명령으로 고친다.
- 변경 없는 점검에 빈 커밋을 만들지 않는다.

## 멈추는 곳

2단계 승인 뒤에는 멈추지 않고, 묻지도 경과를 보고하지도 않는다. 합의에 없던 판단은 목표·범위 안이면 직접 정하고
보고의 "합의와 달라진 점"에 남긴다. 계획서가 있으면 본문은 고치지 않고 `변경·결정 로그`에 한 줄 더한다.

예외는 다음뿐이다. 이때는 깨졌다고 본 관찰을 근거로 보이고 묻는다: 멈춤 전제가 깨졌을 때, 목표를 이룰 수 없을 때,
범위 밖을 건드려야 할 때, 필요한 도구·권한이 없을 때.

## 이어받기 메모

세션이 끊겨도 다른 세션이 이어받을 수 있게 메모 하나를 단계를 끝낼 때마다 갱신한다. 담을 것: 레포·브랜치·base·HEAD,
끝낸 단계와 남은 단계, 막힌 것, 합의와 달라진 점. 6단계 머지 판단은 이 메모와 4단계 증거를 근거로 한다.

- 프로젝트나 상시 지침이 세션 기록 문서를 정했으면 그 문서에 쓰고 따로 만들지 않는다.
- 없으면 계획서 옆에 `handoff.md`로 둔다. 계획서가 코드 레포 안에 있거나 없으면 프로젝트 지침이 정한 작업 폴더에
  둔다. 팀이 보는 코드 레포 안에는 두지 않는다. 둘 곳이 없으면 2단계에서 한 번 물어 프로젝트 지침에 적는다.
- 계획서 없이 진행한 작은 작업은 메모를 만들지 않고 보고로 대신한다.
- "작업 이어서 해줘"면 이 메모와 `git log <base>..HEAD`로 남은 단계부터 이어간다.
