# problem-definition

"무엇을 만들까"가 아니라 "무엇을 이뤄야 하고, 무엇으로 이뤘다고 판정하나"를 문서로 세운다. 기획 문서 세 개
(문제 정의 → 설계 → 플랜) 중 첫 번째다. 세 문서의 경계·연결·저장 위치·검수 절차는 이 플러그인의
`references/planning-docs.md`(이 스킬 폴더 기준 `../../references/planning-docs.md`)가 정한다. 시작 전에 읽는다.

**핵심 원칙**

- **해법을 쓰지 않는다.** 문제 안에 "X를 만든다"가 섞이면 선택지가 그 해법 하나로 좁아진다. 해법이 떠오르면
  문서 본문에 쓰지 말고 "사용자가 정할 것" 아래 `→ solution-design:` 메모로만 남긴다.
- **정의의 주인은 사용자다.** 이 스킬은 구조를 세우고, 질문하고, 후보를 낸다. 문제·세부 목표·판정 기준·범위를
  정하는 것은 사용자다. 에이전트가 먼저 채운 정의는 확정되지 않은 전제가 되어 뒤따르는 설계·플랜 전체를 끌고 간다.
  - 사용자가 주지 않은 수치·대상·전제는 **그 칸마다** `후보:`를 붙인다. 판정 기준 안의 작은 조건도 마찬가지다 —
    개수("초안 2안"), 제외 조건("스팸함 아님"), 대상 환경("실기기에서"), 포함 항목("금액과 일시")이 요청에
    없었으면 `후보:`다. 문서 머리에 "전부 잠정"이라고 한 줄 적는 것으로 대신하지 않는다 — 읽는 사람은 칸 단위로
    읽고, 표시 없는 칸은 확정으로 읽는다.
  - 정의 전체를 가르는 전제(대상 플랫폼, 사업 모형, 대상 고객층, 무엇을 "완성"으로 볼지)는 후보로도 채우지 말고
    "사용자가 정할 것"에 질문으로 올린다.
- **판정할 수 없는 목표는 정의가 끝나지 않은 것이다.** "개선하기"는 끝났는지 알 수 없다. 무엇으로 달성을
  판정할지 세워야 설계도, 플랜도, 평가도 성립한다.

## 실행 절차

### 1. 입력 모으기

대화나 사용자가 준 문서에서 먼저 찾고, 없는 것만 묻는다.

- 목표와 그 원천(회의록, 지시, 본인 생각). 원천 문서가 있으면 읽고 목표·완료 기준 문장을 그대로 인용한다
- 저장 위치 — `planning-docs.md`의 저장 위치 규칙을 따른다

### 2. 문제 정의

목표마다 네 칸을 적는다.

| 칸 | 내용 |
|---|---|
| 지금 상태 | 무엇이 어떻게 되어 있는가. 확인한 사실만 |
| 이룰 상태 | 목표가 이뤄지면 무엇이 달라지는가. 해법이 아니라 달라진 상태로 쓴다 |
| 왜 | 원천에서 나온 이유. 인용과 출처 |
| 범위 밖 | 이 목표가 다루지 않는 **상태**. 이번에 미루는 작업은 플랜에 둔다 |

사용자에게서 나오지 않은 칸은 `후보:`로 두거나 질문으로 남긴다. 목표 자체가 흐려서 네 칸이 서지 않으면, 그
목표는 grill로 의도를 먼저 캐내자고 제안한다.

### 3. 세부 목표로 분해

목표 하나를 이룰 상태 여럿으로 쪼갠다. 작업도 해법도 아니라 상태로 쓴다 — "안내 팝업을 만든다"가 아니라
"로그인이 실패하면 사용자가 이유를 안다".

- 세부 목표를 모두 이루면 상위 목표가 이뤄지는가 본다. 빠진 조각이 있으면 드러낸다.
- 세부 목표끼리 따로 판정할 수 있게 나눈다. 겹치면 한쪽이 끝났는지 알 수 없다.
- 의도가 흐린 세부 목표에는 `→ grill`을 붙인다.
- 분해는 두 단계 정도에서 멈춘다. 더 내려가면 해법이나 작업이다.

### 4. 판정 기준 (OKR)

목표와 세부 목표를 Objective로, 판정 기준을 Key Result로 쓴다. Objective마다 KR 1~3개. KR은 `O1.1 KR1`처럼
목표 번호와 함께 부른다 — 설계·플랜이 이 이름으로 가리킨다.

- KR은 판정할 수 있는 **결과**다. "화면 5개 수정"은 작업이고, "결과 화면에서 다음 행동으로 가는 버튼이 있다"는 결과다.
- **참/거짓으로 판정할 수 있으면 참/거짓으로 쓴다.** 수치 목표는 사용자가 값을 줬거나 기준선이 있을 때만 쓴다.
  근거 없는 목표값("60% 이상", "5명 중 4명")은 판정을 정확해 보이게 할 뿐, 그 숫자가 왜 성공선인지 아무도 모른다.
  수치가 필요한데 값이 없으면 "기준선 대비 상승"처럼 방향만 두고 목표값은 `후보:`나 질문으로 남긴다.
- 제출·배포처럼 해냈는지가 곧 결과인 이정표도 참/거짓 KR이다.
- KR마다 네 칸을 채운다.

| 칸 | 내용 |
|---|---|
| 판정 기준 | 관찰 가능한 조건. 참/거짓 우선. 수치면 값의 출처(사용자·기준선)가 있어야 하고, 없으면 `후보:` |
| 판정 방법 | `확인`(파일·코드·상태로 기계 확인) / `에이전트 채점`(기준 문장으로 검수 에이전트가 판정) / `사람 판정` |
| 판정 시점 | 날짜나 앞 단계("구현 후", "베타 뒤 1주") |
| 유형 | `약속`(반드시 달성) / `도전`(0.0~1.0으로 채점, 0.7이면 양호) |

`에이전트 채점` KR은 맥락 없는 에이전트가 그 문장만 읽고 판정할 수 있게 쓴다. "사용성이 좋다"는 채점할 수 없고,
"결과 화면 첫 화면에 다음 행동 버튼이 하나 이상 있고, 그 문구가 동사로 시작한다"는 채점할 수 있다.

### 5. 저장과 검수

1. `assets/problem-definition.template.md` 형식으로 쓰고 저장한다.
2. 기계 검사를 돌린다.

   ```bash
   python3 <이 스킬>/scripts/check_problem.py <문서 경로>
   ```

   비거나 허용되지 않은 KR 칸, 출처 없이 수치가 든 KR, 이 문서에 오면 안 되는 절(작업·일정·요구사항·위험)과
   작업 체크박스를 짚는다. 수치 KR 경고는 그 값을 사용자가 줬으면 무시하고, 아니면 `후보:`를 붙인다. 오류는
   고치고 다시 돌린다.
3. `planning-docs.md`의 검수 절차대로 `plan-reviewer`를 부른다. 루브릭은 이 스킬의 `references/review-rubric.md`,
   관점은 `기획`이다.
4. 미통과를 고친다. 사용자가 정할 문제(`후보` KR, 전제 질문)로 걸린 것은 고치지 말고 질문으로 올린다.

### 6. 보고와 다음 질문

대화에는 다음만 적는다.

- 저장 위치
- 사용자가 정해야 할 것 중 **가장 먼저 막히는 질문 하나**와 선택지. 나머지는 목록으로만
- 검수 결과: 통과 수, 남은 미통과와 이유 (독립 검수를 못 돌렸으면 첫 줄에)
- 다음 단계: 문제 정의가 확정되면 `solution-design`으로 설계를 쓴다

사용자가 답하면 해당 칸을 확정하고, 그 답에 걸린 세부 목표·KR을 함께 고친다. 한 곳만 고치면 문서가 자기모순이
된다.

## 행동 원칙

- 정의하는 동안 해법을 고르거나 작업을 실행하지 않는다.
- 사용자가 준 사실·수치는 그대로 쓰고, 모르는 것은 추측하지 않고 묻는다.
- 사용자가 관찰이나 질문을 말할 때 그것을 정의 변경 지시로 읽지 않는다. 확인하고 고친다.
