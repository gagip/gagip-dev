# 문제 정의 검토 기준

problem-definition이 쓴 문서를 맥락 없이 검토할 때 쓴다. 스킬을 개발할 때의 품질 채점과, 실제 사용 때의 검수가
같은 기준을 쓴다.

## 검토자에게 주는 지시

- 문제 정의 문서만 읽고 판정한다. 문서를 쓴 대화의 맥락은 받지 않는다.
- 항목마다 `통과` / `미통과` / `판정 불가` / `해당 없음`을 매기고, 근거로 문서의 해당 줄을 인용한다.
- `미통과`는 무엇을 어떻게 고치면 통과하는지 한 줄로 적는다.
- 사용자가 정할 문제(예: `후보:`로 남은 칸)는 문서 결함이 아니다. `판정 불가`로 두고 "사용자 확인 필요"라고 적는다.
- 파일을 고치지 않는다.

## 기준

### 문제와 목표

| # | 기준 | 미통과 예 |
|---|---|---|
| 1 | 목표마다 지금 상태·이룰 상태·왜·범위 밖이 있고, 왜에는 원천이 붙어 있다 | 이룰 상태만 있고 왜 하는지 없음 |
| 2 | 세부 목표가 작업이 아니라 상태로 쓰였고, 모두 이루면 상위 목표가 이뤄진다 | "문서 작성"처럼 작업을 세부 목표로 둠, 상위 목표에 필요한 조각이 빠짐 |
| 3 | 세부 목표끼리 따로 판정할 수 있게 나뉘었다 | 두 세부 목표가 같은 결과를 다른 말로 반복 |
| 4 | 사람이 정할 내용을 지어내지 않았다. 요청 원문에 없는 수치·대상·전제는 그 칸마다 `후보:`가 붙었고(문서 머리의 일괄 단서는 인정하지 않는다), 정의 전체를 가르는 전제는 질문으로 올라갔다 | 요청에 없던 "iOS만"을 확정처럼 씀 |
| 5 | 해법이 섞이지 않았다. 이룰 상태·세부 목표·KR·범위 밖이 만들 것이나 구현 방식을 정하지 않는다(해법 메모는 "사용자가 정할 것"의 `→ solution-design:` 줄에만 있다) | "안내 팝업을 추가한다"를 이룰 상태로 둠, KR이 "재시도 버튼이 3회 제한으로 동작"처럼 특정 구현을 가정 |
| 6 | 작업·일정·위험이 섞이지 않았다. 담당 표시 작업 목록, 날짜표, 위험 목록이 없다 | "에이전트: 조사한다" 체크박스가 있음 |

### 판정 기준 (OKR)

| # | 기준 | 미통과 예 |
|---|---|---|
| 7 | Objective마다 KR 1~3개가 있고, KR마다 판정 기준·방법·시점·유형이 있다 | 판정 방법이나 시점이 빈 KR |
| 8 | KR이 작업이 아니라 결과를 잰다. 참/거짓으로 판정할 수 있는 KR은 참/거짓으로 썼고, 수치 목표값은 출처(사용자·기준선)가 있거나 `후보:`다 | "화면 5개 수정"을 KR로 둠, 근거 없이 "60% 이상"을 성공선으로 둠 |
| 9 | `에이전트 채점` KR은 맥락 없는 에이전트가 그 문장만으로 판정할 수 있다 | "사용성이 좋다" |

## 출력 형식

```
검토 대상: <경로>
통과 N / 미통과 N / 판정 불가 N / 해당 없음 N

| # | 판정 | 근거(인용) | 고칠 것 |
|---|---|---|---|
```
