# solution-design

문제를 **어떻게 풀지**를 의사결정자가 읽고 승인할 수 있는 설계 문서로 쓴다. 기획 문서 세 개(문제 정의 → 설계 →
플랜) 중 두 번째다. 세 문서의 경계·연결·저장 위치·검수 절차는 이 플러그인의 `references/planning-docs.md`(이
스킬 폴더 기준 `../../references/planning-docs.md`)가 정한다. 시작 전에 읽는다.

**핵심 원칙**

- **설계는 의사결정자가 읽는다.** 문서만 보고 갈림길마다 무엇을 골랐고 왜 골랐는지 판단할 수 있어야 한다.
  설계 판단은 주제별로 묶어 `결정 | 이유 | KR` 표로 낸다. 나열식 문단으로 이어 쓰면 갈림길이 몇 개인지,
  어디까지가 한 판단인지 안 보인다.
- **결정은 목표에 매단다.** 결정마다 번호(`D1`)를 붙이고, 그 결정이 기여하는 KR(`O1.1 KR1`)을 적는다. 어떤 KR에도
  기여하지 않는 결정은 과잉 설계이거나 문제 정의에 빠진 목표가 있다는 신호다 — 사용자에게 어느 쪽인지 묻는다.
- **다른 문서의 몫을 쓰지 않는다.** 문제·목표·성공 기준은 문제 정의를 가리킨다. 작업 순서·담당·일정·검증 절차·
  코드 리뷰·브랜치명은 플랜 몫이다.
- **코드 전문·프롬프트 전문·완성된 diff·파일별 작업 순서표는 넣지 않는다.** 그런 디테일은 구현 단계에서 나오고
  리뷰 때 diff로 논의한다. 배제 대상은 완성된 코드 본문·내부 호출 순서·file:line 참조이지 공개 인터페이스가
  아니다 — 새로 만들거나 바꾸는 함수·클래스 시그니처, CLI 옵션 같은 공개 인터페이스는 그것이 필요한 이유를
  설명하는 결정 문장 안에 넣는다. 별도 절로 빼지 않는다.
- **갈림길은 사용자가 고른다.** 방법이 둘 이상이면 가르는 기준을 세우고 방안을 장단점과 함께 내 사용자가 고르게
  한다(권장안을 첫 번째로). 실질적 대안이 없으면 "대안 없음"을 밝힌다. 사용자가 고르지 않은 결정은 그 칸에
  `후보:`를 붙인다.

## 실행 절차

### 1. 입력 확인

| 입력 | 처리 |
|---|---|
| 문제 정의 문서 위치 | 읽고 KR 목록(`O1.1 KR1` …)을 확보한다 |
| 이슈 번호·URL | `gh issue view <번호> --json number,title,body,labels,url`로 읽는다. 문제 정의 문서가 없으면 아래 "문제 정의가 없을 때"를 따른다 |
| 자연어 주제 | 그대로 주제로 쓴다. 문제 정의 문서가 없으면 아래를 따른다 |
| 기존 설계 문서 | 읽고 `check_solution.py`와 루브릭으로 점검한 뒤 누락을 알리고 보강할지 묻는다 |
| 인자 없음 | 무엇의 설계인지 묻는다 |

**문제 정의가 없을 때**: `problem-definition`부터 쓰자고 제안한다. 사용자가 생략을 고르면 머리말에
`문제 정의: 생략 (<이유>)`를 적고 KR 칸은 `—`로 둔다. 이슈 본문의 "완료 기준"이 있으면 그 인용을 이유에 적는다.

저장 위치는 `planning-docs.md`의 저장 위치 규칙을 따른다.

### 2. 탐색과 논의

- 사용자 질문에 답하고 방향을 함께 정한다. 불명확한 부분은 구조화 질문 도구가 있으면 쓰고, 없으면 권장안을 첫
  번째에 둔 번호 목록으로 묻는다. 임의로 정하지 않는다.
- 이슈·문제 정의가 언급한 파일·심볼이 실제 코드에 없으면 바로 알린다.
- 코드베이스만으로 판단이 서지 않는 외부 사실(라이브러리 동작, API 스펙, 버전별 변경, 표준)은 웹 검색으로 찾고
  원문을 확인한다. **출처 URL을 그 근거에 기댄 결정 옆이나 `## 참고 자료`에 남긴다.** 출처 없는 외부 주장은
  쓰지 않는다.
- 재사용할 기존 패턴·자산이 있으면 새로 만들기 전에 그것부터 본다.
- **실험으로만 판정 가능한 미검증 전제**(외부 SDK·플랫폼·비동기 동작 등)가 있는지 본다. 있으면 3절
  `기술 리스크 / 선행 검증`으로 분리한다. 사용자에게 묻거나 문서로 풀리는 불확실성은 대상이 아니다.
- 구조·흐름이 복잡하면 다이어그램·시각화 도구가 있을 때 대화 응답에서 보여준다. 문서에는 판단과 근거만 남긴다.

**외부 요인으로 막히면 보류로 저장한다.** 가장 근본적인 결정이 우리 손 밖의 의존(다른 팀 확인, 외부 응답)에
막히면 그때까지의 조사·검증 결과를 잃지 않게 머리말 `상태: 보류 (<기다리는 것>)`로 저장하고, 막힌 결정은
미해결 설계 사안에 무엇을 기다리는지와 함께 적는다.

### 3. 문서 작성

`assets/solution-design.template.md` 형식으로 쓴다.

| 절 | 담는 것 |
|---|---|
| 머리말 | 작성일, `문제 정의:` 위치(또는 생략 사유), 이슈, 상태(초안·확정·보류) |
| 1. 요구사항 | 주제별 `# \| 결정 \| 이유 \| KR` 표. 이유에는 대안 대비 무엇이 나은지. 조사에서 나온 근거는 별도 절이 아니라 그 결정의 이유 칸에 요약한다. 조사 비용이 컸던 발견(실기기·외부 API를 직접 열어보고서야 안 사실)은 반드시 남긴다 |
| 초안에서 철회한 것 | 있으면. 왜 그 길로 안 갔는지가 다음 사람의 재발명을 막는다 |
| 2. 제약 | 무엇을 할 수 없고 그래서 어떻게 되는지. 많으면 성격별로 나눈다 |
| 3. 기술 리스크 / 선행 검증 | 해당할 때만. 아래 형식 |
| 4. 미해결 설계 사안 | 아직 정하지 않은 설계 결정과 무엇을 기다리는지. 없으면 "없음" |
| 참고 자료 | 외부 근거가 있으면 출처 URL |

**선행 검증 형식** — 검증할 질문(가장 불확실한 전제 1~2개) / 검증 방법(버리는 최소 코드로 그 한 점만) /
통과 기준(**통과 신호가 검증 대상 경로를 실제로 거쳤는지**까지 — 경로를 안 타고 즉시 떨어진 신호를 통과로
오판하지 않게) / 실패 시 대안 / 타임박스 / 검증 뒤 처리(검증 코드는 커밋하지 않고 배운 것만 설계에 반영) /
착수 재판단(한 점만 찔렀는데 본 구현이 낼 결과가 이미 상당 부분 나왔으면 범위를 줄이거나 접을지 묻는다).
선행 검증을 **언제 누가 돌릴지**는 플랜이 정한다.

### 4. 저장과 검수

1. 저장한다.
2. 기계 검사를 돌린다. 문제 정의 문서가 있으면 함께 넘겨 KR 연결을 확인한다.

   ```bash
   python3 <이 스킬>/scripts/check_solution.py <설계 문서> [--problem <문제 정의 문서>]
   ```

   결정 번호·칸 누락, 없는 KR을 가리키는 결정, 이 문서에 오면 안 되는 절(배경·목표·성공 지표·작업·일정·검증·
   코드 리뷰·브랜치)과 작업 체크박스를 짚는다. 오류는 고치고 다시 돌린다.
3. `planning-docs.md`의 검수 절차대로 `plan-reviewer`를 부른다. 이 단계는 건너뛰지 않는다. 루브릭은 이 스킬의 `references/review-rubric.md`다.
   관점은 바꾸는 대상에 따라 더한다 — 코드·구조·API·데이터 흐름·설정·빌드를 바꾸면 `코드`, 화면·UI·사용자 흐름을
   바꾸면 `디자인`. 관점이 둘이면 한 응답에서 병렬로 띄운다. 코드와 대조해야 하면 코드베이스 절대경로와 HEAD를
   함께 넘긴다. 프로젝트에 전용 비평 에이전트·스킬(규제 문구·도메인 검수 등)이 있으면 해당할 때 함께 부른다.
4. 미통과와 Blocker는 고친다. 판정이 `반려`면 2절로 돌아가 다시 설계한다. Major 이하는 사용자와 취사선택한다.
   사용자가 정할 문제는 질문으로 올린다.

### 5. 보고와 다음 단계

대화에는 다음만 적는다.

- 저장 위치와 상태
- 가장 먼저 막히는 질문 하나와 선택지. 나머지 미해결 사안은 목록으로
- 검수 결과: 통과 수, 관점별 판정, 남은 미통과·Blocker (독립 검수를 못 돌렸으면 첫 줄에)
- 다음 단계: 사용자가 설계를 확정하면 머리말 상태를 `확정`으로 바꾸고 `work-plan`으로 플랜을 쓴다.
  구현은 플랜 승인 뒤다

## 행동 원칙

- 설계하는 동안 코드를 고치지 않는다. 선행 검증 코드도 플랜 승인 전에는 돌리지 않는다.
- 이슈·문제 정의에 모호한 부분이 있으면 임의로 정하지 않고 묻는다.
- 새 의존성이 필요하면 요구사항 결정으로 밝힌다(버전 고정 규칙 영향 포함).
