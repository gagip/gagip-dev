# 설계 검토 기준

solution-design이 쓴 문서를 맥락 없이 검토할 때 쓴다. 스킬을 개발할 때의 품질 채점과, 실제 사용 때의 검수가 같은
기준을 쓴다.

## 검토자에게 주는 지시

- 설계 문서와, 받았다면 문제 정의 문서만 읽고 판정한다. 문서를 쓴 대화의 맥락은 받지 않는다.
- 코드베이스 경로를 받았으면 문서가 전제하는 파일·심볼·동작이 실제로 그런지 확인한다. 확인하지 못한 전제는
  "미확인"으로 적는다.
- 항목마다 `통과` / `미통과` / `판정 불가` / `해당 없음`을 매기고, 근거로 문서의 해당 줄을 인용한다.
- `미통과`는 무엇을 어떻게 고치면 통과하는지 한 줄로 적는다.
- 사용자가 정할 문제(`후보:`, 미해결 설계 사안)는 문서 결함이 아니다. `판정 불가`로 두고 "사용자 확인 필요"라고 적는다.
- 문제 정의가 `생략`이면 3·4번은 `해당 없음`으로 둔다.
- 파일을 고치지 않는다.

## 기준

### 결정

| # | 기준 | 미통과 예 |
|---|---|---|
| 1 | 설계 판단이 주제별 `결정 \| 이유 \| KR` 표에 있고, 결정마다 번호(D)가 있다. 왼쪽 열만 훑어도 무엇을 정했는지 보인다 | 판단이 문단 속에 묻혀 있음 |
| 2 | 이유가 대안 대비 무엇이 나은지를 말한다. 갈림길이 있던 결정은 고른 기준이 보인다 | 이유가 결정을 되풀이함("캐시를 쓴다 — 캐시가 필요해서") |
| 3 | 결정마다 적힌 KR에 실제로 기여한다 | 로깅 형식 결정이 "안내 문구 표시" KR에 매달림 |
| 4 | 문제 정의의 KR 중 어느 결정과도 이어지지 않은 KR이 있으면, 설계가 필요 없는 이유나 미해결 사안이 적혀 있다 | 핵심 KR 하나가 설계에서 통째로 빠짐 |
| 5 | 사용자가 정할 결정을 지어내지 않았다. 갈림길이 있는데 확정처럼 쓴 결정은 사용자가 고른 것이거나 그 칸에 `후보:`가 있다 | 요청에 없던 저장소 선택을 확정처럼 씀 |
| 6 | 공개 인터페이스(시그니처·CLI 옵션 등)가 필요한 결정은 그 결정 문장 안에 인터페이스가 있다. 코드 전문·diff·file:line·파일별 작업 순서표는 없다 | 함수 본문 전체를 붙임, 새 CLI 옵션 이름이 어디에도 없음 |

### 경계

| # | 기준 | 미통과 예 |
|---|---|---|
| 7 | 문제·목표·성공 기준을 다시 쓰지 않고 문제 정의를 가리킨다 | "## 목표" 절에 문제 정의 내용을 옮겨 적음 |
| 8 | 작업 순서·담당·일정·검증 절차·코드 리뷰·브랜치명이 없다 | "먼저 A를 고치고 다음 B" 순서, 테스트 계획 절 |

### 불확실성

| # | 기준 | 미통과 예 |
|---|---|---|
| 9 | 제약마다 그 결과(그래서 무엇이 안 되거나 어떻게 되는지)가 있다 | "서버 변경 불가"만 적고 영향 없음 |
| 10 | 실험으로만 판정 가능한 전제가 있으면 선행 검증이 있고, 통과 기준이 검증 대상 경로를 실제로 거쳤는지까지 요구한다. 그런 전제가 없으면 `해당 없음` | SDK 콜백 동작에 기대면서 선행 검증이 없음, 통과 기준이 "콜백이 온다"뿐 |
| 11 | 외부 사실(라이브러리 동작·API 스펙 등)에 기댄 결정에 출처 URL이 있다 | "이 SDK는 재시도를 자동으로 한다"에 출처 없음 |

## 출력 형식

```
검토 대상: <경로>
통과 N / 미통과 N / 판정 불가 N / 해당 없음 N

| # | 판정 | 근거(인용) | 고칠 것 |
|---|---|---|---|
```
