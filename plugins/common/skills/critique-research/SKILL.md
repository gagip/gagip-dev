## 왜 필요한가

**쓴 사람은 자기 글을 검증할 수 없다.** 코드는 돌려 보면 틀린 게 드러나지만, 글은 틀려도 그대로 읽힌다 — 특히 표 안의 숫자는 그럴듯해 보여서 저자가 다시 봐도 안 걸린다.

그리고 조사 문서의 결함은 **문장이 아니라 다리에 있다.** 계수는 맞는데 거기서 처방으로 넘어가는 대목이 비약이거나, 자기가 세운 구분이 자기 결론을 반박하거나, 표본 설계가 보장한 결과를 발견으로 적는 식이다. 이건 같은 사람이 다시 읽어서는 안 보인다 — 그 다리를 놓은 게 본인이기 때문이다.

실측(2026-09-16): 스크린샷 653장을 집계한 조사 문서를 다섯 관점에 넘겼더니 여섯 건이 나왔다 — 방향이 반대로 적힌 비교 한 건, 어떤 정의로도 재현되지 않는 상관계수 한 건, 근거 없이 단정한 규제 판정 한 건, 자기 구분이 자기 결론을 뒤집는 자리 한 건, 원자료에 있는데 안 쓴 절 하나, 그리고 **원자료 파일 자체가 부분 집합**이었다는 것. 저자는 그 직전까지 문서를 세 번 고쳤는데 하나도 못 잡았다.

## 언제 쓰나

**쓴다** — 글이 산출물이고 남이 그걸 근거로 다음 일을 할 때:
- 조사·벤치마킹·실측 보고서
- 분석 문서, 의사결정 근거 문서
- 수치·표·집계가 든 모든 문서

**안 쓴다**:
- 디자인 시안·목업 → `mockup-review`가 담당한다. 관점이 다르다 — 시안은 "이 화면이 작동하는가"를 묻고, 이 스킬은 "이 주장이 근거를 갖는가"를 묻는다
- 코드 변경 → 정확성·동시성·테스트 실효성 같은 코드용 관점으로 간다
- 개인 메모, 대화 요약, 한 번 쓰고 버릴 글

## 절차

### 1. 관점을 고른다

**전부 다 띄우지 않는다.** 문서 성격에 맞는 것만 고른다. 아래 다섯이 기본 후보다.

| 관점 | 무엇을 묻나 | 언제 넣나 |
|---|---|---|
| **수치 재현** | 문서의 모든 숫자를 원자료에서 다시 계산해 일치하는가. 집계 정의가 절마다 일관되는가 | 원자료가 파일로 있을 때. **원자료가 있으면 이건 거의 항상 넣는다** |
| **논증 구조** | 관찰에서 결론으로 넘어갈 때 빠진 전제. 자기모순. 제목이 본문보다 센 자리. 표본 구성이 결론을 만든 자리 | 문서가 권고·판정을 낼 때 |
| **미사용 인사이트** | 원자료에 있는데 문서가 안 쓴 것 | 원자료가 문서보다 클 때 |
| **실행 유용성** | 이 문서를 받아 다음 일을 할 사람이 무엇을 결정할 수 있나. 안 읽어도 결과가 같은가 | 문서가 누군가의 입력일 때 |
| **압축** | 무엇을 자르고 무엇을 합치나 | 문서가 길어졌을 때 |

성격이 다르면 새로 짠다 — 위 다섯은 목록이지 정답이 아니다.

### 2. 프롬프트를 규격대로 쓴다

**네 가지를 반드시 넣는다.** 하나라도 빠지면 그만큼 검증이 약해진다.

1. **읽기 전용을 명시한다** — "파일을 편집·생성하지 말고 git 명령·빌드를 실행하지 마라." 분석용 일회성 스크립트 실행이 필요하면 그것만 따로 허용한다. `git` 금지를 따로 적는다 — "실행 금지"만으로는 상태를 바꾸는 git 명령이 안 걸린다.
2. **도구 호출 상한과 부분 결과 반환을 적는다** — "도구 호출 N회 이내. 예산을 넘기면 완료 못 해도 그때까지의 부분 결과를 반환하라." 여럿을 동시에 띄울 때 안 돌아오는 에이전트를 기다리며 시간을 버리지 않는다. 8~14회면 대개 충분하다.
3. **근거를 대게 한다** — "각 지적에 문서의 문장을 인용하라. 근거 없는 인상 비평은 쓰지 마라." 없으면 일반론만 돌아온다.
4. **내 논리를 주지 않는다** — 왜 그렇게 썼는지, 무엇을 고민했는지, 어떤 지적을 이미 받았는지를 **한 글자도 넣지 않는다.** 주면 그 옹호 논리를 그대로 흡수해 저자와 같은 사각지대를 공유한다. 주는 것은 **문서 경로 · 원자료 경로 · 필드 구조 · 이 문서를 받을 사람이 누구인지**까지다.

### 3. 한 응답에서 동시에 띄운다

관점끼리는 서로 독립이므로 순차로 띄울 이유가 없다. 한 응답에 전부 넣어 병렬로 돌린다.

### 4. 돌아온 것을 판정한다 — 전부 받아들이지 않는다

**검증 결과도 틀린다.** 원자료로 확인할 수 있는 지적은 직접 확인한 뒤 반영한다.

| 돌아온 것 | 어떻게 |
|---|---|
| 수치 불일치 | **직접 다시 계산한다.** 검증자의 집계 정의가 문서와 다를 뿐일 수 있다 |
| 논리 지적 | 문서의 그 문장을 열어 읽는다. 맞으면 고치고, 고칠 수 없으면 **약점을 문서에 적는다** |
| 놓친 인사이트 | 원자료에서 확인 장수를 직접 센 뒤 넣는다 |
| 서로 충돌하는 지적 | 충돌 자체를 사용자에게 보인다. 임의로 한쪽을 고르지 않는다 |

**고칠 수 없는 약점은 지우지 말고 적는다.** "독립 검증에서 지적받아 그대로 적는다"로 문서 안에 남기면, 다음 사람이 그 근거를 어디까지 믿을지 스스로 판단할 수 있다. 약점을 숨긴 문서보다 약점을 적은 문서가 더 오래 쓰인다.

### 5. 보고에 실행 여부를 밝힌다

- 돌렸으면 **몇 관점을 돌렸고 무엇이 나왔는지**, 반영한 것과 반영 안 한 것을 가른다.
- **안 돌렸으면 "독립 검증 미실행"을 보고 첫 줄에 밝힌다.** 검증 없이 낸 문서를 검증된 것처럼 보이게 두지 않는다.
- 서브에이전트를 쓸 수 없는 세션이면 같은 관점으로 직접 보되, **"독립 검증이 아니다"를 먼저 밝힌다** — 자기 글을 자기가 본 것이라 옹호가 섞인다.

## 원자료가 있으면 먼저 이것부터

수치 재현 관점을 띄우기 **전에**, 원자료 파일을 열어 **레코드 수를 세고 문서가 주장하는 N과 같은지 확인한다.**

집계 산출물은 중간본과 최종본이 같은 폴더에 생기기 쉽고, 이름만으로는 어느 쪽이 완성본인지 안 갈린다. 잘못된 파일을 근거로 삼으면 **문서를 몇 번 고쳐도 계속 틀린 입력 위에서 계산하게 된다** — 개정할 때 계산은 다시 하지만 계산의 입력은 의심하지 않기 때문이다.

문서를 고칠 때마다 반복한다. 한 번 맞았다고 계속 맞지 않는다.
