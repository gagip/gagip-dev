# 목표 설계 검토 기준

goal-design이 쓴 문서를 맥락 없이 검토할 때 쓴다. 스킬을 개발할 때의 품질 채점과, 실제 사용 때의 끝 검토가 같은
기준을 쓴다.

## 검토자에게 주는 지시

- 설계 문서만 읽고 판정한다. 문서를 쓴 대화의 맥락은 받지 않는다.
- 항목마다 `통과` / `미통과` / `판정 불가` / `해당 없음`을 매기고, 근거로 문서의 해당 줄을 인용한다.
- `미통과`는 무엇을 어떻게 고치면 통과하는지 한 줄로 적는다.
- 사용자가 정할 문제(예: `후보:`로 남은 칸)는 문서 결함이 아니다. `판정 불가`로 두고 "사용자 확인 필요"라고 적는다.
- 기한이 "없음"이면 기한·일정 항목(8·9)은 `해당 없음`으로 둔다.
- 파일을 고치지 않는다.

## 기준

### 문제와 목표

| # | 기준 | 미통과 예 |
|---|---|---|
| 1 | 목표마다 지금 상태·이룰 상태·왜·범위 밖이 있고, 왜에는 원천이 붙어 있다 | 이룰 상태만 있고 왜 하는지 없음 |
| 2 | 세부 목표가 작업이 아니라 상태로 쓰였고, 모두 이루면 상위 목표가 이뤄진다 | "문서 작성"처럼 작업을 세부 목표로 둠, 상위 목표에 필요한 조각이 빠짐 |
| 3 | 세부 목표끼리 따로 판정할 수 있게 나뉘었다 | 두 세부 목표가 같은 결과를 다른 말로 반복 |
| 4 | 사람이 정할 내용을 지어내지 않았다. 요청 원문에 없는 수치·대상·전제는 그 칸마다 `후보:`가 붙었고(문서 머리의 일괄 단서는 인정하지 않는다), 설계 전체를 가르는 전제(대상 플랫폼, 사업 모형, 대상 고객층, "완성"의 뜻)는 질문으로 올라갔다 | 사용자가 말하지 않은 타겟·수치를 확정처럼 기술, "앱스토어"를 특정 스토어로 단정, 요청에 없는 사업 모형을 전제로 KR을 씀 |

### 판정 기준 (OKR)

| # | 기준 | 미통과 예 |
|---|---|---|
| 5 | Objective마다 KR 1~3개가 있고, KR마다 판정 기준·방법·시점·유형이 있다 | 판정 방법이나 시점이 빈 KR |
| 6 | KR이 작업이 아니라 결과를 잰다. 참/거짓으로 판정할 수 있는 KR은 참/거짓으로 썼고, 수치 목표값은 출처(사용자·기준선)가 있거나 `후보:`다 | "화면 5개 수정"을 KR로 둠, 근거 없이 "60% 이상"을 성공선으로 둠 |
| 7 | `에이전트 채점` KR은 맥락 없는 에이전트가 그 문장만으로 판정할 수 있다 | "사용성이 좋다" |

### 작업과 일정

| # | 기준 | 미통과 예 |
|---|---|---|
| 8 | 목표마다 기한 판정이 있고, 근거가 사람 몫 크기·쓸 수 있는 칸·앞 단계 사슬에서 나온다. 안 들어가면 축소안이 있다 | 근거 없이 모두 "들어감" |
| 9 | 날짜표에 사람 몫만 있고, 고정 일정과 겹치지 않으며, 몰리는 날을 짚었다 | 에이전트 작업에 날짜를 배정, 회의 시간에 설계 작업 배치 |
| 10 | 담당 표시가 일의 성격과 맞다 | 범위 결정을 `에이전트`로, 코드 점검을 `사람`으로 표시 |
| 11 | 앞 단계가 실제 선후 관계와 맞고, 불필요한 앞 단계로 병렬 가능한 일을 막지 않는다 | 빌드가 구현보다 앞섬, 독립 조사에 앞 단계를 붙임 |
| 12 | 병렬이 안 되는 자원을 찾고 대응을 적었다 | 실물 한 대에 동시 작업을 가정 |
| 13 | 작업 항목이 끝났는지 판정할 수 있는 문장이다 | "정리하기", "개선하기" |
| 14 | 하지 않을 일마다 이유가, 위험마다 대응이 있다 | 제외 목록만 있고 이유 없음 |

## 출력 형식

```
검토 대상: <경로>
통과 N / 미통과 N / 판정 불가 N / 해당 없음 N

| # | 판정 | 근거(인용) | 고칠 것 |
|---|---|---|---|
```
