# work-plan

설계를 **누가 무엇을 어떤 순서로 하고, 무엇으로 확인하나**로 바꾼다. 기획 문서 세 개(문제 정의 → 설계 → 플랜)
중 마지막이고, 구현에 들어가기 전 사용자 승인을 받는 관문이다. 세 문서의 경계·연결·저장 위치·검수 절차는 이
플러그인의 `references/planning-docs.md`(이 스킬 폴더 기준 `../../references/planning-docs.md`)가 정한다.
시작 전에 읽는다.

**핵심 원칙**

- **만드는 일이 아니라 사람 칸이 병목이다.** 에이전트가 병렬로 돌면 구현은 짧다. 순서와 일정은 사람의 설계·결정·
  리뷰·실물 작업으로 센다.
- **작업은 설계와 목표에 매단다.** 작업마다 그 작업이 이루는 설계 결정(`D1`)이나 KR(`O1.1 KR1`)을 적는다. 어디에도
  매달리지 않는 작업은 범위를 조용히 넓히는 신호다.
- **확정된 것만 옮기지 않고 가리킨다.** 요구사항·규칙은 설계를, 문제·판정 기준은 문제 정의를 가리킨다.
- **들어가지 않으면 들어가지 않는다고 적는다.** 억지로 넣은 플랜은 첫날부터 틀린다. 줄이거나 뺄 것을 드러내고
  사용자가 고르게 한다.
- **사용자가 주지 않은 일정·크기·부재는 지어내지 않는다.** 칸마다 `후보:`를 붙이거나 묻는다.

## 실행 절차

### 1. 입력 모으기

대화나 사용자가 준 문서에서 먼저 찾고, 없는 것만 묻는다.

- 설계 문서. 머리말의 `문제 정의:`로 문제 정의 문서도 찾는다. 설계가 없으면 `solution-design`부터 제안한다.
  사용자가 생략을 고르면 머리말에 `설계: 생략 (<이유>)`를 적고 작업은 KR에 직접 매단다.
- 설계 상태가 `확정`이 아니면 확정할지 먼저 묻는다. 초안 위에 플랜을 쌓으면 설계가 바뀔 때 플랜이 통째로 틀린다.
- 기한과 고정 일정(행사, 마감, 회의). 기한이 없으면 일정 절은 만들지 않는다
- 다른 사람의 부재. 리뷰어·협업자가 없는 날은 그 사람이 필요한 작업을 놓을 수 없다
- 사용자 본인의 휴일·가용 시간. 참고로만 표시한다 — 휴일에 일할지는 사용자가 정한다
- 저장 위치 — `planning-docs.md`의 저장 위치 규칙을 따른다

날짜는 `date`로 확인한다. 요일을 추측하면 틀린다.

### 2. 작업 범위

- **이번에 하는 것**: 이번 플랜이 다루는 설계 결정(`D1`…) 목록.
- **미루는 작업**: 이번에 하지 않는 일과 이유. 이유가 없으면 다음에 같은 논의를 되풀이한다. 설계 결정을 통째로
  미루면 그 번호를 적는다. 이 목표가 다루지 않는 **상태**는 여기가 아니라 문제 정의의 "범위 밖"이다.

### 3. 작업 설계

설계 결정과 KR마다 그것을 이루는 작업을 적는다. 작업마다 담당 하나, 앞 단계, 대응 대상을 붙인다.

```
- [ ] <담당>: <끝났는지 판정할 수 있는 문장> ← <앞 단계> [<D번호·KR>]
```

| 표시 | 뜻 | 에이전트가 할 수 있는 것 |
|---|---|---|
| `사람(설계)` | 문제·기준·타겟·시나리오를 정한다 | 재료 수집, 후보 제시까지 |
| `사람(결정)` | 선택지 중 고르거나 범위를 정한다 | 선택지와 근거 정리까지 |
| `사람(리뷰)` | 에이전트 산출물을 받아들이거나 돌려보낸다 | 리뷰할 것을 정리해 올리기까지 |
| `사람(실물)` | 실물 조작, 외부 계정 조작, 사람과의 대화 | 준비물 정리까지 |
| `에이전트` | 구현·조사·빌드·검증·초안 | 전부 |

- 사용자가 자기 몫을 정했으면("나는 결정이랑 리뷰만") 그 밖의 일을 사람 몫으로 두지 않는다. 외부 계정·권한 때문에
  사람이 해야 하면 작업 문장에 그 이유를 적거나, 에이전트가 할 수 있는지를 질문으로 올린다.
- 대응 대상은 `[D1]`, `[O1.1 KR1]`, `[D1, O1.2 KR1]`처럼 적는다. 어느 결정에도 속하지 않는 공통 작업(브랜치 만들기
  등)만 `[공통]`이다.
- 앞 단계는 `← X`로 적는다. X가 끝나야 시작할 수 있다. 앞 단계가 없는 `에이전트` 항목은 사용자 확인 뒤 바로 돌릴
  수 있다.
- 기다릴 필요가 없는 작업에 앞 단계를 붙이지 않는다. 병렬로 돌 수 있는 일을 늦춘다.
- 앞 단계에는 그 작업이 실제로 필요로 하는 입력만 건다. 질문 여러 개를 묶은 "착수 전제" 하나를 모든 작업의 앞
  단계로 걸지 않는다 — 질문마다 그 답을 쓰는 작업에만 건다.
- 같은 묶음 안의 작업을 가리킬 때는 번호만 쓰지 말고 작업 이름까지 쓴다(`← 실패 경로 목록 저장`). 번호만 쓰면 그
  작업이 자기가 속한 묶음 전체를 기다리는 모양이 된다.
- 설계에 선행 검증이 있으면 그것을 첫 `에이전트` 작업으로 두고, 그 결과가 필요한 작업만 기다리게 한다.
- KR 판정도 한 줄로 넣는다. 판정 방법이 `확인`·`에이전트 채점`이면 `에이전트`, `사람 판정`이면 `사람(리뷰)`.
- 동시에 쓸 수 없는 자원(실물 한 대, 같은 파일을 건드리는 작업, 외부 계정·승인, 한 사람에게만 있는 권한)을 찾아
  순서를 정하거나 한 에이전트에 묶는다.
- 축소안을 적었으면, 그 축소안을 골랐을 때 앞 단계가 막지 않는지 본다. 막으면 앞 단계에 조건을 붙인다.
- 파일별 구현 순서까지 내려가지 않는다. 그건 구현 단계에서 코드 상태를 보고 정한다.

### 4. 검증 방법

문제 정의의 KR마다 무엇을 어떻게 확인하는지 적는다.

| 대상 | 확인 방법 | 예상되는 관찰 | 그때의 해석 |
|---|---|---|---|
| O1.1 KR1 | <무엇을 띄워 무엇을 보는지, 어떤 테스트로> | <나올 결과> | <무슨 뜻인지 — 실패로 읽힐 결과가 실은 유효한 경우 명시> |

- **최소 성공 기준** 한 줄: 무엇이 되면 이 작업이 성공인가.
- **테스트 실효성 확인**: 회귀 테스트·구조 가드를 새로 쓰면, 잡으려는 결함을 일부러 넣어 실제로 실패하는지 보고
  되돌린다(되돌린 뒤 `git diff`가 비었는지 확인).
- **실제 실행 확인**: 무엇을 어떻게 띄워서 무엇을 보는지 구체적으로.

### 5. 일정과 기한 판정 (기한이 있을 때)

- 날짜표에는 고정 일정과 사람 몫만 놓는다. 에이전트 몫은 앞 단계가 끝나면 병렬로 돌므로 날짜를 잡지 않는다.
- 사람 몫마다 크기(짧음 / 반나절 / 하루)를 적고 사용자에게 확인받는다. 추정이다.
- 목표마다 기한 안에 들어가는지 판정한다. 근거는 사람 몫 크기 합, 쓸 수 있는 칸, 앞 단계 사슬의 길이다.
  판정 전에 칸마다 거기 놓인 사람 몫 크기를 더해 칸 크기와 비교한다. 넘치면 그 칸에 걸린 목표는 `들어감`이 아니다.
- 사람 몫이 몰리는 날을 짚고, 그날 결정이 늦어지면 무엇이 밀리는지 적는다.
- 들어가지 않으면 축소안(어떤 작업을 줄이나, 어떤 설계 결정을 미루나, 기한을 옮기나)을 내고 사용자가 고르게 한다.
  축소안은 사람 몫을 줄여야 한다. 에이전트 산출물만 줄이는 것은 병목을 건드리지 않는다.

### 6. 리스크, 코드 리뷰, 브랜치

- **리스크**: 진행을 막을 수 있는 것마다 대응을 붙인다. 설계를 가르는 불확실성은 설계 문서에 있으므로 가리키기만 한다.
- **코드 리뷰** — 코드를 바꾸는 플랜이면 아래 체크리스트를 넣는다. `implement`로 실행하면 그 정리·리뷰 단계가
  이 체크리스트를 대신한다.
  - [ ] `/simplify` 실행 — 재사용·단순화·효율 관점으로 정리하고 수정 적용 (품질 전용, 버그는 잡지 않음)
  - [ ] 프로젝트에 커스텀 코드 리뷰 스킬이 있으면 함께 실행 (찾았으면 이름을 적는다)
  - [ ] 독립 검증 — 맥락 없는 읽기 전용 서브에이전트에 레포 경로·HEAD·변경 파일 목록만 주고 검토받는다
  - [ ] 지적 중 **위험한 것만** 수정 — 정확성 버그·보안·데이터 손상·크래시. 정리·스타일은 반영하지 않는다

  따로 배포·제출되는 단위(예: 서버와 앱)가 둘 이상이면 리뷰 사슬도 단위마다 나눈다. 한 사슬로 묶으면 한쪽
  구현이 늦거나 축소안으로 빠질 때 다른 쪽 배포·제출까지 막힌다.
- **브랜치명** — 코드를 바꾸는 플랜이면 머리말에 적는다. 프로젝트 규칙이 있으면 그것을, 없으면 이슈가 있을 때
  `fix/<번호>-<slug>`(레이블 fix·bug·hotfix) 또는 `feat/<번호>-<slug>`, 없을 때 `feat/<slug>`. slug는 영문 소문자와
  하이픈으로 40자 이하.

### 7. 저장, 검수, 승인

1. `assets/work-plan.template.md` 형식으로 쓰고 머리말 상태를 `초안`으로 저장한다.
2. 기계 검사를 돌린다. 앞 문서를 함께 넘겨 문서 간 연결을 확인한다.

   ```bash
   python3 <이 스킬>/scripts/check_plan.py <플랜> [--design <설계>] [--problem <문제 정의>]
   ```

   담당 표시 누락, 에이전트 항목의 날짜, 대응 대상 없는 작업, 없는 결정·KR을 가리키는 작업, 작업이 하나도 없는
   설계 결정, 검증 방법이 없는 KR, 끝나는 조건 없는 리뷰·수집 항목, 기한과 날짜표의 어긋남, 이 문서에 오면 안 되는
   절을 짚는다. 오류는 고치고 다시 돌린다.
3. `planning-docs.md`의 검수 절차대로 `plan-reviewer`를 부른다. 이 단계는 건너뛰지 않는다. 루브릭은 이 스킬의 `references/review-rubric.md`이고,
   앞 문서 경로를 함께 넘긴다.
4. 미통과를 고친다. 사용자가 정할 문제는 질문으로 올린다.
5. **승인을 받는다.** 아래 보고를 한 뒤 "이 플랜대로 진행할까요?"를 명시적으로 묻는다. 사용자가 승인하면 머리말을
   `상태: 승인됨 (YYYY-MM-DD)`로 바꾸고 저장한다. 승인 전에는 구현하지 않는다.
6. 승인되면 `implement`로 넘긴다. 사이클 머리말 `plan:`에 이 플랜 파일의 절대경로를 적는다. 문서 도구에
   저장했으면 사이클 폴더에 마크다운으로 내보내 그 경로를 적는다.

### 보고

대화에는 다음만 적는다.

- 저장 위치
- 사용자가 정해야 할 것 중 **가장 먼저 막히는 질문 하나**와 선택지. 나머지는 목록으로만
- 기한이 있으면 목표별 기한 판정 요약과 축소안
- 지금 바로 돌릴 수 있는 에이전트 작업(앞 단계 없는 항목)
- 검수 결과: 통과 수, 남은 미통과와 이유 (독립 검수를 못 돌렸으면 첫 줄에)

사용자가 답하면 해당 칸을 확정하고, 그 답에 걸린 작업·검증·일정을 함께 고친다. 승인 뒤 플랜을 고치면 상태를
`초안`으로 되돌리고 다시 승인받는다.

## 행동 원칙

- 플랜을 쓰는 동안 작업을 실행하지 않는다. 착수는 사용자가 플랜을 승인한 뒤다.
- 구현량으로 일정을 늘리지 않는다. 에이전트 병렬 환경에서 늘어나는 것은 리뷰다.
- 사용자가 준 날짜·부재·일정은 그대로 쓰고, 모르는 것은 추측하지 않고 묻는다.
- 진행 상황은 이 문서에 쌓지 않는다. 실행 중 진행은 `implement`의 사이클 기록이 맡는다.
