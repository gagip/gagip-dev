# work-plan

계획서는 두 독자를 위해 쓴다. 착수할 에이전트는 무엇을 어디까지 하고 무엇으로 끝났다고 할지를 읽고, 승인할
사람은 무엇을 정해야 하는지를 읽는다. 둘 중 누구도 쓰지 않는 칸은 만들지 않는다. 분량은 1~2쪽이다.

## 작업 종류별 문서

| 종류 | 착수 전 | 끝 |
|---|---|---|
| 개발 | 이슈(왜·완료 기준). `implement`의 바로 착수 기준을 넘거나 사용자가 요청하면 계획서도 쓴다 | PR 본문 |
| 기획 | 계획서 | 결정 문서(`html-brief` 등). 정해진 것은 기준 문서와 이슈로 옮긴다 |
| 연구·조사 | 계획서(판정선) | 보고서와 원자료 |
| 디자인(화면 방향) | 계획서 없음. 합의한 요구와 비교할 변수를 정한 시안 | 시안과 고른 안·이유 몇 줄 |

## 절차

### 1. 입력 모으기

이슈·대화·사용자가 준 문서에서 먼저 찾고 없는 것만 묻는다. 의도가 흐리면 `grill`로 먼저 캐묻는다. 날짜는
`date`로 확인한다. 프로젝트 메모리 목록에서 같은 종류 작업의 지난 결정(규모·PR 수·머지 주체)을 찾아 읽고
계획에 반영한다.

### 2. 현재 상태 확인

계획이 기대는 코드·자료·화면을 직접 열어 확인하고 출처(`경로:줄`, 커밋, 링크)를 단다. 확인하지 못한 것은
"미확인"으로 적는다. 이미 해결된 일이면 계획서를 쓰지 않고 근거와 함께 알린다.

### 3. 계획서 쓰기

`assets/work-plan.template.md` 형식으로 쓰고 머리말 상태를 `초안`으로 둔다. 방안·검증 수단 칸은 종류마다 다르다.

| 종류 | 방안 | 검증 수단 |
|---|---|---|
| 개발 | 바꿀 곳(파일·모듈 단위)과 PR 단위. 파일별 구현 순서까지 내려가지 않는다 | 돌릴 테스트·명령, 새 테스트가 잡을 결함(되살려 실패하는지 본다), 실제로 무엇을 띄워 무엇을 보는지 |
| 기획 | 정할 것 목록, 각각의 재료(조사·초안·선택지), 누가 정하나 | 결정이 남을 자리(기준 문서·이슈) |
| 연구 | 질문과 출처 범위 | 질문마다 판정선: 무엇이 나오면 무엇을 정하나 |

- 연구의 판정선은 자료를 보기 전에 고정한다. 나중에 바꾸면 변경·결정 로그에 이유와 함께 남긴다.
- 개발이면 머리말에 브랜치명을 적는다. 프로젝트 규칙을 따르고, 없으면 `<fix|feat>/<이슈번호>-<slug>`(이슈가 없으면
  `feat/<slug>`), slug는 영문 소문자·하이픈 40자 이하.
- 사용자가 주지 않은 일정·크기·수치는 지어내지 않는다. `후보:`를 붙이거나 묻는다.

### 4. 합의

승인 뒤에는 이 절에 없는 일로 사용자를 부르지 않으므로 실행 중 사용자가 필요한 것을 모두 여기 모은다.

- 정할 것: 사안마다 배경·선택지·권장안. 고를 재료(초안·시안·조사)가 있어야 하는 결정은 재료를 먼저 만들어 함께
  묻는다. "재료가 나와야 고를 수 있다"는 착수 뒤로 미룰 이유가 아니다.
- 승인: push·PR, 외부 게시·제출처럼 실행 중 필요한 승인. 조건부면 조건까지.
- 준비물: 로그인·실물 기기·측정처럼 사용자 손이 드는 것과, 그것으로 확인할 항목.
- 기한: 있으면 그 안에 들어가는지 한 줄. 안 들어가면 무엇을 줄일지 선택지로 낸다.
- 멈춤 전제: 틀리면 작업 상당 부분이 헛수고가 되는 사실과, 실행 중 무엇을 보면 깨졌다고 보는지. 틀려도 한두 줄만
  바뀌는 것은 적지 않는다.

### 5. 독립 검수 (조건부)

아래 중 하나에 해당할 때만 `plan-reviewer`를 관점을 지정해 한 번 부른다. 그 밖에는 사용자 승인만으로 착수한다.

- 바꿀 파일이 10개를 넘을 것 같다
- 되돌리기 비싼 작업이다(데이터 이전·삭제, 외부 공개·출시)
- 연구 계획의 판정선

관점은 하나를 고른다. 기획·연구면 기획, 화면을 바꾸면 디자인, 그 밖의 개발이면 코드다. 프롬프트에는 계획서
절대경로, 관점, 사용자 요청 원문, 코드베이스 절대경로와 HEAD(코드와 대조할 때), 디자인 관점이면 시안·스크린샷 경로,
도구 호출 상한(기본 15회)만 넣고, 왜 그렇게 썼는지는
넣지 않는다. 보고의 "읽은 것"에 계획서가 없으면 그 보고는 버린다. Blocker는 고치고, 사용자가 정할 문제는 정할
것에 올린다.

`plan-reviewer`를 이름으로 부를 수 없는 하네스에서는 이 스킬 폴더 기준 `../../agents/plan-reviewer.md`의 머리말을
뺀 본문을 서브에이전트 지시로 넘긴다. 서브에이전트 도구가 없으면 같은 관점으로 직접 보고, 보고 첫 줄에 "독립 검수
미실행 — <없던 도구>"를 밝힌다.

### 6. 승인

아래 보고를 하고 "이 계획대로 진행할까요?"를 명시적으로 묻는다. 승인되면 머리말을 `상태: 승인됨 (YYYY-MM-DD)`로
바꿔 저장한다. 개발은 `implement`로 넘긴다.

## 저장 위치

프로젝트 지침(`CLAUDE.md`·`AGENTS.md` 등)이 정한 작업 폴더에 둔다. 없으면 그 프로젝트에서 처음 쓸 때 한 번 묻고,
받은 위치를 프로젝트 지침에 한 줄로 적어 이후로는 묻지 않는다. 계획서에는 로컬 경로와 내부 판단이 들어가므로 팀이
보는 코드 레포 안은 제안하지 않는다. 파일명은 작업 폴더 안 `계획.md`, 작업 폴더가 없으면
`YYYY-MM-DD_<주제>_계획.md`.

## 보고

대화에는 저장 위치, 정할 것(서로 기대지 않는 사안은 번호를 붙여 한 번에), 승인·준비물·멈춤 전제, 검수를 돌렸으면
그 결과만 적는다.

## 행동 원칙

- 계획서를 쓰는 동안 코드를 바꾸지 않는다. 결정 재료(조사·초안·시안)를 만드는 것만 예외다.
- 진행 상황은 계획서에 쌓지 않는다. 진행은 작업 목록과 커밋이, 결과는 PR 본문·보고서가 맡는다. 결정이 바뀌면
  `변경·결정 로그`에 한 줄 더한다.
- 승인 뒤 범위·완료 기준이 바뀌면 상태를 `초안`으로 되돌리고 다시 승인받는다.
