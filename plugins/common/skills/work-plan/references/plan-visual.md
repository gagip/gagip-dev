# 계획 시각 자료

승인할 사람이 글을 읽지 않고도 "무엇이 어떻게 바뀌고, 무엇을 골라야 하는지"를 눈으로 보고 정하게 하는 HTML 한 장이다. 계획서(md)는 그대로 두고, 이 파일은 계획서 옆에 둔다.

## 언제 만드나

- 화면·문구·사용자에게 보이는 동작이 바뀐다
- 결정이 필요한 것이 있고, 선택지마다 결과가 달라진다(화면, 비용·시간 같은 수치, 흐름)
- 사용자가 요청했다

내부 리팩터·한 줄 수정처럼 보여 줄 결과가 없으면 만들지 않는다.

## 구성 — 위에서 아래로

1. 머리: 무엇을 바꾸는 계획인지 제목과 1~2문장, 새로 생기는 부분 표시가 무엇인지 범례 한 줄. 예시 데이터를 쓰면 무엇을 가정했는지 함께 적는다.
2. 기능 묶음: 바뀌는 기능마다 묶음 하나를 둔다. 묶음 머리에 기능 이름과 "지금은 어떤지" 한 줄을 쓰고, 그 아래에 그 기능을 사용자가 겪는 상태별 화면(처음 진입, 진행 중, 경계 상황, 결과, 새로 뜨는 창 중 해당하는 것)을 가로로 나란히 둔다. 실제 기기 폭으로 그리고, 화면마다 위에 번호 붙은 제목과 "무엇이 새로·달라졌는지" 한 줄 설명을 단다. 여러 기능을 한 줄에 섞으면 승인할 사람이 무엇이 왜 바뀌는지 따라가기 어렵고, 기능별로 훑어야 빠진 상태를 알아챈다.
3. 지금 모습: 기존 화면의 같은 자리가 크게 바뀌면 그 묶음 맨 왼쪽에 지금 모습 한 칸을 둔다. 새로 생기는 화면이면 두지 않는다.
4. 결정이 필요한 것: 계획서 "결정이 필요한 것" 표의 줄마다 칸 하나를 두고, 선택지별로 고르면 어떻게 되는지(예상 결과)를 나란히 보여 준다. 무엇으로 보여 줄지는 표의 "보여 줄 방식"을 따른다. 화면이 달라지면 같은 예시 데이터로 그린 화면을, 비용·시간·용량이 달라지면 같은 가정으로 계산한 수치나 막대를, 동작 순서가 달라지면 흐름 그림을 쓴다. 선택지 카드마다 그림을 하나씩 넣고, 그 아래에 얻는 것과 잃는 것을 한 줄씩 적고, 권장안에 표시를 단다. 위 기능 묶음에 이미 그린 화면이어도 "위 ② 참고"로 넘기지 말고 이 칸에 다시 둔다. 글로만 적거나 위를 가리키면 승인할 사람이 결과를 머릿속으로 그려 보거나 스크롤을 오가야 해서, 고르기 어렵고 잘못 고르기 쉽다. 칸 제목은 계획서와 같은 "결정이 필요한 것"으로 쓴다.
5. 이번에 하지 않는 것. 흐리게 처리하고 뺀 이유를 한 줄로 쓴다.

## 만드는 법

- 프로젝트의 실제 색·크기 값을 가져온다. 스타일 파일의 CSS 변수(`--이름: 값`)를 같은 이름과 값으로 옮겨 쓰고, 어두운 테마 값이 있으면 같이 옮긴다. 비슷한 색을 새로 고르면 승인한 모습과 구현 결과가 어긋난다.
- 화면은 그림을 따로 그리지 않는다. 앱의 실제 부품 스타일과 계산 로직을 가져와 예시 데이터로 실제로 계산해 그린다. 그래야 숫자와 규칙이 계획과 어긋나지 않는다.
- 새로 생기는 부분은 앱 색과 겹치지 않는 색의 점선 테두리로 표시하고, 위쪽에 이 표시를 켜고 끄는 토글을 둔다.
- 외부 의존 없이 HTML 한 파일로 열리게 한다(CDN 스크립트·웹폰트를 쓰지 않는다). 지금 화면 캡처는 base64로 넣는다.
- 움직임이 있으면 재생하고, "다시 보기" 단추를 둔다.
- 문구는 계획서에 적은 원문과 같게 쓴다. 쉬운 한국어로 쓰고, 섹션 번호 대신 무엇을 정하는지로 부른다.

## 확인과 전달

- 브라우저로 열어 스크린샷을 찍고 직접 본다(깨짐, 겹침, 이미지 누락, 계산 결과). 확인하지 않은 시안을 보내면 승인할 사람이 오류를 대신 찾게 된다.
- 계획서 머리에 이 파일 경로를 한 줄로 적는다.
- 파일 보내기 도구로 대화에 렌더해 띄우고(`display: render`), 대화에는 화면마다 무엇을 볼지 한 줄씩과 결정이 필요한 것만 적은 뒤 "이대로 구현할까요?"를 묻는다. 승인 전에는 코드를 바꾸지 않는다.
