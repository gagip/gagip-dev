# 플랜 검토 기준

work-plan이 쓴 문서를 맥락 없이 검토할 때 쓴다. 스킬을 개발할 때의 품질 채점과, 실제 사용 때의 검수가 같은
기준을 쓴다.

## 검토자에게 주는 지시

- 플랜 문서와, 받았다면 설계·문제 정의 문서만 읽고 판정한다. 문서를 쓴 대화의 맥락은 받지 않는다.
- 항목마다 `통과` / `미통과` / `판정 불가` / `해당 없음`을 매기고, 근거로 문서의 해당 줄을 인용한다.
- `미통과`는 무엇을 어떻게 고치면 통과하는지 한 줄로 적는다.
- 사용자가 정할 문제(`후보:`로 남은 칸, 사용자가 정할 것)는 문서 결함이 아니다. `판정 불가`로 두고 "사용자 확인
  필요"라고 적는다.
- 기한이 "없음"이면 기한·일정 항목(9·10)은 `해당 없음`으로 둔다. 설계나 문제 정의가 `생략`이면 그 문서와의
  정합성 항목(1·2)은 해당 부분만 `해당 없음`으로 둔다.
- 파일을 고치지 않는다.

## 기준

### 세 문서의 정합성

| # | 기준 | 미통과 예 |
|---|---|---|
| 1 | 작업이 가리키는 설계 결정·KR이 그 작업으로 실제로 이뤄진다. 설계 결정마다 이루는 작업이 있거나 미루는 작업에 이유와 함께 있다 | "문구 리소스로 옮기기" 작업이 로그 전송 결정(D3)을 가리킴 |
| 2 | 문제 정의·설계의 내용을 다시 쓰지 않고 가리킨다. 설계에 없는 새 설계 판단(구조·인터페이스 선택)을 작업 안에서 몰래 정하지 않는다 | 작업 문장에 "캐시는 Redis로" 같은 설계에 없는 결정이 들어 있음 |

### 작업

| # | 기준 | 미통과 예 |
|---|---|---|
| 3 | 담당 표시가 일의 성격과 맞다 | 범위 결정을 `에이전트`로, 코드 점검을 `사람`으로 표시 |
| 4 | 앞 단계가 실제 선후 관계와 맞고, 불필요한 앞 단계로 병렬 가능한 일을 막지 않는다. 축소안을 골라도 앞 단계가 막지 않는다 | 빌드가 구현보다 앞섬, 독립 조사에 앞 단계를 붙임 |
| 5 | 병렬이 안 되는 자원을 찾고 대응을 적었다. 그런 자원이 없으면 `해당 없음` | 실물 한 대에 동시 작업을 가정 |
| 6 | 작업 항목이 끝났는지 판정할 수 있는 문장이다 | "정리하기", "개선하기" |
| 7 | 미루는 작업마다 이유가, 리스크마다 대응이 있다 | 미루는 목록만 있고 이유 없음 |

### 검증

| # | 기준 | 미통과 예 |
|---|---|---|
| 8 | 문제 정의의 KR마다 확인 방법·예상 관찰·해석이 있고, 확인 방법이 그 KR의 판정 기준을 실제로 잰다. 실행 확인은 무엇을 띄워 무엇을 보는지 구체적이다 | "테스트한다"뿐, 판정 기준은 "문구가 뜬다"인데 확인은 단위 테스트 통과 여부만 봄 |

### 일정과 기한

| # | 기준 | 미통과 예 |
|---|---|---|
| 9 | 목표마다 기한 판정이 있고, 근거가 사람 몫 크기·쓸 수 있는 칸·앞 단계 사슬에서 나온다. 안 들어가면 축소안이 있다 | 근거 없이 모두 "들어감" |
| 10 | 날짜표에 사람 몫만 있고, 고정 일정·다른 사람의 부재와 겹치지 않으며, 몰리는 날을 짚었다 | 에이전트 작업에 날짜를 배정, 회의 시간에 설계 작업, 리뷰어 휴가일에 리뷰 배치 |

### 지어내지 않기

| # | 기준 | 미통과 예 |
|---|---|---|
| 11 | 사용자가 주지 않은 일정·크기·부재·전제를 지어내지 않았다. 요청에 없는 값은 칸마다 `후보:`가 붙었거나 질문으로 올라갔다 | 사용자가 말하지 않은 리뷰어 일정을 확정처럼 씀, 특정 스토어·플랫폼으로 단정 |

## 출력 형식

```
검토 대상: <경로>
통과 N / 미통과 N / 판정 불가 N / 해당 없음 N

| # | 판정 | 근거(인용) | 고칠 것 |
|---|---|---|---|
```
