# 작업 구현

합의를 끝낸 코드 작업을 끝까지 실행한다. 진행은 작업 목록과 커밋으로 보이고, 결과는 PR 본문과 최종 보고에 남긴다.
단계마다 기록 파일을 만들지 않는다. 구현 방법은 대상 레포의 `CLAUDE.md`/`AGENTS.md`를 따르고, 레포 관례가 다루지
않는 코드 판단(계약·실패 표현·공개 범위·시그니처·함수 분리)은 플러그인의 `references/coding-philosophy.md`(이 스킬
폴더 기준 `../../references/coding-philosophy.md`)를 따른다.

## 시작 조건

승인된 계획서(`work-plan`, 머리말 `상태: 승인됨`)가 있으면 그것이 기준이다. 없으면 바로 착수해도 되는지 본다. 아래 중
하나라도 해당하면 코드를 건드리지 않고 `work-plan`부터 연다.

- 요청을 둘 이상으로 읽을 수 있거나, 구현 방법에 사용자가 고를 선택지가 있다
- 사용자에게 보이는 동작·문구가 요청에 적힌 것과 다르게 바뀌거나, 기능·문구·데이터를 지운다
- API·저장 형식·설정 키처럼 밖과의 약속을 새로 고르거나 바꾼다
- 되돌리려면 커밋 되돌리기 한 번으로 끝나지 않는다(데이터 이관·배포 순서 등)

해당 없으면 바로 착수하고, 최종 보고에 "계획서 없이 진행 — 착수 기준 해당 없음"을 남긴다.

착수 전에 계획서·이슈를 실제 코드와 대조한다. 주석·변수명이 아니라 실제 문자열·값·동작을 본다. 이미 해결됐거나,
없는 파일·심볼을 전제하거나, 계획서의 준비물이 아직 없으면 근거를 보이고 멈춘다. 이슈는 대상 레포 안에서
`gh issue view <번호> --json title,body,labels,number`로 읽는다(`repository` 필드는 gh 버전에 따라 실패한다).
같은 작업의 브랜치·워크트리가 이미 있는지 `git worktree list`·`git branch --list`로 보고, 있으면 이어간다.

## 진행 순서

아래 순서를 작업 목록에 올리고 하나씩 끝낸다. 작업 목록 도구가 없으면 대화에 체크리스트로 둔다.

1. **브랜치·작업 위치** — 프로젝트 규칙을 따른다. 없으면 브랜치명은 `<타입>/<이슈번호>-<요약>`(타입은 `fix`·`feat`·
   `docs`·`test`·`chore`·`refactor`, 요약은 영문 소문자 kebab-case 3~5단어). 작업 위치는 레포의 워크트리 생성
   스크립트가 있으면 그것, 없으면 `git worktree add`(추적 제외 설정 파일은 따로 복사해야 할 수 있다고 최종 보고에
   남긴다). 레포 지침이 main 직접 작업을 정했으면 그대로 한다. 어느 쪽이든 첫 변경 전 `git rev-parse HEAD`를 base로
   적어 둔다. 아래 리뷰 범위·커밋 정리·이어받기가 모두 이 base를 기준으로 한다.
2. **구현** — 작은 동작 단위로 구현 → 그 변경에 맞는 검증 → 커밋을 반복한다. 새 공개 함수는 `coding-philosophy.md`
   12장의 네 가지를 스스로 확인한다. 새 테스트·가드는 고친 결함을 되살려 실패하는지 보고 되돌린다.
3. **정리** — `simplify` 스킬로 재사용·단순화·효율을 정리한다. 없으면 읽기 전용 서브에이전트에 diff를 주고 같은
   관점으로 검토받는다.
4. **코드 리뷰** — [code-review-criteria.md](references/code-review-criteria.md)대로 관점별 서브에이전트를 한 응답에서
   병렬로 띄운다. 범위는 `git diff <base>...HEAD`, `git diff HEAD`, `git ls-files --others --exclude-standard`를 합친
   것이다. 무엇을 고칠지는 기준 문서가 정한다. 고친 지적은 검증해 커밋하고, 반영하지 않은 지적은 최종 보고에 남긴다.
5. **문서 영향** — 이 변경으로 틀리게 된 레포 안 문서(README·지침·`docs/`)를 같은 브랜치에서 고친다. 레포 밖 문서는
   목록으로 최종 보고에 남긴다.
6. **커밋 정리** — 앞 커밋을 다시 고친 커밋(정리·리뷰 반영·문서 수정)은 원 커밋에 합친다. 후속 커밋은 처음부터
   `git commit --fixup=<대상>`으로 만들고 `GIT_SEQUENCE_EDITOR=true git rebase -i --autosquash <base>`로 합친다.
   합치기 전 HEAD에 백업 브랜치를 만들고, 합친 뒤 `git diff <백업> HEAD`가 비었는지와 작성자가 그대로인지 본다. 확인되면 백업 브랜치를 지우고 그
   해시를 최종 보고에 적는다. 충돌하면
   `git rebase --abort`하고 정리를 생략한다. 브랜치가 이미 원격에 있으면 강제 push 승인 없이는 합치지 않는다.
7. **제출** — [verification.md](references/verification.md)대로 최종 코드의 완료 조건별 증거를 확인한다.
   실패·미실행·미확인이 남으면 전체 달성으로 보고하지 않는다. 계획서의 착수 전 합의나 사용자 지시에 push·PR 승인이 있을 때만 push하고, 프로젝트·전역 지침이 정한 PR
   스킬(없으면 `create-pr`)로 PR을 만든다. 승인이 없으면 커밋까지 하고 끝낸다. PR 머지는 하지 않는다.

검증은 [verification.md](references/verification.md)의 독립 도구로 실행·기록한다. 계획서·이슈의 조건을
그대로 사용하고 별도 상태 문서를 만들지 않는다. 저장소 밖 작업 폴더의 실행 로그만 남긴다.

## 커밋 규칙

- 매 커밋 전에 그 변경에 맞는 타입 검사·테스트·실행을 실제로 돌린다. 못 돌렸으면 이유와 함께 "미검증"으로 남긴다.
- 매 커밋 직전 `pwd`·`git rev-parse --show-toplevel`·`git branch --show-current`로 작업 위치를 확인한다.
- 작성자는 대상 레포의 git 설정을 그대로 쓴다. `--author`·`GIT_AUTHOR_*`로 덮지 않고, 서브에이전트에 커밋을 맡기면
  이 규칙을 지시에 적는다.
- `--no-verify`로 훅을 우회하지 않는다. 포맷 검사 실패는 레포의 포맷 명령으로 고친다.
- 커밋 스킬은 프로젝트·전역 지침이 정한 것, 없으면 `commit`을 쓴다. 변경 없는 점검에 빈 커밋을 만들지 않는다.

## 멈추는 곳

착수 뒤에는 멈추지 않고, 묻지도 경과를 보고하지도 않는다. 합의에 없던 판단은 목표·범위 안이면 직접 정하고 최종
보고의 "합의와 달라진 점"에 남긴다. 계획서가 있으면 본문은 고치지 않고 `변경·결정 로그`에 한 줄 더한다.

예외는 다음뿐이다: 계획서의 멈춤 전제가 깨졌을 때(깨졌다고 본 관찰을 근거로 보인다), 목표를 이룰 수 없을 때, 범위
밖을 건드려야 할 때, 필요한 도구·권한이 없을 때.

## 이어받기 메모

세션이 끊겨도 다른 세션이 이어받을 수 있게 메모 하나를 단계를 끝낼 때마다 갱신한다. 담을 것: 레포·브랜치·base·HEAD,
끝낸 단계와 남은 단계, 막힌 것, 합의와 달라진 점.

- 프로젝트나 상시 지침이 세션 기록 문서를 정했으면 그 문서에 쓰고 따로 만들지 않는다.
- 없으면 계획서 옆에 `handoff.md`로 둔다. 계획서가 코드 레포 안에 있거나 없으면 프로젝트 지침이 정한 작업 폴더에
  둔다. 팀이 보는 코드 레포 안에는 두지 않는다. 둘 곳이 없으면 착수 전에 한 번 물어 프로젝트 지침에 적는다.
- 계획서 없이 바로 착수한 작은 작업은 메모를 만들지 않고 최종 보고로 대신한다.
- "작업 이어서 해줘"면 이 메모와 `git log <base>..HEAD`로 남은 단계부터 이어간다.

## 최종 보고

바뀐 동작 · 핵심 결정 · 확인한 것 · 남은 한계를 먼저 짧게 설명한다. 구체적인 이전/이후와 이유를
실제 코드·검증 증거에 맞춰 쓰고, 설명을 생성했다는 이유로 사용자 이해가 완료됐다고 기록하지 않는다.
완료 보고 전에도 verification.md의 `check`로 모든 완료 조건을 확인한다.

작업 위치(레포·브랜치) · 커밋 목록 · 검증 결과(무엇을 돌려 어떻게 나왔는지, 못 한 것은 "미검증") · 반영하지 않은 리뷰
지적 · 문서 영향 · 합의와 달라진 점 · 제출 여부(PR URL). PR을 만들었으면 같은 내용을 PR 본문에 싣는다.
