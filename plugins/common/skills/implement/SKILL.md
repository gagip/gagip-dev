# 작업 구현

앞 단계에서 합의를 끝낸 작업을 끝까지 실행한다. 흐름은 problem-definition(문제 정의) →
solution-design(설계) → work-plan(플랜 저장·승인) → implement이고, 요구사항이 흐리면 어느 단계에서든
grill로 캐묻는다. 상태·순서는 `cycle.py`, 단계 검증은 `gate.py`,
실제 구현 방법은 대상 레포의 `CLAUDE.md`/`AGENTS.md`가 담당한다. `handoff.md`는 상태 기록이며
실행 권한의 증거가 아니다.

스크립트는 이 스킬 디렉터리의 `scripts/`에 있다. 아래 명령의 `scripts/cycle.py`는 이 스킬
디렉터리 기준 경로이고, 설치 캐시에서 실행해도 된다.

## 시작 조건

다음 둘 중 하나가 있어야 시작한다. 없으면 코드를 건드리지 않고 앞 단계 스킬부터 연다.

1. **승인된 계획서** — work-plan으로 승인받은 플랜 문서(머리말 `상태: 승인됨`. 디자인 인계 명세도
   인정). 사이클 머리말 `plan:`에 그 파일의 절대경로를 적는다. 문서 도구에 저장한 플랜이면 사이클
   폴더에 마크다운으로 내보내 그 경로를 적는다.
2. **작은 작업 판정** — 계획서 없이 가도 되는지 5개 항목을 판정해 모두 `아니오`인 경우.
   판정 표 형식은 [작업 접수](references/intake.md)에 있다. 하나라도 `예`면 work-plan부터.

## 사이클 위치

사이클 폴더는 프로젝트 지침이 정한 곳에만 만든다. 지침에 위치가 없으면 그 프로젝트에서 처음 쓸 때
작업 시작 전에 사용자에게 한 번 묻고, 받은 위치를 그 프로젝트 지침에 적어 이후로는 묻지 않는다.
사이클에는 로컬 경로와 내부 판단이 들어가므로 팀이 보는 코드 레포 안은 제안하지 않는다.

- 새 작업: `python3 scripts/cycle.py <위치>/<YYYY-MM-DD_주제> init --title "<한 줄 제목>" [--plan <계획서 경로>]`
- 기존 작업: `<위치>/<주제>/handoff.md`를 찾아 이어간다.
- 같은 작업의 기존 사이클·브랜치가 있으면 중복 생성하지 않는다. 대상 레포에서
  `git worktree list`와 `git branch --list`로 확인한다.

프로젝트 지침이 implement 추가 단계(맥락 수집, 도메인 검수, 커밋·PR 스킬, 브랜치 관행 등)를 정하면
해당 단계에서 그대로 따른다.

## 상태 머신으로 실행

### 1. 조회한다

```bash
python3 scripts/cycle.py <사이클 폴더> status
```

명령은 진행 순서와 완료된 단계의 실제 상태를 다시 검사한다. 현재 단계가 ship·close이면
커밋 작성자와 미커밋 변경도 검사한다. 실패하면 원인을 고친 뒤 재조회한다. 실패 출력이 있는데
다음 단계로 진행하지 않는다. 종결 상태면 실행을 끝낸다. `gate.py --stage`는 개별 관문의 읽기 전용
진단일 뿐, 단계 완료나 다음 단계 실행 승인이 아니다.

### 2. 현재 단계의 절차만 읽고 수행한다

| 현재 단계 | 읽을 절차 |
|---|---|
| intake | [작업 접수](references/intake.md) |
| branch·implement·simplify·review·docs·ship | [실행 절차](references/execution.md)의 공통 원칙과 해당 단계 절 |
| close | 아래 종결 절차 |

커밋은 별도 단계가 아니다. 구현·정리·리뷰 수정·문서 작업에서 작은 변경마다 검증하고 커밋한다.
산출물 파일명: `00_intake.md` · `01_branch.md` · `02_implement.md` · `03_simplify.md` ·
`04_review.md` · `05_docs.md` · `07_ship.md` · `08_close.md`.

### 3. 검증 후 완료를 기록한다

산출물을 작성한 뒤 다음 명령을 실행한다. 진행 표·종결값·결정 로그를 먼저 완료로 고치지 않는다.

```bash
python3 scripts/cycle.py <사이클 폴더> complete intake --artifact 00_intake.md --decision "작업 범위와 검증 조건을 계획서·코드와 대조해 확정"
```

`--decision`에는 무엇을·왜·누가 정했는지 한 줄을 적는다. 명령은 현재 미완 단계만 받아 선행 관문과
현재 관문을 확인하고, 성공한 경우에만 상태와 로그를 함께 저장한다. 실패하면 파일을 바꾸지 않는다.
계획서 파일이 실제로 있는지는 intake를 완료로 바꾸는 이 순간에만 확인한다.

CLI끼리의 동시 저장은 잠금으로 막는다. 같은 사이클을 동시에 수동 편집하지 않는다.

## 멈추는 곳

- **시작 전** — 계획서와 실제 코드가 어긋나거나, 이미 해결된 작업이면 근거를 보이고 멈춘다.
- **시작 뒤에는 멈추지 않는다.** 합의에 없던 판단은 목표·범위 안이면 직접 정하고, 사이클 결정 로그
  (`--decision`)와 `08_close.md`의 `## 합의와 달라진 점`에 남긴다.
- 예외는 둘뿐이다: 계획의 목표를 이룰 수 없을 때, 플랜이 미루거나 문제 정의가 범위 밖으로 둔 것을 건드려야 할 때. 필요한 도구·
  권한이 없을 때도 여기에 든다.

## 제출 모드

기본은 초안(`draft`)이다. `mode`가 없어도 초안으로 읽는다. 사용자가 리터럴 `--auto`를 명시한
경우에만 자동 모드를 기록한다. 자연어 "자동으로 해줘"는 자동 모드 요청으로 해석하지 않는다.

```bash
python3 scripts/cycle.py <사이클 폴더> mode auto --decision "사용자가 --auto로 push·PR까지 요청"
```

초안의 현재 단계가 ship이면 push·PR을 수행하지 않고 생략을 기록한 뒤 close로 간다. PR 머지는
이 절차가 하지 않는다.

```bash
python3 scripts/cycle.py <사이클 폴더> skip ship --decision "초안 모드이므로 원격 제출 생략"
```

## 종결

`08_close.md`에 두 절을 쓴다.

- `## 종결` — intake의 검증 조건 각각의 결과와 종결값(`달성`). 충족하지 못했으면 달성으로 닫지 않는다.
- `## 합의와 달라진 점` — 계획서·판정과 다르게 직접 정한 것. 없으면 "없음".

```bash
python3 scripts/cycle.py <사이클 폴더> complete close --artifact 08_close.md --decision "검증 조건 충족으로 종결"
```

사용자가 작업이 불가능하다고 판단한 경우에만 `stop --decision "<사유>"`로 종결한다. stop은 미완
단계를 완료·생략으로 바꾸지 않는다.
