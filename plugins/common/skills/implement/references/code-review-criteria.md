# 코드 리뷰 기준

`implement`의 코드 리뷰 단계는 아래 관점마다 맥락을 모르는 읽기 전용 서브에이전트를 **한 응답에서 병렬로** 띄워 판정한다. 메인 세션은 지시서를 만들고, 돌아온 보고를 대조·재확인해 판정한다. 서브에이전트를 쓸 수 있으면 메인 세션이 직접 diff를 판정하지 않는다(쓸 수 없을 때는 3절 마지막 항목).

## 1. 레포 정본 탐색 (최우선)

diff 대상 레포에서 다음을 이 순서로 찾는다. 찾으면 **그 문서의 어휘·규칙을 그대로** 판정 기준으로 쓴다 — 이 문서의 폴백 어휘(require/check/assert 등)로 바꿔 부르지 않는다.

1. `CLAUDE.local.md`/`CLAUDE.md`/`AGENTS.md`가 "코딩 지침"·"계약"이라는 이름으로 가리키는 문서 (예: `docs/coding-guidelines.md`)
2. 계약 검증 헬퍼를 정의한 소스 파일 — 보통 `shared/lib/contract.ts` 류 경로, 파일 최상단 주석에 "SSOT"·"정의"라고 스스로 밝힌 파일 (예: 공개 계약 검사와 내부 불변식 검사를 나눠 둔 `contract` 모듈)
3. 레포 루트의 `DESIGN.md` (UI 코드 리뷰 시 — 토큰·컴포넌트 규칙)

1·2가 없으면 플러그인의 `references/coding-philosophy.md`(이 스킬 폴더 기준 `../../references/coding-philosophy.md`)를
폴백 정본으로 넘긴다. 관점별로 짚을 장: 정확성·계약은 1·2·4·5·8·9·12장, 가독성·명확성은 3·7·9·13장,
최소 변경은 8·13장, 테스트는 6·10·11장. 레포 정본이 있어도 그 정본이 다루지 않는 항목은 이 문서로 판정한다.

찾은 정본 경로는 모든 관점 에이전트에 판정 기준으로 넘긴다. 정본 문서가 예외·비직관적 결정을 설명해 두었으면(예: 특정 검사를 디버그 빌드에서만 켜는 이유) 그 근거까지 읽으라고 지시한다.

## 2. 관점 (관점 하나에 서브에이전트 하나)

| 관점 | 보는 것 | 🔴로 올리는 경우 |
|---|---|---|
| 정확성·계약 | 레포 정본이 있으면 그 규칙으로, 없으면 폴백 계약 프로그래밍(아래)으로 export 함수·공개 API를 판정한다. 밖으로 내놓는 것(export 함수·타입·컴포넌트 props·API 응답 형태)을 먼저 본다. 로직 오류, 경계값, 실패 처리, 경쟁 상태 | 정확성·계약 위반, 데이터 손상 위험 |
| 가독성·명확성 | 이름이 하는 일을 드러내는가, 함수 길이·분기 구조, 이름 없는 숫자, 주석이 "왜"만 담는가(코드 재서술·경위 주석), 주변 코드 관례(명명·파일 배치·스타일)와 어긋남, 관심사가 섞이거나 불필요한 결합·추상화를 새로 만들었는가 | 이름·구조가 동작을 잘못 알려 오용을 부를 때만. 나머지는 🟡 |
| 최소 변경 | 요청에 없는 기능·파일·스크립트·가드·호환 코드, 쓰이지 않거나 없어도 되는 변수·함수·export·타입·분기, 한 번만 쓰는 추상화, "나중에 필요할 수도 있어서" 만든 확장 지점, 기존 코드·이미 깔린 의존성으로 대체할 수 있는 새 코드, 변경과 관련 없는 파일 수정. 제안마다 "빼도 요청이 지켜지는 이유"를 한 줄로 댄다. 입력 검증·유실 방지 실패 처리·보안처럼 깎으면 안 되는 것은 대상이 아니다 | 없어도 깨지는 것이 없는 추가물. 빼면 반영, 남길 이유가 있으면 🟡로 내리고 이유를 최종 보고에 한 줄로 댄다 |
| 테스트 | 새·바뀐 테스트가 이름대로 검증하는가, 결함을 되살리면 실패하는가(약한 단언), 빠진 경계·실패 경우, 테스트 사이 상태 공유. 테스트가 없는 변경 코드에 필요한 테스트와 수준(단위/E2E). 레포의 기존 E2E 체계로 추가할 최소 시나리오. 이 변경이 기존 테스트를 깨는지 | 되살릴 수 있는 옛 결함(버그 수정·재발 방지 가드·새 방어 코드)에 회귀 테스트가 없음, 기존 테스트를 깨뜨림. 나머지는 🟡 |
| 사용자 노출 문구 (조건부) | 아래 절 | 검수 에이전트가 위험으로 판정한 문구 |

**폴백 계약 프로그래밍** (레포 정본이 없을 때): 판단 기준은 신뢰 여부가 아니라 **프로세스 경계 여부**다. 같은 프로세스 내부 호출은 잘못된 값이 호출자 버그이므로 즉시 실패(require류)해야 하고, 네트워크·파일·OS API처럼 프로세스 경계를 넘는 곳은 예외 대신 결과 타입으로 반환해 호출자가 복구하게 해야 한다.

**사용자 노출 문구**: 이 변경이 사용자에게 보일 문장을 추가·수정했고 프로젝트 지침이 문구 검수 에이전트(규제·법무·브랜드 등)를 정했으면, 그 문자열만 `파일:라인`과 원문으로 모아 그 에이전트에 넘긴다. 시안 단계에서 검수를 거친 문구도 다시 넘긴다. 문구를 건드리지 않았거나 검수 에이전트가 없으면 이 관점은 띄우지 않는다.

## 3. 지시서 공통

- **넘긴다**: 대상 레포 절대경로, base, HEAD, 변경 파일 목록(`git diff <base>...HEAD --name-only`와 미커밋·새 파일), 찾은 레포 정본 경로, 그 관점의 "보는 것"과 "🔴로 올리는 경우". 최소 변경 관점에는 요청 원문(계획서가 있으면 `목표와 완료 기준`·`할 일` 절, 없으면 이슈나 사용자 요청 한 줄)도 넘긴다.
- **넘기지 않는다**: 왜 그렇게 만들었는지(설계 이유·경위·이전 판단).
- **제약**: 읽기 전용(파일 편집·git 상태 변경 금지), 빌드·테스트·서버 실행 금지(실행해야 알 수 있는 것은 "실행 확인 필요"로 표시), 도구 호출 상한, 넘을 것 같으면 부분 결과 반환, 변경 파일 목록 밖 결함은 보고하지 않음(관례 비교를 위한 읽기는 허용, 테스트 관점의 기존 테스트 파손은 보고 대상), 지적이 없으면 "지적 없음" 명시.
- **보고 형식**: 첫머리에 실제로 확인한 HEAD(`git rev-parse HEAD` 결과)와 읽은 파일 목록, 이어서 지적마다 등급 후보 · `파일:줄` · 문제 · 수정안(코드 발췌).
- 서브에이전트를 쓸 수 없는 환경이면 같은 관점으로 직접 보고, 판정에 **"독립 검수 미실행"을 밝힌다**.

검증 기록은 조건·명령·관찰이 실제 요구 동작을 확인하는지도 본다. 종료 코드만으로 충분하지 않다.
변경 설명이 있으면 동작·실패 처리·한계가 실제 코드와 같은지 대조하고, 증거 없는 주장은 확인 필요로 남긴다.

## 4. 보고 대조와 판정

1. 보고가 밝힌 HEAD가 지시한 HEAD와 다르면 그 보고를 버리고 그 관점을 다시 띄운다.
2. 지적마다 관련성부터 본다: 변경 범위 안인가, 이미 사용자와 정한 사항과 겹치는가. 겹치면 🟡로 두고 최종 보고의 반영하지 않은 지적에 `기존 결정: <근거>`로 적는다.
3. 🔴 후보는 메인 세션이 코드를 직접 다시 읽어 확인한다. 코드가 보고와 다르면 등급을 내리고 반박 근거를 적는다.
4. 발견을 🔴(위 표의 "🔴로 올리는 경우") / 🟡(그 밖의 스타일·취향·개선) 로만 나눈다. **🔴만 고치고 진행한다** — 🟡는 최종 보고에 "발견했으나 반영 안 함"으로 한 줄만 남기고 커밋을 막지 않는다.
