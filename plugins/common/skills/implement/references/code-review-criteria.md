# 코드 리뷰 라우터

`implement`의 `review` 단계가 무엇을 기준으로 diff를 판정할지 정한다. 새 기준을 여기서 상세 정의하지 않는다 — **레포에 이미 있는 정본을 최우선으로 따르고**, 없을 때만 아래 폴백을 쓴다.

## 1. 레포 정본 탐색 (최우선)

diff 대상 레포에서 다음을 이 순서로 찾는다. 찾으면 **그 문서의 어휘·규칙을 그대로** 판정 기준으로 쓴다 — 이 문서의 폴백 어휘(require/check/assert 등)로 바꿔 부르지 않는다.

1. `CLAUDE.local.md`/`CLAUDE.md`/`AGENTS.md`가 "코딩 지침"·"계약"이라는 이름으로 가리키는 문서 (예: `docs/coding-guidelines.md`)
2. 계약 검증 헬퍼를 정의한 소스 파일 — 보통 `shared/lib/contract.ts` 류 경로, 파일 최상단 주석에 "SSOT"·"정의"라고 스스로 밝힌 파일 (예: 공개 계약 검사와 내부 불변식 검사를 나눠 둔 `contract` 모듈)
3. 레포 루트의 `DESIGN.md` (UI 코드 리뷰 시 — 토큰·컴포넌트 규칙)

**정본을 찾았으면** 그 문서가 정의한 개념으로 diff의 공개(export) 로직을 판정한다. 예: 그런 레포에서는 "require/check"가 아니라 "이 export 함수가 인자를 `ensure()`로 검증하는가(공개 계약) / 내부 사후조건을 `invariant()`로 검증하는가(구현자 책임)"로 묻는다. 정본 문서가 예외·비직관적 결정을 설명해 두었으면(예: 특정 검사를 디버그 빌드에서만 켜는 이유) 그 근거까지 읽고 리뷰에 반영한다 — 근거를 모르고 "다른 플래그를 쓰라"는 식의 틀린 지적을 하지 않는다.

## 2. 폴백 (레포 정본이 없을 때만)

① **계약 프로그래밍** — 이 export 함수/공개 API가 사전조건·사후조건을 검증하는가. 판단 기준은 신뢰 여부가 아니라 **프로세스 경계 여부**: 같은 프로세스 내부 호출은 잘못된 값이 호출자 버그이므로 즉시 실패(require류)해야 하고, 네트워크·파일·OS API처럼 프로세스 경계를 넘는 곳은 예외 대신 결과 타입으로 반환해 호출자가 복구하게 해야 한다.

② **공개 인터페이스 중심** — diff 전체를 훑기보다, 이 변경이 **밖으로 내놓는 것**(export되는 함수·타입·컴포넌트 props·API 응답 형태)에 우선 집중한다. 내부 전용 로직의 사소한 스타일은 넘어간다.

③ **모듈화** — 관심사가 섞이지 않았는지, 과도한 추상화나 불필요한 결합을 새로 만들지 않았는지 본다. "나중에 필요할 수도 있어서" 만든 확장 지점은 지적한다.

## 3. 항상 확인 (정본 유무와 무관)

④ **테스트 실효성** — 이 변경이 **되살릴 수 있는 옛 결함**을 다루는가(버그 수정, 재발 방지 가드, 새 방어 코드)? 그렇다면 그 결함을 재현하는 회귀 테스트가 있는가. 신규 기능의 정상 경로에는 적용하지 않는다.

⑤ **사용자 노출 문구의 규제 위험** — 이 변경이 **사용자에게 보일 문장**을 추가·수정했는가(번역 파일, 화면에 박힌 문자열, 서버 응답을 그대로 뿌리는 자리, 에러·빈 상태 문구). 그렇다면 그 문자열만 모아 `wellness-copy-critic` 서브에이전트에 넘긴다 — 각 항목을 `파일:라인`과 원문으로 주고, **왜 그렇게 썼는지는 주지 않는다**(설명을 주면 그 옹호 논리를 그대로 흡수해 리뷰어가 아니라 변호인이 된다).

이 축만 서브에이전트로 빼는 이유는 나머지와 성격이 달라서다. ①~④는 diff를 읽으면 판정이 서지만, 규제는 **내가 방금 쓴 문장을 내가 통과시키는** 구조라 같은 컨텍스트에서 보면 통과 쪽으로 기운다. 시안 단계에서 이미 검수를 거친 문구라도 다시 본다 — 구현하며 바뀌었을 수 있고, 시안을 안 거치고 들어온 문자열(에러·빈 상태·나중에 끼운 번역)이 섞여 있다.

문구를 건드리지 않은 변경이면 이 축은 넘어간다. 서브에이전트를 쓸 수 없는 환경이면 같은 기준으로 직접 보되, 판정에 **"독립 검수 미실행"을 밝힌다**.
