# PR 리뷰 시각 자료

사용자가 머지 전에 직접 리뷰할 PR마다 한 장짜리 HTML을 만들어 대화에 띄운다. 한 줄 수정·문서만 바꾼 PR은 만들지 않는다.

## 1. 설명 방식을 먼저 정한다

- 이 PR을 한 문장으로 말한다. 예: "두 갈래였던 업로드 경로를 하나로 줄였다", "같은 값이 세 곳에 흩어져 있던 것을 한 곳으로 모았다".
- 그 문장이 가장 잘 보이는 모양을 고른다. 정해진 틀은 없다.
  - 실행 경로가 바뀌면 흐름 그림, 상태·데이터 모양이 바뀌면 상태 그림이나 전/후 표, 화면이 바뀌면 전/후 스크린샷, 그림이 필요 없으면 표나 코드 발췌.
  - 남는 것·없어지는 것·새로 생긴 것은 색이나 선으로 구분하고, 그 구분을 그림 옆에 한 줄로 밝힌다.
- 주제가 여럿이면 주제마다 따로 설명 방식을 고른다.

## 2. 이해시키는 요소가 있는지 점검한다

띄우기 전에 아래 물음에 자료만 보고 답할 수 있는지 확인한다. 답이 안 나오는 물음이 있으면 그 요소를 채운다.

| 물음 | 채우는 요소 |
|---|---|
| 이 코드가 원래 무엇을 하는가 | 처음 보는 사람 기준 2~3문장. 실제 앱이 어느 길을 타는지 |
| 무엇이 바뀌는가 | 바꾸기 전과 후를 나란히 놓은 그림·표, 핵심 diff 3~6줄 |
| 왜 바꿨는가 | 그대로 두면 생기는 문제를 한 줄로 |
| 무엇을 정했고 무엇을 버렸는가 | 구현하며 정한 설계 판단마다 고른 것 · 버린 대안 · 근거. 사용자가 정할 것이 남았으면 따로. 없으면 "설계 판단 없음 — 기계적 변경" |
| 믿어도 되는가 | 돌린 확인과 결과(검색 0건, 테스트 수, 변형 주입, 독립 리뷰, CI). 못 한 것은 "미검증"과 이유 |
| 어디부터 보면 되는가 | 먼저 볼 파일 2~3개와 훑어도 되는 파일 |
| 얼마나 큰가 | 동작이 바뀌는지(그대로 / 바뀜 / 고침), 바뀐 파일 수, `+추가 / −삭제` 줄 |

## 3. 저장과 전달

- 프로젝트 지침이 정한 작업 보고 자리(작업 폴더)에 `PR<번호>-쉬운-설명.html`로 저장한다. 팀이 보는 코드 레포 안에는 두지 않는다.
- 외부 라이브러리 없이 HTML·CSS 한 파일로 만든다.
- 브라우저로 열어 스크린샷 한 장으로 깨짐을 확인한 뒤, 파일 보내기 도구로 대화에 렌더해 띄운다(`display: render`).
- PR 본문·댓글에 올리는 것은 사용자가 요청할 때만 한다.

## 4. 쓰는 법

- 쉬운 한국어로 쓴다. 전문어·약어는 처음 쓸 때 괄호로 푼다.
- 숫자·주장은 PR 실물(`gh pr view <번호> --json additions,deletions,changedFiles`, `gh pr diff`)과 실제 실행 결과에서 가져온다. 추측은 "~였을 것"으로 한정한다.
- 세션 안에서만 통하는 판정 코드(지적 id 등)·로컬 경로·내부 논의 이력을 넣지 않는다.
