# 작업 접수 (intake)

접수는 합의된 입력(계획서 또는 작은 작업 판정)을 이 사이클의 명세로 옮기는 단계다. 멈춰도 되는
마지막 자리이므로, 계획서와 실제 코드가 어긋나는지를 여기서 다 확인한다.

## 절차

### 1. 입력을 읽는다

**계획서가 있을 때** — 머리말 `plan:`의 파일을 읽는다. 요구사항·비목표·검증 방법을 이 사이클의
기준으로 삼는다.

**이슈 번호가 있을 때** — 대상 레포 디렉터리 안에서:

```bash
gh issue view <번호> --json title,body,labels,number
```

`--json`에 `repository` 필드를 넣지 않는다 — gh CLI 버전에 따라 지원하지 않아 존재하는 이슈에도
명령이 실패한다. 대상 레포 안에서 이 명령이 성공하는 것 자체가 "이 레포 소속 이슈"라는 확인이다.
명령이 실패하면 추측으로 진행하지 않고 실패 원인(이슈 없음 / 명령 오류)을 구분해 보고한다.

### 2. 코드베이스와 대조한다

**로직 설명이 아니라 실제 값을 확인한다.** 입력이 문구·표시값·동작을 문제 삼으면 관련 코드의
주석·변수명만 보고 판단하지 말고 실제 문자열·값·동작을 직접 조회해 대조한다(주석은 이슈와 맞아
보였는데 실제 문구는 이미 다른 커밋에서 고쳐져 있던 사례가 있다).

- 이미 해결된 작업이면 구현하지 않고 근거와 함께 알린다.
- 계획서·이슈가 실제 코드와 어긋나면(없는 파일·심볼, 계획의 전제와 다른 동작) 근거를 보이고 멈춘다.
- 그 밖에는 멈추지 않는다. 이 단계를 넘기면 이후에는 [실행 절차](execution.md)의 무정지 규칙을 따른다.

### 3. `00_intake.md`를 쓴다

```markdown
## 출처

이슈 #123 — <제목>          ← 또는 계획서 제목, 또는 요청 한 줄

## 무엇을 고치나

| 파일 | 조치 |
|---|---|
| <경로> | <무엇을 어떻게> |

## 검증 조건

- `<실행 가능한 명령>` 통과
- <자동 검사가 불가능한 것> — 사람 확인

## 범위 밖

- <이번에 안 건드리는 것과 그 이유>
```

- 네 절은 관문이 검사한다. 출처는 비어 있지 않으면 된다.
- 검증 조건의 각 항목은 백틱으로 감싼 실행 명령이거나 "사람 확인"이라고 적는다. close 단계가 이
  목록을 대조 기준으로 쓴다.

### 4. 계획서가 없으면 생략 판정을 쓴다

머리말 `plan:`이 비었으면 `00_intake.md`에 아래 표를 그대로 둔다. 항목 이름과 값은 정확히 이 글자여야
한다(값은 `예` 또는 `아니오` — `아니요`도 형식 오류로 막힌다).

```markdown
## 계획서 생략 판정

| 항목 | 판정 |
|---|---|
| 요청과 다른 사용자 노출 변화 | 아니오 |
| 기능·문구·데이터 삭제 | 아니오 |
| 외부 약속 선택·변경 | 아니오 |
| 해석·선택지 둘 이상 | 아니오 |
| 한 번 되돌리기로 안 됨 | 아니오 |
```

| 항목 | `예`인 경우 |
|---|---|
| 요청과 다른 사용자 노출 변화 | 사용자에게 보이는 동작·문구가 요청에 적힌 것과 다르게 바뀐다 |
| 기능·문구·데이터 삭제 | 기능·안내 문구·데이터를 지운다 |
| 외부 약속 선택·변경 | API·저장 형식·설정 키처럼 밖과의 약속을 새로 고르거나 바꾼다 |
| 해석·선택지 둘 이상 | 요청을 둘 이상으로 읽을 수 있거나 구현 방법에 고를 선택지가 있다 |
| 한 번 되돌리기로 안 됨 | 되돌리려면 커밋 되돌리기 한 번으로 끝나지 않는다(데이터 이관·배포 순서 등) |

하나라도 `예`면 관문이 "계획서 필요"로 막는다. 그때는 draft-plan으로 계획서를 만들어 승인받고
`plan:`에 경로를 적은 뒤 다시 접수한다. 판정은 최종 보고에 그대로 인용된다.
