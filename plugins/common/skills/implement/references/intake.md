# 작업 명세 정규화 (intake)

## 왜 이 단계가 있나

이 부서는 입력을 두 갈래로 받는다 — GitHub 이슈와, 디자인 부서가 `handoffs/`에 놓은 구현 명세다.
둘은 담을 수 있는 정보가 다르다. 이슈는 팀이 보는 공개 산출물이라 로컬 경로·시안 파일 참조를
넣을 수 없고, 인계 명세는 그런 참조를 그대로 갖는다.

**분기를 여기 한 단계에 가둔다.** 이후 단계와 관문은 입력이 무엇이었는지 모른다. 분기가
파이프라인 전체로 번지면 단계마다 두 갈래를 다뤄야 하고, 그 갈래는 대개 한쪽만 검증된다.

## 절차

### 1. 입력을 읽는다

**이슈 번호일 때** — 대상 레포 디렉터리 안에서:

```bash
gh issue view <번호> --json title,body,labels,number
```

`--json`에 `repository` 필드를 넣지 않는다 — gh CLI 버전에 따라 지원하지 않아 **존재하는 이슈에도
명령 자체가 실패한다**(2026-08-24 실측). `gh issue view`는 실행한 디렉터리의 remote를 기준으로
찾으므로, 대상 레포 안에서 이 명령이 성공하는 것 자체가 "이 레포 소속 이슈"라는 확인이다.

명령이 실패하면 **중단한다.** 추측으로 진행하지 않고, 실패 원인(이슈 없음 / 명령 오류)을 구분해
보고한다.

**인계 명세일 때** — `handoffs/<파일>.md`를 읽는다. 디자인 부서 핸드오프는 이미
`## 무엇을 고치나` · `## 검증 조건` · `## 범위 밖` 구조라 절 이름만 맞추면 변환이 없다.

### 2. 코드베이스와 대조한다

**로직 설명이 아니라 실제 값을 확인한다.** 입력이 문구·표시값·동작을 문제 삼으면, 관련 코드의
주석·변수명만 보고 "맞다"고 판단하지 말고 **실제 문자열·값·동작을 직접 조회**해 대조한다.

2026-08-25 드릴 테스트 실측: 코드 주석은 이슈와 일치해 보였지만 실제 i18n 문구는 이미 다른
커밋에서 고쳐져 있어, 이슈 자체가 이미 해결된 상태였다.

이미 해결된 것으로 보이면(관련 수정 커밋을 `git log`로 확인 등) **구현을 진행하지 말고** 근거와
함께 사용자에게 알린다. 어긋나거나 해석이 갈리는 지점이 있을 때만 사용자에게 확인한다 — 그
외엔 질문 없이 다음으로 넘어간다.

### 3. `00_intake.md`를 쓴다

네 절을 반드시 넣는다. 관문이 이 절들을 검사한다.

```markdown
## 출처

이슈 #123 — <제목>          ← 또는: handoffs/2026-08-27_측정화면.md

## 무엇을 고치나

| 파일 | 조치 |
|---|---|
| <경로> | <무엇을 어떻게> |

## 검증 조건

- `<실행 가능한 명령>` 통과
- <자동 검사가 불가능한 것> — 사람 확인

## 범위 밖

- <이번에 안 건드리는 것과 그 이유>
```

**검증 조건의 각 항목은 백틱으로 감싼 실행 명령이거나 "사람 확인"이라고 적혀 있어야 한다.**
관문이 이걸 검사하는 이유는, 나중에 `close` 단계가 이 목록을 대조 기준으로 쓰기 때문이다.
"잘 되는지 본다" 같은 항목은 무엇을 확인하면 끝인지가 안 정해진 것이라 통과시키지 않는다.
