# 단계별 실행 절차 (branch ~ ship)

`cycle.py status`가 안내한 단계의 절과 아래 공통 원칙을 읽고 실행한다. 상태 전이·모드·중단 조건은
[implement](../SKILL.md)이 담당한다. 이 문서는 단계 작업과 산출물만 정한다.

## 원칙

`00_intake.md`가 이미 무엇을 고칠지와 무엇으로 끝났다고 할지를 정해 뒀다는 전제로 시작한다.
여기서는 **구현 방법을 지시하지 않는다** — 대상 레포의 `CLAUDE.md`/`AGENTS.md` 관례를 그대로 따른다.
레포 관례가 다루지 않는 코드 판단(계약·실패 표현·공개 범위·시그니처·이름 붙이는 범위·함수 분리)은
플러그인의 `references/coding-philosophy.md`(이 스킬 폴더 기준 `../../references/coding-philosophy.md`)를 따른다.

리뷰 기준은 이 문서와 [code-review-criteria.md](code-review-criteria.md)에 직접 있다.
커밋·PR은 프로젝트·전역 지침이 정한 스킬을, 없으면 `common:commit`·`common:create-pr`을 호출한다. 필요한 스킬이 없으면
첫 커밋 또는 제출 전에 그 사실을 알린다.

> **cwd 확인 습관**: Bash 작업 디렉터리는 호출 간에 지속되지만 세션 상태는 아니다.
> `implement` 시작과 매 커밋 직전에 `pwd`와 `git rev-parse --show-toplevel`로 지금 위치가
> 이 사이클의 `repo`가 맞는지 재확인한다 — 다른 작업과 섞이면 조용히 엉뚱한 곳에 커밋된다.

### 작은 변경마다 검증·커밋

구현·정리·리뷰 지적 수정·문서 수정에서는 **작은 변경 → 해당 검증 → 커밋 스킬**을 반복한다.
작업 전체가 끝날 때까지 커밋을 미루지 않는다. 한 단계에 여러 커밋이 들어갈 수 있으며,
단계마다 하나씩 맞출 필요는 없다. 함께 있어야 동작하는 코드와 설명은 같은 커밋으로 묶는다.
변경 없는 점검에는 빈 커밋을 만들지 않는다.

- 매 커밋 전에 그 변경에 맞는 타입 검사·테스트·문서 링크 확인 등을 실제 실행한다.
  실패하면 수정 후 다시 검증하고, 실행하지 못했다면 이유를 알린다. 검증 통과로 기록하지 않는다.
- 작성자는 대상 레포의 git 설정을 그대로 쓴다. `GIT_AUTHOR_NAME`·`GIT_AUTHOR_EMAIL`·`--author`로
  덮어쓰지 않는다. 서브에이전트에 커밋을 맡길 때도 이 규칙을 명시한다.
- 포맷 검사 실패는 레포의 포맷 쓰기 명령으로 고쳐 재시도한다. `--no-verify`로 우회하지 않는다.
- 해당 단계 산출물에 무엇을·왜 바꿨는지, 검증 명령·결과와 커밋 해시를 남긴다.
  커밋한 변경이 이후 정리·리뷰로 바뀌면 다시 검증하고, 바꾼 기능 커밋을 대상으로
  `git commit --fixup=<대상 해시>`로 후속 커밋을 만든다. 후속 커밋은
  [커밋 정리](#커밋-정리--docs-완료-뒤-ship-실행생략-전)에서 기능 커밋에 합친다.

### 합의 밖 판단 — 멈추지 않는다

리뷰 지적으로 설계를 바꾸는 경우를 포함해 [멈추는 곳](../SKILL.md#멈추는-곳) 규칙을 따른다.
계획서는 고치지 않는다(승인받은 정적 문서다).

### 정리·리뷰 범위

정리·리뷰에는 `handoff.md`의 `base`를 기준으로 **이미 커밋한 작업 전체**와 재개 중인 변경을
함께 전달한다. `git diff <base>...HEAD`와 `git diff HEAD`,
`git ls-files --others --exclude-standard`로 커밋된 변경·미커밋 변경·새 파일을 확인한다.
스킬·서브에이전트를 호출할 때도 이 범위를 명시하고, 산출물에 검토한 base와 HEAD를 기록한다.

## branch — 브랜치·작업 위치

### 브랜치명 (이 문서가 직접 계산한다)

기본 관행: `<타입>/<이슈번호>-<요약>`. 프로젝트 지침이 다른 형식을 정하면 그것을 따른다.

- **타입**: 라벨에 `bug`/`fix` 계열이면 `fix`, `feature`/`enhancement`면 `feat`, 문서면 `docs`,
  테스트면 `test`, 정리성이면 `chore`/`refactor`. 라벨이 모호하면 제목의 동사·명사로 추론한다.
- **요약**: 제목을 소문자 kebab-case로 3~5단어 축약.
- 예: 이슈 #42 "설정 화면 저장 버튼이 두 번 눌림" → `fix/42-settings-double-save`

### 작업 위치

레포가 정한 방식을 우선순위대로 시도한다.

1. 팀 공유 워크트리 생성 경로가 있으면 그것 — `worktree-setup` 스킬, `npm run wt:new` 등
   (프로젝트에 있으면).
2. 없으면 `scripts/worktree-create.sh <브랜치명> --base <base>`.
3. 그것도 없으면 `git worktree add <경로> -b <브랜치명>`으로 대체하고, `.env` 등 미추적 설정은
   수동 확인이 필요할 수 있다고 최종 보고에 남긴다.

`--main`을 지정받았거나 레포 지침이 main 직접 커밋을 정했으면 워크트리를 만들지 않고 현재
위치에서 진행하되, `handoff.md` 머리말에 `allow_main: true`를 적는다 — 관문은 산출물 산문이
아니라 이 스위치를 본다. 이때 `base`에는 브랜치 이름 대신 **첫 변경 전의 커밋 해시**
(`git rev-parse HEAD`)를 적는다. base와 작업 브랜치가 같은 main이면 관문이 셀 커밋 범위가 비어
제출·종결을 넘지 못한다.

### 산출물과 상태

`01_branch.md`에 브랜치명·작업 경로·base를 적고, **`handoff.md` 머리말의
`repo`·`branch`·`base`(+ 메인에서 작업하면 `allow_main`)를 채운다.** 관문이 그 값으로 실제
git을 돌리므로 여기가 정본이다. `base`는 비워 두면 관문이 멈춘다 — 기본 브랜치가 `develop`인
레포에서 `main`으로 조용히 대체되면 엉뚱한 커밋 집합을 검사하게 되기 때문이다.

## implement — 구현

명세가 요청한 변경을 작은 동작 단위로 구현하고, 공통 원칙에 따라 각각 검증·커밋한다.
코드를 쓰기 전에 레포 코딩 지침(없으면 `coding-philosophy.md`)을 읽고, 새로 만드는 공개 함수마다 같은 문서 12장의
네 가지(시그니처, 숨은 상태, 본문의 전제 검사, 조용한 실패)를 스스로 확인한다.
`02_implement.md`에 바꾼 것을 목록으로 남긴다.

## simplify — 정리

`simplify` 스킬이 있으면 호출해 재사용·중복·불필요 코드를 정리한다.
없으면 별도 서브에이전트에 대상 저장소·변경 diff를 주고 같은 세 관점으로 읽기 전용 검토를
맡긴 뒤 지적을 반영하고 관련 검증을 다시 돌려 커밋한다. 독립 검토 도구도 없으면 미실행임을
알리고 이 단계를 완료하지 않는다.
`03_simplify.md`의 `## 정리 결과` 절에 무엇을 정리했는지 적는다. 정리할 게 없었으면 "없음".

## review — 코드 리뷰

[code-review-criteria.md](code-review-criteria.md)대로 관점별 서브에이전트(정확성·계약, 가독성·명확성,
최소 변경, 테스트, 해당하면 사용자 노출 문구)를 한 응답에서 병렬로 띄우고, 보고를 대조·재확인해 판정한다.

`04_review.md`의 `## 판정` 절 머리에 검토한 base·HEAD, 띄운 관점, 각 보고가 밝힌 HEAD를 한 줄씩 적고,
지적을 표로 남긴다:

```markdown
| 등급 | 내용 | 반영 |
|---|---|---|
| 🔴 | 외부 입력이 검증 없이 쓰인다 | 반영(3f791317) |
| 🔴 | 오류 문구가 내부 예외 메시지를 그대로 노출한다 (ko.json:142) | 반영(8af26bdd, 5f3182cc: 문구 키 분리) |
| 🟡 | 변수명이 모호하다 | 미반영 |
```

🔴 행의 반영 칸은 `반영(<고친 커밋 해시>)`로 쓴다. 해시는 7자리 이상, 여럿이면 쉼표로 잇고 설명은 `:` 뒤에 둔다. 관문은 낱말이 아니라 해시마다 이 브랜치 `base..HEAD` 커밋에 있는지를 본다.

문구 검수 지적도 **같은 표에 넣는다**. 별도 절이나 전용 관문을 만들지 않는 것은 의도적이다 —
🔴이면 다른 🔴과 똑같이 관문이 막으므로, 새 검사 코드 없이 이미 있는 관문이 그대로 일한다.

등급의 정의와 무엇을 고칠지는 리뷰 기준 문서가 정한다 — 여기서 다시 적지 않는다. 관문이
막는 것은 반영 칸이다: 🔴 행이 하나라도 미반영이면 넘어가지 못한다. 지적이 하나도 없었으면
절에 "없음"이라고 적는다(빈 절은 리뷰를 했는지 알 수 없어 관문이 막는다).
지적을 수정했다면 해당 변경을 검증하고 커밋한 뒤 판정에 반영한다.

## 커밋 정리 — docs 완료 뒤, ship 실행·생략 전

제출 모드와 상관없이 한다. 목표: `base..HEAD`의 각 커밋이 기능·변경 단위 하나를 담고, 제목만 읽어도
무엇이 바뀌었는지 알 수 있다. "리뷰 반영"·"정리"·"수정"처럼 경위만 말하는 커밋을 남기지 않는다.

결과는 `08_close.md`의 `## 커밋 정리` 절에 적는다(close 때 이 절을 지우지 않는다).

1. `git log --format='%h %s' <base>..HEAD`를 본다. 정리·리뷰 지적 수정·문서 수정 커밋이 앞선 기능 커밋의
   코드를 고쳤거나 제목이 경위만 말하면 정리한다. 이미 기능 단위면 `## 커밋 정리`에 "불필요"와 이유를 적고 끝낸다.
2. 브랜치가 이미 원격에 있으면(`git ls-remote --heads origin <브랜치>`가 한 줄 이상) 정리하면 강제 push가 필요하다.
   착수 전 합의에 강제 push 승인이 없으면 정리하지 않고 `## 커밋 정리`에 "원격 브랜치 있음, 정리 생략"을 적는다.
3. 정리 전 HEAD를 `## 커밋 정리`에 적고(`git rev-parse HEAD`), 같은 해시에 백업 브랜치 `backup/<브랜치>-before-regroup`을
   만든다. 이미 있으면 이름 뒤에 정리 전 HEAD의 짧은 해시를 붙인다.
4. 후속 커밋마다 합칠 기능 커밋을 정해 `## 커밋 정리`에 대응표(후속 커밋 해시·제목 → 대상 커밋 해시·제목)로 적는다.
5. 합친다. 편집기를 여는 명령은 쓰지 않는다:
   - 후속 커밋이 처음부터 `git commit --fixup=<대상>`으로 만들어졌으면 `GIT_SEQUENCE_EDITOR=true git rebase -i --autosquash <base>`.
   - 그 밖에는 순서 파일을 고치는 스크립트를 쓴다: `GIT_SEQUENCE_EDITOR='<스크립트>' git rebase -i <base>`.
     스크립트는 대응표대로 후속 커밋 줄을 대상 커밋 줄 바로 뒤로 옮기고 `pick`을 `fixup`으로 바꾼다.
     합친 뒤 설명이 달라진 대상 커밋은 그 묶음 바로 뒤에 `exec git commit --amend -F <메시지 파일>` 줄을 넣는다(메시지는 커밋 스킬 규칙으로 파일에 먼저 쓴다).
   - 충돌로 멈추면 `git rebase --abort`로 되돌리고 `## 커밋 정리`에 "충돌, 정리 생략"과 충돌한 커밋을 적는다.
   - 한 커밋에 여러 기능이 섞여 있어 합치기로 풀 수 없으면 base에서 최종 트리를 파일 단위로 나눠 다시 쌓는다.
6. 검증한다. 하나라도 어긋나면 `git reset --hard <백업 브랜치>`로 되돌리고 원인을 고쳐 5부터 다시 한다:
   - `git diff <정리 전 HEAD> HEAD`가 0줄이다.
   - 모든 커밋에서 타입 검사가 통과한다: `git rebase -x '<타입 검사 명령>' <base>`. 실패로 멈추면 `git rebase --abort` 뒤 그 커밋을 고친다.
     레포가 원래 타입 검사 오류를 안고 있으면 base의 오류 수를 기준으로 삼아 "기준보다 늘지 않음"을 본다.
   - 커밋 작성자가 바뀌지 않았다(`git log --format='%an <%ae>' <base>..HEAD`).
   - 현재 브랜치가 사이클 브랜치다(`git branch --show-current`).
7. 산출물의 해시를 정리 뒤 해시로 바꾼다. 새 해시는 대응표의 대상 커밋 제목으로 찾는다(`git log --format='%h %s' <base>..HEAD`):
   - `04_review.md` 판정표의 `반영(<해시>)`를 그 수정이 합쳐진 커밋의 새 해시로 고친다.
   - `02_implement.md`·`03_simplify.md`·`05_docs.md`에 적은 커밋 해시도 고친다. 대응을 못 찾은 해시는 지우지 말고
     "정리 전 해시, 백업 브랜치에 있음"으로 표시한다.
   - `04_review.md` 판정 머리의 검토 HEAD와 보고별 HEAD는 바꾸지 않고 "정리 전 해시"로 표시한다.
8. `cycle.py <사이클 폴더> status`로 완료된 단계의 관문을 다시 통과하는지 확인한다. review 관문이
   "반영 커밋이 이 브랜치 커밋에 없음"으로 막히면 7을 다시 한다.
9. `## 커밋 정리`에 백업 브랜치 이름, 정리 뒤 커밋 목록, 6의 검증 결과를 적는다. 백업 브랜치는 PR 머지 뒤 지운다고 최종 보고에 한 줄 남긴다.

## ship — push·PR (자동 모드에서만)

실제 push 직전에 `cycle.py <사이클 폴더> status`를 다시 실행한다. 종료코드가 0이고
다음 단계가 ship일 때만 진행한다. 이 검사에서 `base..HEAD` 커밋 전량의 작성자 이메일과
커밋 존재·깨끗한 작업트리를 확인한다. 실패했다면 원인을 해결하고 재검사한다.

현재 상태가 제출을 요구하고 사용자 승인도 있을 때만 수행한다. 리터럴 `--auto`와 승인된 플랜의
`제출: push·PR까지`가 이 승인이다([제출 모드](../SKILL.md#제출-모드)). Codex에서는 아래 Claude 전용
리스 명령을 실행하지 않고, Codex의 권한·승인 절차와 대상 저장소의 push 규칙을 따른다.
push 확인 훅(예: push 확인 훅)을 쓰는 환경이면 리스(lease)가 있을 때만
push·PR 생성을 무개입 통과시킨다. 이 경우에만 아래 리스를 생성하고 마지막에 해제한다.

```bash
repo_root=$(git rev-parse --show-toplevel)
<push 확인 훅이 정한 리스 생성 명령> --repo "$repo_root"
```

**push** — `git push -u origin <브랜치명>`(신규) 또는 `git push`(추적 중). 결합 명령이나 강제
옵션을 섞지 않는다 — 섞으면 리스가 있어도 확인을 받는다(의도된 동작). 예외: 커밋 정리로 원격 브랜치와
갈라졌고 착수 전 합의에 강제 push 승인이 있으면 `git push --force-with-lease`만 쓴다.

**PR 생성** — 프로젝트·전역 지침이 정한 PR 스킬(없으면 `common:create-pr`)을 호출하고, 만들어진 PR URL을 `07_ship.md`에 적는다.

> **PR 스킬이 중단하면 즉시 리스를 해제한다.** PR 스킬은 워킹트리 dirty·base 모호·blocker
> 존재 시 의도적으로 멈추도록 설계돼 있다. 그 순간 리스가 살아있으면 이후 수동 재시도가
> 화이트리스트를 통해 새어나갈 수 있다.

**리스를 생성했다면 항상 마지막에 (성공·실패·중단 무관하게)**:

```bash
<push 확인 훅이 정한 리스 해제 명령> --repo "$repo_root"
```

PR 머지는 이 파이프라인이 하지 않는다 — 항상 사람이 확인한다.
