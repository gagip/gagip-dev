# Write Docs

읽는 사람이 되묻지 않고 바로 판단·행동할 수 있고, 모든 사실이 출처로 확인된 문서를 만든다.

## 완료 기준

- 독자와 이 문서로 할 일이 한 줄로 정해져 있다.
- 문서의 사실마다 출처가 있고, 직접 보지 못한 것은 문서의 「확인 필요」 칸에 있다.
- 문서 종류 가이드라인을 따랐다.
- 맥락 없는 검토자가 문서만 읽고 막힌 곳을 고쳤다.
- 게시 전 검사를 통과했거나, 남긴 줄마다 화면에 실제로 보이는 제품 용어라는 이유를 보고에 적었다.

## 1. 문서 종류를 고르고 가이드라인을 연다

| 종류 | 쓰는 때 | 가이드라인 |
|---|---|---|
| 기능 명세 | 이미 있거나 곧 만들 기능의 동작을 팀이 기준으로 삼을 때 | [references/기능-명세.md](references/기능-명세.md) |
| 기획 계획서(PRD) | 새 기능을 왜·무엇을 만들지 팀이 계속 참고할 때 | [references/기획-계획서.md](references/기획-계획서.md) |
| 결정 문서 | 선택지를 비교해 정하거나 정한 내용을 남길 때 | [references/결정-문서.md](references/결정-문서.md) |
| 제품 방향 문서 | 누구의 어떤 문제를 풀고 무엇을 하지 않을지 제품 전체의 기준으로 삼을 때 | [references/제품-방향.md](references/제품-방향.md) |

승인 뒤에도 사람들이 계속 읽는 문서인지로 판정한다. 승인으로 역할이 끝나는 착수 합의용 계획서는 이 스킬로 쓰지 않는다. 이 판정이 모호할 때만 독자가 누구인지 한 번 묻는다.

프로젝트 지침에서 저장 위치와 작업 폴더를 찾는다. 같은 종류의 기존 문서가 있으면 한 편을 열어 절 구성과 표 형식을 맞춘다. 문장 규칙, 출처 규칙, 결정 문서 상태 규칙은 기존 문서와 달라도 이 스킬을 따른다. 기존 문서의 내용은 사실표에서 원본으로 다시 확인한다.

## 2. 독자와 목적을 한 줄로 쓴다

```
독자: <직무·역할> / 읽고 나서 할 일: <판단·행동 하나>
```

독자가 정해지면 쓸 낱말과 뺄 정보가 정해진다. 요청에 독자가 없으면 문서 종류와 맥락으로 추정하고 완료 보고에 밝힌다.

## 3. 사실표를 쓴다

문서를 쓰기 전에 작업 폴더에 `<문서 이름>_사실표.md`를 만든다. 작업 폴더가 없으면 문서가 저장될 폴더 밖에 `<문서 이름>_작업/`을 만든다. 이 표는 게시하지 않는다.

```markdown
| 문서에 쓸 사실 | 출처 | 확인 |
|---|---|---|
| 측정 알림 기본 시각은 20:00 | src/alarm.ts 41행 | 직접 봄 |
| 분석 완료 푸시 문구는 서버가 정함 | 앱 코드에 발송부 없음, 서버 코드 못 봄 | 미확인 |
```

- 출처는 코드 위치, 실행 화면, 서버 응답, 원문 쪽수처럼 다시 열 수 있는 실물로 쓴다.
- 메모, 옛 계획서, 앞선 문서, 대화, 기억은 출처로 쓰지 않는다. 그 안의 사실은 원본을 열어 확인한다. 문서끼리 또는 문서와 코드가 다르면 코드와 실행 결과를 기준으로 하고 다른 점을 표에 적는다.
- 기획 의도와 결정은 코드에 없다. 사용자가 이번 요청에서 말한 내용, 사용자가 지정한 기획서·시안·회의 기록을 출처로 쓰고 인용 위치를 적는다. 없으면 지어내지 않고 미확인으로 둔다.
- 상태 값과 오류의 뜻은 이름으로 짐작하지 않고 발동 조건을 코드에서 읽는다.
- 환경과 시점을 나눈다: 개발 서버와 운영 서버, 코드에 있음과 출시 빌드에 포함됨, 사내 규칙과 원문 규정.
- 규정을 인용할 때는 적용 대상까지 원문에서 확인한다.
- 제약을 적을 때는 바꿀 수 없는 것인지 확인한다. 「할 수 없다」, 「없다」는 쓸 수 있는 도구로 시도한 뒤에 쓴다.
- 다른 팀에 맡길 일로 적기 전에 이미 되는 기능인지 코드에서 확인한다.

## 4. 초안을 쓴다

가이드라인의 절 순서로 쓴다. 사실표에 없는 단정 문장은 쓰지 않는다. 미확인 줄은 본문에 단정하지 않고 「확인 필요」 칸에 무엇을 누구에게 확인할지와 함께 올린다. 자료끼리 대조한 내용은 문서에 옮기지 않고, 정해야 할 것만 「확인 필요」에 올린다.

문장 규칙:

- 개조식으로 쓰고 「~함」, 「~없음」처럼 맺는다. 대화체를 쓰지 않는다.
- 본문에 파일 이름, 함수 이름, PR·이슈 번호, 내부 코드값을 넣지 않는다. 개발자에게 필요한 근거는 문서 끝 접힌 「개발 참고」에 둔다.
- 작업 경위, 회의·검토 날짜 꼬리표, 세션 안에서만 통하는 이름을 쓰지 않는다.
- 문장마다 대상·값·행동을 담는다. 없으면 지운다.
- 항목마다 독자가 이것으로 무엇을 하는지 답한다. 답이 없으면 지운다.
- 전문어와 약어는 처음 쓸 때 푼다.

## 5. 검토하고 검사한다

맥락 없는 검토자에게 문서 경로, 사실표 경로, 2단계의 독자·목적 줄, [references/review-rubric.md](references/review-rubric.md) 경로만 준다. 서브에이전트를 못 쓰면 같은 기준으로 직접 보고 완료 보고에 「독립 검토 미실행」을 밝힌다. 지적을 고친 뒤 사실표와 문서를 대조해 표에 없는 단정 문장을 지운다.

게시 전 검사를 실행한다.

```bash
python3 <이 스킬>/scripts/check_doc.py <문서 경로>
```

걸린 줄을 고치거나 「개발 참고」로 옮긴다. 화면에 실제로 보이는 제품 용어만 그대로 두고 완료 보고에 이유를 적는다. 코드 이름, 파일 이름, 번호는 남기지 않는다.

노션 같은 외부 게시는 사용자 승인 뒤에 한다.

## 6. 보고한다

```
문서: <경로>
사실표: <경로> (직접 봄 N줄, 미확인 M줄)
독자·목적: <한 줄>
확인 필요: <항목 목록>
검토: <고친 내용 한 줄 또는 독립 검토 미실행>
게시 전 검사: <통과 또는 남긴 줄과 이유>
```
