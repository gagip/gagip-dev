# 기능 명세 가이드라인

기본 독자는 기획자·디자이너·대표처럼 코드를 읽지 않는 사람이다. 본문만 읽고 기능의 의도와 상황별 동작을 판단할 수 있어야 한다.

## 절 구성

1. **기획 의도**: 문제, 대상 사용자, 목표, 설계 원칙. 현재 동작 설명으로 대신하지 않는다.
2. **화면**: 실제 화면 캡처에 번호와 한 줄 설명을 붙인다. 기본·빈·불러오는 중·실패·권한 꺼짐처럼 상태마다 넣는다. 못 찍은 상태는 「미캡처」로 적고 이유를 쓴다.
3. **흐름**: 진입부터 끝까지 분기를 그림이나 번호 목록으로 쓴다. 분기가 없으면 뺀다.
4. **화면 규칙**: 화면마다 `항목 | 규칙` 표. 화면 문구는 그대로 인용하고 값을 숫자로 쓴다.
5. **예외 처리**: `상황 | 표시` 표. 실패·빈 값·권한·네트워크를 빠짐없이 쓴다.
6. **개발 중 결정 사항**: 사용자가 지정한 기획서·시안에 없었는데 구현에서 정해진 동작. 비교할 자료가 없으면 뺀다.
7. **범위 외**: 이 기능이 하지 않는 것과 다른 문서가 맡는 것.
8. **확인 필요**: 무엇을 누구에게 확인할지, 답이 없으면 어떻게 둘지.

문서 끝에 접힌 **개발 참고**를 둔다: 기준 코드와 커밋, 파일, 경로, API, 관련 PR. 노션은 토글, HTML은 `<details>`, 마크다운은 `## 개발 참고` 절로 쓴다.

## 현재 동작 문서와 신규 기능 문서

- 현재 동작을 정리하는 문서면 첫 줄에 기준 앱 버전과 기준 날짜를 쓰고, 커밋은 개발 참고에 쓴다. 코드에 있는 대로 쓰고, 바꾸고 싶은 점은 「확인 필요」로 올린다.
- 신규 기능용 칸(목표 지표, 일정 등)은 현재 동작 문서에 빈칸으로 채우지 않는다.
- 아직 없는 기능을 적을 때는 절 제목이나 줄에 「예정」을 밝힌다.

## 견본

```markdown
**목표**

- 결과 화면에서 다음 날 측정 알림을 제안, 기본 시각은 그 결과의 측정 시각

| 항목 | 규칙 |
| --- | --- |
| 저장 | 저장 버튼 없음. 바꾸면 즉시 저장, 저장 중 토글 비활성 |

| 상황 | 표시 |
| --- | --- |
| 저장 실패 | 토글 되돌림 + 「저장하지 못했어요. 다시 시도해 주세요.」 |
```
