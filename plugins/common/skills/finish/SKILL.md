# finish

작업 끝의 반복 체인 `정리 → 리뷰 → 문서 점검 → 커밋 → push → PR`을 한 호출로 묶는다.
세션 로그 분석 결과 이 체인(특히 `commit → create-pr`, `simplify → code-review`)이 가장 빈번한
수동 반복이었다 — 단계마다 다음 스킬을 손으로 부르던 것을 한 번에 잇는다.

> **핵심 원칙: 커밋·PR 스킬을 하드코딩하지 않는다.**
> 저장소 전용 커밋·PR 스킬은 다른 환경에 없을 수 있다. 커밋 단계와 PR 단계는 항상
> **그 프로젝트에 적용되는 스킬을 감지해서** 이어 수행한다(아래 Step 4·Step 6).

---

## 실행 절차

호출과 함께 전달된 자연어 인자에서 스킵 옵션을 먼저 파싱한다(`no-simplify`/`no-review`/`no-pr`).

다른 스킬로 이어갈 때 스킬 호출 도구가 있으면 대상 스킬을 호출한다. 없으면 사용 가능한 스킬
목록에서 대상 지침을 찾아 읽고 현재 에이전트가 그대로 수행한다. 대상 지침도 없으면 조용히
건너뛰지 말고 사용자에게 알린다.

### Step 0: 변경 확인

```bash
git status --short && git diff --stat
```
변경이 없으면 즉시 중단하고 사용자에게 알린다(커밋할 것 없음).
현재 브랜치가 `main`/`master`/`develop`이고 적용 중인 프로젝트 지침이 직접 작업을 허용하지 않으면
**경고**하고 계속할지 확인한다. 프로젝트 지침이 직접 작업을 명시적으로 허용하면 그 규칙을 우선한다.

> 이 빈 변경 체크는 "정리·리뷰 전" 기준이다 — Step 1·2(simplify·code-review `--fix`)가 새 변경을
> 만들 수 있으므로, 그 단계 후 변경이 생기면 정상 진행한다.

### Step 1: 코드 정리 (`no-simplify`면 생략)

`simplify` 스킬을 호출해 reuse·중복·불필요 코드를 정리한다.

### Step 2: 코드 리뷰 (`no-review`면 생략)

`code-review` 스킬을 **effort `medium`**, **위험 지적만 수정**(`--fix`)으로 호출한다.

> **effort 정규화:** code-review에 넘기는 effort는 항상 유효값(`low`/`medium`/`high`/`max`/`ultra`)
> 중 하나로 **명시 전달**한다. 오타(`meduim`)나 미지정이면 기본값 `medium`으로 교정해서 넘긴다 —
> 인식 못 한 값을 넘기면 의도와 다른 강도로 실행될 수 있으므로 추측에 맡기지 않는다.

리뷰가 🔴 위험(버그·보안·데이터 손상)을 지적하면 그것만 반영하고, 스타일/취향은 건너뛴다.

### Step 3: 문서 점검 — 이 변경이 어긋나게 만든 문서 찾기

코드는 리뷰를 받지만 문서는 아무도 안 보는 채로 틀린 상태가 된다. PR 시점이 가장 싸게 고칠
마지막 자리다. 아래 중 **해당되는 것만** 본다.

1. **이 작업이 참조하거나 이끈 문서** — `README`·프로젝트 지침 파일·레포 `docs/`·구현 계획서가 이제
   틀리거나 "예정 → 완료"로 바뀌었나.
2. **바꾼 계약·인터페이스** — 실행 명령어·파일 경로·설정 키·환경 변수·API 요청/응답을 바꿨으면
   그것을 적어 둔 문서가 따라왔나. 특히 남이 그대로 복사해 쓰는 명령은 틀리면 곧장 막힌다.
3. **이번에 드러난 재사용 지식** — 팀이 다시 걸릴 뻔한 함정이면 별도 지식 저장소 후보다.

빠르게 훑는 방법: 이번 diff에서 **사라지거나 이름이 바뀐 식별자**(클래스·상수·설정 키·문자열 키)를
추려 `grep -rn <이름> --include="*.md"` 로 문서를 훑는다. 0건이면 "문서 영향 없음"이 확인된 것이다.

**어디에 반영하나**
- **그 레포 안 문서**(`README`·`AGENTS.md`·`CLAUDE.md`·`docs/`)는 **같은 커밋/PR에 함께** 넣는다 — 코드와 설명이
  갈라지면 다음 PR까지 틀린 채로 남는다. 그래서 이 단계가 커밋보다 앞에 있다.
- **레포 밖 문서**는 PR에 넣을 수 없으므로 **무엇을 어디에 고칠지 목록으로 제시**하고 사용자가
  고르게 한다. "어긋났다"로 끝내지 말고 파일과 틀린 대목을 짚는다.

**결과를 한 줄 남긴다** — 고쳤으면 무엇을, 볼 게 없으면 "문서 영향 없음". 점검 자체를 건너뛰지 않는다.
레포가 크거나 어디가 어긋났는지 판단이 안 서면 문서·코드 불일치를 훑는 읽기 전용 서브에이전트를 쓴다.

### Step 4: 커밋 — **프로젝트 규칙 자동 감지**

커밋 스킬을 다음 우선순위로 **감지**해서 호출한다(하드코딩 금지):

1. 현재 하네스가 읽는 프로젝트 지침 파일(`AGENTS.md`, `CLAUDE.md` 등) 중 현재 위치에서 가장
   가까운 적용 범위에 커밋 스킬이 명시돼 있으면 그것
   (예: `gagip-dev` → `plugin-commit`)
2. 없으면 현재 하네스가 실제로 로드한 전역 지침에 명시된 커밋 스킬
3. 둘 다 없으면 폴백 `common:commit`

> **이어 수행 전 가용성 확인(사전조건):** 감지한 커밋 스킬이 현재 세션에 **실제 로드돼 있는지** 확인한다.
> 저장소 전용 커밋 스킬은 다른 레포에선 없을 수 있다(이 스킬 자신은 common 플러그인이라
> 어디든 따라가지만, 부품은 아니다). 감지한 스킬이 없으면
> 조용히 넘기지 말고 "감지된 `<X>` 스킬이 이 환경에 없어 `common:commit`으로 폴백합니다"라고
> 사용자에게 알린 뒤 폴백한다.

> 판단 기준: "이 프로젝트에서 커밋은 무슨 스킬로 하라고 적혀 있는가". 적혀 있으면(그리고 로드돼 있으면)
> 그걸 따르고, 없을 때만 범용 `common:commit`을 쓴다. 다른 저장소의 전용 스킬을 가정하지 않는다.

작은 단위로 나눠 커밋하는 게 적절하면 그렇게 한다(커밋 시점 컴파일 가능 상태 유지).

### Step 5: push — **사용자 확인 게이트** (`no-pr`면 Step 6과 함께 생략)

push는 **반드시 사용자 확인을 받고** 진행한다(커밋 원칙: 원격 push 전 확인 필수).
사용자가 이미 "push까지" 명시했으면 바로 진행한다.

- `gagip-dev` 등 `release` 스킬을 쓰는 레포에서는 `git push`를 직접 호출하지 말고
  그 레포 규칙대로 `release` 스킬을 거친다(프로젝트 지침을 따름). **단 `release` 스킬이 현재
  로드돼 있을 때만** — 없으면 사용자에게 알리고 `git push`(확인 후)로 폴백한다.
- 그 외는 push 후 Step 6.

### Step 6: PR 생성/갱신 — **프로젝트 규칙 자동 감지** (`no-pr`면 생략)

PR 스킬을 다음 우선순위로 **감지**해서 호출한다(Step 4의 커밋 스킬과 같은 원칙 — 하드코딩 금지):

1. 현재 하네스가 읽는 프로젝트 지침 파일 중 현재 위치에서 가장 가까운 적용 범위에 PR 스킬이 명시돼 있으면 그것
2. 없으면 현재 하네스가 실제로 로드한 전역 지침에 명시된 PR 스킬
3. 둘 다 없으면 폴백 `common:create-pr`

> **호출 전 가용성 확인(사전조건):** 감지한 PR 스킬이 현재 세션에 **실제 로드돼 있는지** 확인한다.
> 저장소 전용 PR 스킬은 다른 레포엔 없을 수 있다. 감지한 스킬이 없으면 조용히 넘기지 말고
> "감지된 `<X>` 스킬이 이 환경에 없어 `common:create-pr`으로 폴백합니다"라고 알린 뒤 폴백한다.
> **폴백 대상까지 없거나 비활성화된 경우**(사용자가 settings.json에서 껐을 수 있다) `gh pr create`를
> 임의로 직접 실행하지 말고 — PR 스킬은 base 판정·중복 PR 확인 같은 안전 검사를 담고 있다 —
> 어떤 스킬로 PR을 만들지 사용자에게 확인한 뒤 진행한다.

PR 본문에 **private 경로·내부 코드명·개인 메모를 넣지 않는다**(반복 교정 지점이었음).
base 브랜치가 기본값(develop)이 아닐 수 있으니, 작업 맥락상 다른 base가 맞으면 사용자에게 확인한다.

### Step 7: 요약 보고

수행한 단계와 결과(커밋 해시·PR URL)를 한눈에 보고한다. 건너뛴 단계도 명시한다.
문서 점검 결과("무엇을 고쳤다" 또는 "문서 영향 없음")도 한 줄로 포함한다.

## 설계 원칙

- **기존 스킬 재사용**: finish는 새 로직을 만들지 않고 검증된 스킬을 순서대로 엮는 얇은 오케스트레이터다.
- **프로젝트 중립**: 커밋·push·PR 스킬은 모두 프로젝트 규칙을 따른다. 회사/개인 어디서나 동작.
- **안전 게이트 유지**: push 전 사용자 확인, base 브랜치 확인, main/develop 직접 작업 경고는 생략하지 않는다.
- **이슈→PR 오케스트레이터의 부품**: 상위 파이프라인 스킬이 구현 후 단계로 finish를 재사용한다.
