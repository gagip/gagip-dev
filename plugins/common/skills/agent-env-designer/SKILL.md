# Agent Environment Designer

입력으로 받은 "특정 문제(도메인)"에 대해, 그 문제를 잘 푸는 에이전트를 만들기 위한 환경 설계안을 E = {T, H, V, S, C} 프레임워크로 산출한다.

- T (Tasks) — 풀게 시킬 문제 집합
- H (Harness) — 에이전트-환경 상호작용을 관리하는 스캐폴딩(툴, 롤아웃 프로토콜, 컨텍스트 관리, 실패 시 재시도/반성 루프)
- V (Verifier) — 결과물을 점수/보상으로 바꾸는 채점기
- S (State) — 에피소드 간 상태가 이어지는지 여부
- C (Configuration) — 턴 제한, 컨텍스트 예산 등 설정값

핵심 원칙: **검증가능성(verifiability)이 판정가능성(judgeability)보다 우월하다.** 프로그램적으로 맞았는지 틀렸는지 판별 가능한 설계가, LLM에게 "이거 잘했는지 봐줘"라고 시키는 것보다 항상 우선한다. V 설계에 가장 많은 공을 들여야 한다.

## 진행 절차

### 0단계 — 문제 정의 및 목적 확인

사용자가 문제를 한두 문장으로만 던졌다면, 다음을 짧게 확인한다(모호할 때만 AskUserQuestion 사용, 이미 충분히 구체적이면 생략하고 바로 진행):

- 이 환경의 용도가 **(a) 실제 RL 훈련용**(API/파인튜닝 접근 권한과 컴퓨팅 예산이 있는 경우)인지, **(b) 추론 시점 에이전틱 루프/Skill 설계용**(Claude Pro 등 일반 개발 환경에서 프롬프트·툴·검증 스크립트로 구현하는 경우)인지. 대부분의 사용자는 (b)에 해당하므로 불확실하면 (b)를 기본값으로 삼고 명시한다.
- "성공"의 정의: 이 문제가 풀렸다는 것을 어떻게 알 수 있는가 (최종 산출물 예시가 있으면 좋음)
- 사용 가능한 리소스: 코드 실행 환경, 특정 도메인 데이터, 기존 테스트/체크리스트 유무

### 1단계 — V (Verifier) 먼저 설계

T보다 먼저 V를 설계한다. 검증기 설계가 전체 환경의 성패를 좌우하기 때문이다.

문제를 다음 세 범주 중 하나로 분류한다:

1. **완전 검증 가능** — 정답 대조, 코드 실행/컴파일, 수치 계산, 형식 증명(Lean 등), 스키마/타입 검증. 가능하면 항상 이 범주로 문제를 재구성할 방법을 먼저 찾는다(예: "글이 좋은가" → "이 체크리스트 항목을 모두 만족하는가"로 쪼개기).
2. **부분 검증 가능** — 체크리스트, 루브릭, 다중 기준 채점. 각 기준을 최대한 이진(pass/fail)에 가깝게 쪼갠다.
3. **판정 필요(비검증)** — 개방형 산출물(글쓰기 톤, 디자인 취향 등). 이 경우에만 LLM-판정(LLM-as-judge)을 쓰고, 되도록 여러 후보를 상대비교(그룹 내 순위)시키는 방식을 권장한다(절대점수 채점보다 게임당하기 어려움).

각 범주에 대해 구체적인 검증 메커니즘, 필요한 도구(테스트 러너, 린터, 컴파일러, 체크리스트 등), 그리고 **보상 게임화(reward hacking) 위험**을 짚는다 — 특히 정적 루브릭이나 LLM 판정을 쓸 경우, 에이전트가 검증기의 약점을 악용할 수 있는 시나리오를 최소 1개 이상 제시하고 방어책을 제안한다(예: 노이즈 주입, 동적 루브릭, 정답 은닉, 판정 기준 무작위화).

### 2단계 — T (Tasks) 설계

- 문제 인스턴스의 형식을 정의한다 (입력/출력 스펙).
- 난이도 커리큘럼을 제안한다 (쉬운 것 → 어려운 것 순서로 몇 단계).
- 데이터 소스를 제안한다: 실제 사례 수집 vs 합성 생성(역번역, 템플릿 변형 등). "작업의 자연성"을 강조 — 실제 사람이 수행하는 작업과 최대한 닮게.
- 다양성 확보 방안 (동일 패턴 반복이 아니라 여러 변형을 포함해야 하는 이유와 방법).

### 3단계 — H (Harness) 설계

- 롤아웃 프로토콜: 단일턴 Q&A인지, 다중턴 대화인지, 도구 사용이 필요한 다단계 작업인지 결정.
- 필요한 도구 목록과 각 도구의 계약(contract)을 설계: 입력 스키마, 구조화된 응답 형식({ok, data, error} 등), 타임아웃/재시도 한도, 멱등성 필요 여부.
- 컨텍스트 관리 전략: 작업이 길어질 경우(수십~수백 턴) 요약/상태 압축 전략을 제안.
- **검증 실패 시 재시도 루프(반성 사이클)를 명시적으로 설계한다.** RL처럼 가중치를 업데이트해 정책을 바꿀 수 없는 대신(추론 시점 설계에서는 모델 가중치가 고정돼 있으므로), "언어적 강화(verbal reinforcement)" 방식으로 대체한다: 행동 실행 → V로 검증 → 실패 시 무엇이 왜 틀렸는지 자연어로 자기비판(self-reflection)을 생성 → 그 비판을 다음 시도의 컨텍스트에 주입 → 재시도. 이 사이클의 최대 반복 횟수는 C(Configuration)에서 못박는다.
- **학습 기록을 단기/장기로 구분해 설계한다.** ①이번 세션/에피소드에서만 유효한 반성은 컨텍스트에 임시로 주입하고 세션 종료 시 소멸시킨다. ②다음 세션이나 다른 문제에도 일반화될 만한 반성(반복적으로 같은 실수가 나오는 패턴 등)은 Skill 파일 수정, CLAUDE.md, 메모리 문서 등 영속 저장소에 기록하도록 구체적으로 제안한다 — 무엇을, 어디에, 어떤 형식으로 적을지까지 명시한다. 이게 곧 추론 시점 환경에서 "가중치 업데이트"에 해당하는 유일한 개선 경로임을 설계안에 짧게 언급한다.
- (b) 용도(추론 시점 설계)인 경우, 이 H를 실제로 어떻게 구현할지 구체화한다: Claude Skill로 절차를 고정할지, 서브에이전트로 분업할지, MCP 커넥터/커스텀 도구가 필요한지.

### 4단계 — S (State) 설계

- 각 에피소드/작업이 서로 독립적인지(stateless), 아니면 여러 에피소드에 걸쳐 상태가 유지되어야 하는지(stateful) 결정.
- stateful이라면 무엇이 지속되어야 하는지(DB 상태, 파일시스템, 누적 메모리 등) 명시.

### 5단계 — C (Configuration) 설계

- 턴/스텝 제한, 컨텍스트 윈도우 예산을 제안하고, 이 값이 에이전트가 배울 수 있는 전략의 범위에 어떤 영향을 주는지 짧게 설명.
- H에서 설계한 재시도/반성 루프의 최대 반복 횟수와 정지 조건(더 이상 개선 없으면 중단 등)을 여기서 확정한다.
- (a) 실제 훈련용이면 트레이너/추론서버/환경 분리 구조를 간단히 제안.
- (b) 추론 시점 용도면 세션/루프의 비용·시간 상한, 정지 조건(stop condition)을 명시.

### 6단계 — 실행 경로 제안 (실현 가능성 체크)

0단계에서 확인한 용도에 따라 구체적인 다음 행동을 제안한다:

- (a) 실제 RL 훈련용이면: Gym 스타일 인터페이스 스켈레톤, 필요한 인프라(트레이너/롤아웃 워커/검증기 분리), 참고할 만한 기존 환경 생태계(재사용 가능한 공개 환경이 있는지)를 언급.
- (b) 추론 시점 설계면: 이 환경을 실제 Claude Skill 초안(트리거 문구, 절차, 검증 스크립트)이나 서브에이전트 구성으로 구체화해서 제시하고, 작은 평가셋(20~50개 케이스) 구성 방안까지 포함. H에서 설계한 반성 루프가 있다면, 그 루프가 Skill의 절차 안에 실제 단계로 반영되어 있는지 확인한다.

## 출력 형식

최종 산출물은 다음 순서의 구조화된 설계 문서로 제시한다 (헤더는 최소한으로, 표/리스트는 정보가 다면적일 때만):

1. 문제 요약 및 용도((a)/(b)) 확인
2. V — 검증기 설계 (가장 상세하게)
3. T — 작업 설계
4. H — 하네스/도구 설계 (재시도·반성 루프, 단기/장기 학습 기록 구분 포함)
5. S — 상태 설계
6. C — 설정값 설계
7. 실행 경로 제안 및 리스크(특히 reward hacking, 데이터 오염, 검증기 우회 가능성)

대화가 캐주얼한 톤으로 진행 중이었다면 과도한 격식 없이, 그러나 각 섹션의 구체성은 유지한다. 사용자가 파일로 저장을 원하면("저장해줘", "문서로 만들어줘" 등) 마크다운 파일로 작성해 전달한다.
