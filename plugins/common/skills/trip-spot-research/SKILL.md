# Trip Spot Research 스킬

여행 스팟은 시간이 지나면 정보가 쉽게 낡는다 — 휴무일이 바뀌고, 새로 생긴 맛집이 있고, 리뷰가 부실한 채로 방치된 곳도 많다. 이 스킬은 "스팟 목록 + 대상 여행 날짜"를 받아서 딥리서치 원칙(계획서 승인 후 실행)을 따르는 `Workflow`로 다음을 한 번에 처리한다: **①** 대상 날짜 기준 실제 영업 여부 재확인, **②** 후기 보강, **③** (선택) 신규 후보 발굴, **④** (노션 DB가 있으면) 결과 반영.

## 언제 쓰는가

- 이미 스팟 DB(JSON, 스프레드시트, 노션 DB 등)가 있고, 특정 날짜에 실제로 갈 수 있는지 재확인하고 싶을 때
- 스팟은 있는데 후기·평점 정보가 부실해서 보강하고 싶을 때
- 기존 스팟 목록을 유지하면서 근처의 새로운 후보를 더 찾고 싶을 때
- 조사 결과를 노션 DB에 구조적으로 반영하고 싶을 때 (선택 — 노션 없이 대화창 보고로도 끝낼 수 있음)

여행지 리서치 자체(스팟을 처음부터 발굴하는 것)가 목적이면 이 스킬보다 `light-research`나 `deep-research`가 맞다. 이 스킬은 **이미 있는 스팟 목록을 검증·보강**하는 데 특화되어 있다.

## 절차

### 1. 입력 확정

다음 세 가지를 사용자에게 확인하거나 대화 맥락에서 확정한다.

- **스팟 목록**: JSON 파일 경로가 주어지면 `Read`로 읽는다. 각 스팟은 최소 `id`(또는 `name`), `name`, `category`, 가능하면 `address`/`hours` 필드를 갖는 게 이상적이나 없어도 진행 가능(그 경우 리서치 단계에서 처음부터 확인).
- **대상 날짜**: "8/8~9"처럼 구체적 날짜(요일 포함, 필요하면 `date` 계산)를 확정한다. 여러 날짜/기간이면 각 날짜에 대해 개방 여부를 따로 판정하게 설계한다.
- **범위 조정**: 카테고리 전체를 다룰지(숙소 포함 여부 등), 사용자가 이미 논의 중인 서브셋(예: "맛집 위주로")만 다룰지 확인한다. 스팟 수가 많으면(50곳 이상) 프롬프트 하나에 다 넣기보다 카테고리별로 나눠 여러 각도로 쪼갠다.

### 2. 계획서 제시 → 승인 후 실행

`deep-research` 실행 원칙과 동일하게, 바로 실행하지 않고 계획서를 먼저 보여주고 승인을 받는다.

- **목적**: 이번 조사로 무엇을 확정하려는지 (예: "8/8·8/9 실제 영업 여부 + 후기 보강 + 노션 반영")
- **탐색 각도**: 아래 "기본 각도" 중 이번 조사에 해당하는 것만 골라 나열
- **규모**: 각도 수 + 종합 1개 + (노션 있으면) 반영 1개 = 예상 총 에이전트 수. 사용자가 토큰/할당량을 신경 쓴다고 하면 각도를 줄이거나 스팟 배치를 나눠 여러 번 돌리는 대안을 제시한다.

승인 후 `references/trip-spot-research-template.js`를 읽고 그 구조를 따라 `Workflow` 툴에 인라인 스크립트로 전달한다.

### 3. 기본 각도 (필요한 것만 선택)

템플릿은 아래 각도를 다 포함하지만, 계획서 승인 시점에 사용자 요청에 안 맞는 각도는 빼고 구성한다.

1. **휴무·영업시간 확인** — 대상 날짜(요일 계산 포함)에 실제로 열려 있는지. 정기휴무일 + 계절 임시휴무 + 예약 필수 여부까지 확인. 기존 DB에 있던 값과 다르면 반드시 표시(`note`에 "기존값 → 실제값" 형태로 남겨서 나중에 diff를 알아볼 수 있게 한다).
2. **후기 보강** — 개인 블로그(티스토리·네이버블로그 등) 우선으로 검색해 인용문·요약 수집. 공식 홍보성 콘텐츠보다 실제 방문기를 우선한다.
3. **신규 후보 발굴** (선택) — 기존 목록에 없는 인근 스팟을 찾는다. 지역/카테고리를 좁혀서 검색 각도를 명확히 잡는다.
4. **지역 이벤트/프로모션 현황** (선택) — 여행 기간에 걸친 지역 행사·할인 프로그램이 있으면 최신 상태(마감 여부 등)를 확인. 매 조사마다 필요한 건 아니므로 사용자가 언급했을 때만 넣는다.
5. **대상 DB 스키마 파악** (노션 등 반영 대상이 있을 때만) — 반영하기 전에 속성 이름·타입을 먼저 확인해서 종합 단계 출력 구조를 그 스키마에 맞춘다.

### 4. 종합 → (선택) 반영

- 종합 에이전트는 모든 각도 결과를 모아 스팟별로 병합하고, "이번 날짜에 못 가는 곳이 있는가"를 executive summary 맨 앞에 명시한다.
- 반영 대상(노션 등)이 있으면 종합 결과를 바탕으로 업데이트/신규 생성을 수행하는 에이전트를 한 번 더 돌린다. 없으면 이 단계는 생략하고 종합 결과를 바로 사용자에게 보여준다.

### 5. 결과 보고

- **휴무로 못 가는 곳**을 가장 먼저 강조한다.
- 기존 DB 값과 실제 확인값이 달랐던 항목을 표로 정리한다.
- 신규 후보를 발굴했다면 별도 목록으로 제시한다.
- 노션에 반영했다면 몇 건 업데이트/생성했는지 알려준다.

## 주의사항

- **노션 MCP로 긴 텍스트를 쓸 때 드물게 음절이 깨지는 인코딩 이슈가 있다.** 짧은 필드(태그, 한두 문장짜리 팁)는 대체로 안전하지만, 인용문·URL이 섞인 긴 리뷰 요약 필드는 쓸 때마다 다른 패턴으로 깨질 수 있고, 재시도해도 다시 깨지는 경우를 확인했다(예: "웅덩이"→"웅데이"→"웅뎅이" 식으로 매번 다르게). 이런 필드가 깨진 걸 발견하면 반복 수정으로 토큰을 태우지 말고, 짧은 필드만 고치고 긴 필드는 "노션에서 직접 확인·수정 권장"으로 안내한 뒤 넘어간다.
- 스팟 수가 많을 때 한 프롬프트에 전체를 다 넣으면 에이전트가 일부를 누락할 수 있다 — 30곳을 넘으면 카테고리별로 각도를 나누는 걸 고려한다.
- 반값여행류의 지역 지원사업처럼 접수 마감이 있는 정보는 "이 스킬을 실행한 시점" 기준 스냅샷이라는 걸 결과 보고에 명시한다 — 나중에 재확인 없이 그대로 믿고 신청 시도하지 않도록.
