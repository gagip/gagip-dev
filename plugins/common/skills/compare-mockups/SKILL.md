# 시안 비교

사용자는 글로 적은 선택지보다 나란히 놓인 화면을 보고 빨리 정확하게 고른다. 이 스킬은 무엇을 고르는지 먼저 정하고,
그것만 다른 안들을 그려 결정까지 잇는다. 고르는 것은 사용자다.

## 1. 시작 조건 확인

프로젝트 지침에서 시안 스킬·도구, 시안을 둘 폴더, 디자인 규칙을 찾는다. 시안 스킬·도구가 적혀 있으면 그리는 방법(2~6절)은
그것을 따르고, 이 절의 시작 조건·세 번 제한과 7절의 결정 기록만 지킨다. 폴더가 없으면 사용자에게 묻되 요청에 적혀 있으면 묻지 않는다.

기능 PRD(`docs/features/<기능>/PRD.md`)가 있으면 문제·근거·확인할 가정을 거기서 찾는다. 빈칸은 조사로 채우고, 조사로
알 수 없는 칸만 묻는다. 문제나 근거가 비었는데 사용자가 먼저 보고 싶어 하면 「탐색용」이라고 밝히고 그린다. 탐색용 시안은
확정안으로 고르지 않는다. 어느 쪽이든 **화면이 답할 질문 하나**를 정한다. 예: 「첫 화면에서 오늘 할 일과
이번 주 흐름 중 무엇을 먼저 보여 줄까?」

같은 질문으로 이미 몇 번 그렸는지 시안 폴더와 기록에서 센다. 한 번에 나란히 낸 안들이 한 번이고 탐색용도 센다.
세 번 안에 못 골랐으면 더 그리지 않는다. 안이 모자란 것이 아니라 질문이나 전제가 맞지 않을 가능성이 크므로, 무엇이
안 골라지게 했는지 적고 질문을 다시 정하자고 한다. PRD가 있으면 Rationale에 못 고른 이유를 날짜와 한 줄로 더한다. 사용자가 이
제한을 알고도 한 번 더 그리자고 하면 그린다. 고른 안을 다듬는 시안은 세지 않는다.

## 2. 현재 화면 진단

현재 화면을 새로 캡처해 직접 열어 본다. 코드 요약이나 남의 설명만 보고 그리면 이미 있는 요소, 순서, 테마를 틀린다.
화면을 띄울 수 없으면 코드로 재현하고 「렌더 미확인」을 밝힌다. 새 화면이라 현재 화면이 없으면 그 사실을 한 줄로 밝히고
넘어간다.

지금 화면이 질문에 답하지 못하는 이유를 화면 요소로 3~5줄 적는다. 요청을 가장 좁게 읽은 틀(문구·요소 추가)과 넓게
읽은 틀(구성 재설계)이 갈리면 진단과 함께 어느 쪽인지 묻고, 답을 받기 전에는 그리지 않는다. 요청에 범위가
정해져 있거나 사용자가 묻지 말라고 했으면 좁은 틀로 진행하고 밝힌다.

## 3. 안 그리기

갈리는 것으로 방식을 고른다.

| 갈리는 것 | 방식 |
|---|---|
| 방향·구성·강조할 것 | 바깥 틀, 데이터, 문구를 똑같이 두고 비교할 변수 하나만 다르게 한다 |
| 스타일·톤 | 데이터와 화면 목적을 똑같이 두고 안마다 참고 화면 하나를 재해석한다. 참고 화면의 경로나 주소를 적는다 |

- 안 하나를 HTML 파일 하나로 만든다. 외부 의존 없이 열리게 한다.
- 실제 데이터, 화면 문구, 디자인 토큰을 쓴다. 없는 기능·수치·필드를 지어내지 않는다. 아직 없는 값은 「예시」로 표시한다.
- 안마다 이름과 한 줄 정의, 무엇에 유리한지, 근거, 잃는 것을 적는다. 설명은 시안 화면 밖에 둔다.
- 새 요소마다 어떤 사용자 질문에 답하는지, 없으면 무엇을 못 하는지 적는다. 답이 없으면 뺀다.

## 4. 한 화면에서 비교

`index.html` 하나에 모든 안을 격자로 둔다. 행은 안, 열은 비교할 상태다. 첫 행은 현재 화면이다. 탭으로 숨기면
사용자가 기억으로 비교하게 되므로 쓰지 않는다. 칸에는 갈리는 부분만 두고 전체 화면 파일을 링크한다. 질문과 진단은
격자 위에 둔다.

브라우저로 렌더해 캡처하고 직접 열어 잘림, 겹침, 깨진 그림을 본다. 브라우저가 없으면 「렌더 미확인」을 밝힌다. 시안과
캡처는 시안 폴더에 남긴다.

## 5. 독립 비평

안마다 읽기 전용 서브에이전트에 [references/critic-role.md](references/critic-role.md), 시안 파일과 캡처 경로, 화면이 답할
질문만 준다. 설계 이유나 대화는 주지 않는다. 만든 이유를 알면 그 이유를 옹호하게 된다. 서브에이전트가 없으면 같은
기준으로 직접 보고 보고 첫 줄에 「독립 비평 미실행 — 이유」를 밝힌다. 사용자가 묻지 말라거나 빨리 보자고 한 것은
비평을 건너뛸 이유가 아니다. 틀린 값이나 깨진 화면은 고치고, 취향과 방향에 관한 지적은 그대로
보여 준다.

## 6. 보이고 묻기

비교 화면을 대화에 띄우고 아래를 보인다. 추천은 근거와 함께 표시하되 대신 고르지 않는다.

```
질문: <화면이 답할 질문 하나>
시안: <index.html 절대경로> (<몇 번째>/3, 탐색용이면 표시)

| 안 | 무엇에 유리한가 | 잃는 것 | 비평 |
|---|---|---|---|

추천: <안과 이유>
고를 것: <질문 하나>
```

피드백을 받아 다듬을 때는 직전 안을 왼쪽에 두고 바꾼 안 하나나 둘을 오른쪽에 둔다.

## 7. 결정 기록과 구현 인계

사용자가 고르면 바로 기능의 `DESIGN.md`(PRD 옆, 없으면 만든다. 기능 폴더가 없으면 시안 폴더의 `결정.md`)에 고른 안, 고른
이유와 사용자 말, 버린 안, 날짜를 적고 PRD References에 링크한다. 탐색용이면 확정하지 않고 알게 된 것만 적는다. 고른 것만으로
구현이 승인된 것은 아니다. 구현으로 넘길 때는 다음을 함께 적는다.

| 칸 | 내용 |
|---|---|
| 무엇을 고치나 | 어느 화면·파일의 어느 값을 무엇으로, 요소가 몇 층으로 나뉘는지 |
| 검증 조건 | 다 됐는지 볼 명령이나 화면 |
| 범위 밖 | 이번에 바꾸지 않을 것 |

시안의 층과 요소를 구현에서 임의로 합치거나 줄이지 않는다. 줄이고 싶으면 줄인 시안을 만들어 나란히 고르게 한다.
